## 2026-09-12 — 跨場次段落趨勢（v1.7.0「Home Turf」）

**目標**：ROADMAP「後續想做的」剩下的那一項「跨場次的主場統計（這個人在這首歌
一向強在哪一段）」。段落評分（v0.9）唱完會說「副歌 2 只有 31%」，但那句話
**每次都不一樣** —— 今天掉的可能只是沒接上氣。能拿來練歌的是另一句：
「這首歌的副歌 2 你**一向**掉 13 個百分點」。

### 難處一：平均起來算出的是「嗓子好不好」，不是「哪一段弱」

第一版的想法很直覺：把每次的段落命中率平均起來，最低的那一段就是弱點。
拿種進去的假資料跑就發現這個做法回答的是另一個問題。

感冒那天每一段都掉 15 個百分點，平均下來**每一段看起來都是弱點**；
狀況好的那天每一段都是強項。整體嗓音狀況會把所有段落一起平移，
而那個平移量比段落之間的真實差異大得多。

所以每一場**先減去那一場自己的平均**再累積 —— 比的是一場演唱的「形狀」
而不是「高度」。測試 `test_bad_voice_day_does_not_make_every_section_a_weakness`
就是釘這件事：第三場整體掉 30 個百分點但形狀不變，結論必須完全一樣。

減平均時刻意**不照音符數加權**：加權的話最長的那一段（通常就是副歌）
會主導基準線，等於拿副歌跟副歌自己比，永遠顯示不出副歌是弱點。

### 難處二：平均值分不出「三次都掉一點」與「一次崩掉」

這兩件事的平均偏差可以一模一樣，但該講的話完全不同：
前者是「這一段要練」，後者是「那天狀況不好」。把後者講成「你一向掉副歌」
是在誣賴人，而且使用者會知道那不是真的 —— 然後整塊功能就不可信了。

所以除了平均偏差還要求**方向一致性**：至少三分之二的場次同一個方向。
偏差恰好為 0 的場次兩邊都不算（它沒有表態）。加上「至少三場」與
「幅度至少 5 個百分點」（沿用單場段落評分的 `MIN_SECTION_SPREAD`，
兩邊對「值得講出來的差距」是同一個手感），一共三道門。

### 難處三：「副歌 2」在重新處理過的歌裡不是同一段

歌曲重新處理（換模型、歌詞來源變了）之後 `chorus_detector` 切出來的曲式
可能多一段主歌，後面所有編號就往後挪一位。那時候把「副歌 2」跨版本相加，
等於把兩段不同的歌混成一筆統計 —— 而且**看不出來**，數字一樣很漂亮。

解法是給每一場存一份**曲式指紋**（可評分段落的標籤依序排成一列），
只比對指紋相同的場次。以**最新一場**的曲式為準，不是用舊曲式的多數決：
否則重新處理之後新資料永遠進不來，趨勢就凍在舊版本上。

### 順手撿到的重傷：舞台頁面從 v1.4.0 起就是壞的

為了看情境背景那一版做過的事（真的開瀏覽器把畫面截下來看），這次也用
Playwright 開了舞台頁面。Console 第一行是：

```
Identifier 'SILENCE_DB' has already been declared
DuetScorer is not defined
```

`mic-agc.js` 與 `duet-scorer.js` 都在最外層宣告了 `const SILENCE_DB`
（還有值不一樣的 `ENV_RISE_TAU` / `ENV_FALL_TAU`）。舞台的 JS 是用 `<script>`
一支一支載進**同一個全域作用域**的，重複宣告 `const` 會讓後載入的
`duet-scorer.js` 在**解析階段**就丟 SyntaxError 而整支不執行；接著
`player.js` 第 118 行 `new DuetScorer(...)` 炸掉 —— **從那一行以後的舞台程式
全部沒有執行**。也就是對唱模式上線（v1.4.0）那一刻起，舞台頁面就是壞的。

最值得記下來的是「為什麼三道檢查全都是綠的」：

| 檢查 | 為什麼沒抓到 |
|------|-------------|
| `node --check` | 一次只看一支檔案，每一支的語法各自都是對的 |
| `node --test` | `require()` 給每支模組獨立作用域，名字不會相撞 |
| 後端 pytest | 根本不碰前端 |

所以補了 `frontend/tests/script-scope.test.js`：照 HTML 實際載入的 `<script>`
清單，檢查同一頁的檔案之間沒有重複的最外層 `const`/`class`。它另外還釘住
一件事 —— `clamp`／`approach`／`dbFromRms`／`round3` 這幾支小工具在好幾個模組
裡各寫了一份。重複的 `function` 宣告**不會**丟錯，但後載入的那一份會默默
覆蓋前面的，所以瀏覽器裡大家其實都在用最後載入的那一份。目前每一份都
一字不差（確認過），這個測試不要求去重（為了幾行工具硬做一支共用模組反而
綁死載入順序），而是釘住「一樣」這個前提：哪天有人只改其中一份就會叫。
故意把衝突加回去跑過一次，確認測試真的會紅。

### 畫法：中線是自己的平均

長條圖沿用段落對決的**對拉**畫法，但中線的意義不同 ——
對決的中線是「兩個人之間」，趨勢的中線是「**這個人自己的平均**」，
往右是主場（青）、往左是弱點（桃紅）。畫絕對命中率的話看到的是
這首歌哪一段難唱，不是這個人哪一段弱，而後者才是要練的東西。

沒被點名的段落（幅度不夠或方向不一致）畫淡色而不是藏起來：
那一段是「還沒有結論」，不是「剛好等於平均」。

一句話上的小事但值得記：第一版寫成「一向低 **+13** 個百分點」——
方向已經由「低」講完了，正負號是第二次講，要讀兩次才懂。句子裡拿掉符號，
長條圖上留著（那裡沒有句子，符號就是方向）。另外 `Math.round` 往 +∞ 捨，
所以 −0.4 個百分點會顯示成「+0」：一個往下偏的段落顯示成正的，改成「±0」。

### 測試（後端 325 條 + 前端 192 條，全綠）

- 新增 `frontend/tests/trend-view.test.js`（11 條）與

## 2026-09-11 — 情境背景（v1.6.0「Never Black」）

**目標**：ROADMAP「後續想做的 → 演唱體驗」剩下的那一項「情境背景
（沒抓到 MV 時的動態視覺）」。商用點歌機（錢櫃的情境畫面、金嗓的背景影片、
JOYSOUND 的映像）都有這一套，而這個系統目前碰到沒有 MV 的歌就是**一片黑**。

黑畫面不只是「比較樸素」。在包廂裡它傳達的訊息是「**這首歌壞掉了**」——
使用者不知道是沒抓到 MV 還是機器當掉，而且整個房間只剩字幕在發光。

### 難處一：不是「有沒有 MV」，是「有沒有畫面」

原本以為這一項的判斷條件就一個：`metadata.video_path` 是不是 null。
實際去看快取才發現真正常見的情況是另一種 ——
YouTube 上大量的「音樂版／歌詞版」上傳其實是**一張靜態圖配四分鐘音訊**。
檔案真的下載到了，`video_path` 有值，所以「這首有沒有 MV」會回答「有」，
舞台就放一張凍結的畫面放整首。那正是情境背景要解決的情況，卻完全繞過判斷。

所以要真的去看畫面：每 1.2 秒把 `<video>` 縮成 32×18 畫進離螢幕 canvas，
算跟上一張的平均亮度差。門檻 2.0（0~255 的刻度）——
真正的靜止圖只有編碼雜訊（0~1），再慢的實拍畫面也遠超過這個值。
在真的瀏覽器裡用 MediaRecorder 現場錄了兩段影片驗證：

| 影片 | 取樣數 | 最大差值 | 判定 |
|------|--------|---------|------|
| 會動的 | 1 | 10.21 | moving（一筆就結案，MV 留著） |
| 整首同一張圖 | 6 | 0.00 | still（情境背景接手） |

門檻兩邊都留了五倍以上的餘裕，這個判定不需要調參。

三個實作上的陷阱，每一個都會讓功能悄悄出錯：

- **暫停中不能取樣**。暫停的畫面永遠跟上一張一模一樣，差值恆為 0 ——
  按個暫停回來就會發現 MV 被換成情境背景了，而且沒有任何錯誤訊息。
- **觀察窗要用牆上時鐘，不能用影片的 `currentTime`**。短片配長歌時
  `<video loop>` 會一直繞回 0，用它算「觀察了幾秒」會得到負數，判定永遠不成立。
  第一版就是這樣寫的，在瀏覽器裡跑才發現（單元測試餵的是遞增的時間戳，測不到）。
- **兩個方向都要閂鎖**。判定過就不再改：唱到一半背景在 MV 與情境之間來回切，
  比兩種都不完美更糟。

還沒判定完的那五秒先放 MV —— 還沒有證據說它是張圖之前，把真的 MV 換掉才是錯的。
判定時間（1.2 秒 × 4 筆 ≈ 5 秒）剛好落在片頭卡還亮著的時間內，切換看不太到。

### 難處二：三道「壓一點點」疊成一片全黑

背景不能跟字幕搶，這件事沒有爭議。實作時亮度被壓了三道：
主題自己的 `baseLuma`、設定頁的亮度上限、以及畫面下半字幕區的 vignette。
每一道單看都只是「壓一點點」。

第一版 render 出來是**全黑**。三道乘起來大約是 0.33 × 0.6 × 0.45，
整張圖只剩下極微弱的色偏 —— 而這件事在程式碼裡完全看不出來，
每個數字都很合理。是真的用 Playwright 把五個主題畫出來看了才發現。

修的方式不是把某個數字調大，是把責任分清楚：

- vignette 那一層的工作是「把任何一支亂七八糟的 MV 壓到字幕看得清楚」。
  情境背景的亮度是我們自己控制的（而且已經被限速器與上限壓過兩道），
  所以情境背景出場時 vignette 自動放輕（`.ambient-canvas.on ~ .stage-vignette`，
  純 CSS 兄弟選擇器，不用 JS 再去切 class）。字幕所在的下緣那一道不放。
- 亮度上限的預設從 0.6 改成 0.85，下限從 0.1 改成 0.3 ——
  滑到 0.1 等於背景被關掉，但模式還顯示「開著」，畫面說的跟看到的就對不上。

順帶：星空主題第一版是一片灰霧。畫布是半解析度、柔邊靠 CSS 的 `blur(6px)`，
漸層類的主題很吃這一套，星點卻被糊掉了。改成依 `data-motion` 分開設柔邊
（星空 2.5px），並在主題資料加 `density` 倍率（星空 ×1.9、燭火 ×0.75）。
這兩個值是看著圖調的，不是算出來的。

### 難處三：背景不准閃

背景跟著音樂動，最直覺的做法是「鼓點一來就把整個畫面打亮」。那是不能做的：
舞台螢幕在暗房間裡佔滿整面牆，高對比的亮度變化**一秒三次以上**就是
光敏性癲癇的誘發條件（一般安全建議是 3 Hz 以下）。

所以亮度與動態被拆成兩件事：

- 亮度走限速器，每秒最多變 `MAX_LUMA_SLEW = 0.45`，而且擺幅本來就小
  （每個主題 ≤ 0.25）。最壞情況（每一幀在全靜音與滿能量之間跳）也被測試釘住。
- 鼓點只推 `beatPulse`（粒子噴一下、波形推一下、線條粗一點），完全不碰亮度。

鼓點偵測本身還踩到一個：移動平均從 0 開始爬的那一秒，「比平均大聲」是必然成立的，
所以前奏一進來會連噴好幾下。修法是第一幀直接把平均值設成當下的值，再加 0.35 秒暖機。

### 成本：背景是最低優先

舞台那條 `requestAnimationFrame` 上還有逐字走字、音高偵測與評分。
那些掉幀所有人都會發現，背景掉幀沒有人會發現 —— 所以背景讓路：
30fps 上限、半解析度畫布（柔邊交給 GPU 合成的 CSS blur，比在 canvas 裡疊十層漸層便宜）、
`document.hidden` 就完全不畫、每幀量自己花多少毫秒，超過 8ms 就降級
（升回去要連續 90 幀都在 4ms 以下，遲滯免得在邊界跳）。

頻譜接的是 `normGain`（伴奏＋導唱），**不含麥克風與罐頭音效**：
背景跟著人講話與掌聲抖動，看起來不是「有反應」而是「壞了」。
另外 analyser 的位元組是 dB 對映，音樂幾乎永遠落在 0.35~0.85 之間，
直接拿 `bytes/255` 當能量會讓背景整首停在高檔，所以把那一段重新攤成 0~1。

### 同一首歌永遠是同一個背景

「自動」主題用 FNV 雜湊從 `song_id` 挑，不是隨機。
隨機看起來比較豐富，在包廂裡卻是反效果：同一首歌昨天是星空今天是霓虹，
第一個反應是「機器怎麼怪怪的」。背景是這首歌的一部分，它要是穩定的。

### 其他

- 佇列項目多了 `has_video`（後端從 metadata 讀）。沒有它的話舞台只能先載
  `original_video.mp4`、等 404 才知道沒有 MV，那一秒的黑畫面剛好落在第一句歌詞上。
  還沒處理過的歌是 `null`（不知道）而不是 `false` —— 當成沒有的話，
  每首有 MV 的歌都會先閃一下情境背景。

## 2026-09-10 — 對唱的段落對決（v1.5.0「Home Turf」）

**目標**：上一輪自己留下的第 3 項「對唱的段落比較（哪一段誰比較強）」。
資料早就在兩邊的 `sectionScorer` 裡（兩位各有一份完整的段落成績），
所以這一輪的工作不是計算，是**決定哪些段落可以拿來比、以及怎麼畫**。

### 這一項真正的難處：分工不是勝負

一開始想的做法是「兩邊的段落命中率直接並排，誰高誰贏」。
把資料倒出來一看就知道這樣會出事：真正的對唱歌曲（《屋頂》那一類）
本來就是**主歌 1 你唱、主歌 2 我唱、副歌一起唱**。
B 沒唱主歌 1，他在那一段的 `note_frames` 是 0、命中率是 0%，
畫面就會宣布「A 以 68% 完勝 B 的 0%」——

那不是唱得比較好，那是**那一段根本不是 B 唱的**。而且被冤枉的人
在包廂裡沒有辦法反駁（畫面就是這樣寫的），這種錯比不做還糟。

所以每一段先過三道守門，才決定要不要給名次：

| 守門 | 門檻 | 不設會怎樣 |
|------|------|-----------|
| 兩邊都唱夠 | 各自被算到的導唱音符 ≥ 30 幀（約 0.5 秒） | 就是上面那個「68% 完勝 0%」 |
| 參與量相當 | 少的那一邊 ≥ 多的那一邊的一半 | 跟一句（40 幀）只要那一句準就有 100%，唱滿整段（400 幀）的人被自己的難處拉低 —— 這種「比較」比不比還糟 |
| 差距夠大 | 命中率差 ≥ 5 個百分點才點主場 | 61% 對 59% 宣布主場，是在幫他們製造爭吵而不是回饋 |

過不了前兩道的段落照樣列出來（那是有用的資訊：這首歌怎麼分工的），
但標成「由 X 主唱」、整列淡化、不計進比數，而且沒唱的那一邊顯示 `—` 而不是 0%——
畫成 0% 看起來像「唱了但完全沒中」，跟「沒唱」是兩件完全不同的事。

前兩道守門能成立，是因為**判定為串音的幀根本不會進段落統計**
（上一輪 `tick(credit)` 的設計）：所以 `note_frames` 剛好就是
「這一位在這一段被算到多少」，不必另外埋一個計數器。

### 門檻與段落評分共用

30 幀與 5 個百分點這兩個值不是新選的，是 `section-scorer.js` 裡
單人段落評分用的同一組（`MIN_SECTION_NOTE_FRAMES` / `MIN_SECTION_SPREAD`）。
兩邊用不同的門檻，會出現「單人成績單說這段有評分、段落對決說沒有」
這種說不通的畫面。兩個檔案是各自獨立的 script（沒有模組系統），
所以照 `DUET_TIE_RATIO` 的前例在 `duet-scorer.js` 再宣告一次、
註解互相指名，並且**用一條測試把兩邊的值釘在一起** ——
註解會被忽略，測試不會。

### 畫法：往中間對拉，而不是兩張圖

兩個人各畫一張獨立的長條圖是最直覺的做法，也是最沒用的做法：
「A 的副歌 1 是 68%」跟「B 的副歌 1 是 41%」分在兩張圖上，眼睛得自己配對。
改成**對拉**（左邊 A 桃紅、右邊 B 青綠、段落標籤釘在正中間），
比較這件事就畫進版面本身了，掃一眼就知道哪幾段偏一邊。

- 兩位的顏色（桃紅／青綠）原本在音準軌跡、計分板、CSS 各寫一次，
  這輪收成 `--duet-a` / `--duet-b` 兩個變數。三處各寫一組色碼的話，
  哪天換了顏色而其中一處沒改，畫面就開始騙人。
- 結算畫面只有九秒，所以最多列六段（超過就只留真的有對決的段落，
  並註明「另有 N 段未列出」），`.duel-rows` 再加 `max-height` 兜底。
- 用 Playwright 真的把這一塊 render 出來看過（從 `player.js` 直接切出
  `renderDuetSectionDuel` 的原始碼餵給預覽頁，不重打一份，
  否則預覽跟真的畫面會慢慢對不上）。第一版的「小明 的主場」多了一個空格，
  是看了圖才發現的 —— 中文字串的空格在程式碼裡看不出來。

### 入庫：只存主場段落

長條圖是結算畫面的現場資訊，不入庫（跟單人段落評分同一個判斷）。
但**主場段落**（領先最多的那一段）進了評分歷史的 `duel_section` 欄位：
「這首歌的副歌一向是我的主場」是回頭看歷史時真正有用的一句話，
一排百分比不是。點歌台與手機端的對唱結算通知也會帶上它
（兩位都沒有對決段落時整段不提 —— 硬湊一句「主場：無」比不講還糟）。

### 測試（前端 10 條 + 後端 3 條）

- `frontend/tests/duet-scorer.test.js`：門檻與段落評分一致（釘死那條）、
  兩人都唱同一段的主場判定與平手、分段接唱標成主唱且不計進比數、
  參與量差太多退成主唱、兩邊都唱不夠的段落不列出、依歌曲順序排列與比數統計、
  段落編號對不齊時不會錯位、壞資料（null / 字串 / 缺欄位）不炸、
  `verdict()` 在只有一個人唱時形狀一樣。
- 後端：`duel_section` 跟著各自那一筆進歷史與 `singer_bests`、
  單人演唱一律空字串、標籤長度上限截斷。
- 後端 289 條、前端 149 條全綠；ruff 與部署檔驗證照樣過。

## 2026-09-09 — 對唱模式：兩支麥克風分別評分（v1.4.0「Two Mics」）

**目標**：ROADMAP「後續想做的 → 演唱體驗」的第一項「對唱模式（兩支麥克風分別評分）」。
商用點歌機（DAM 的デュエット採点、金嗓的男女對唱評分）都有這一套，
而包廂裡那句「這首我們對唱，看誰分數高」是這個系統目前完全接不上的需求。

### 這個功能真正的難處：串音（crosstalk）

寫兩個計分器很簡單。難的是**兩支麥克風在同一個房間裡**：
A 唱歌的時候，B 的麥克風也收得到 A 的聲音。

如果不處理，B 只要把麥克風舉著站在旁邊，分數就會跟 A 差不多。
而這件事最可怕的地方是 **它看起來完全正常** —— 兩邊的分數都在跳、
Combo 也在累計、音準線也在動。現場沒有任何人有辦法發現分數是假的
（除了「奇怪，我明明沒唱」這種沒人會講出口的疑惑）。

所以整個模組的唯一工作，是回答每一幀的那個問題：**這一幀該算誰的？**

| 規則 | 依據 | 為什麼需要 |
|------|------|-----------|
| 電平主導 | 兩支麥克風的原始電平差 ≥ 9 dB 就只算大聲的那一位 | 近距離收音的串音通常比本人小 12~20 dB |
| Schmitt 遲滯 | 進入獨佔差 9 dB、回到「兩邊都算」差 4.5 dB | 沒有遲滯的話門檻附近每幀都在換人，分數會亂跳 |
| 音高分歧例外 | 兩邊音高差 ≥ 1.5 半音就都給分 | 串音是同一個聲音的複製品，音高必然一樣；音高不同就是真的兩個人 |
| 訊號門檻 | 音高分歧只在被壓的那一邊高於底噪 12 dB 時生效 | 底噪的自相關結果基本上是隨機數，拿它比「音高不一樣」等於放串音進來 |

第三條是這次最值得記的一步。原本只有電平主導，那會系統性地冤枉
「唱得比較收的那一位」—— 他小 10 dB，就整首都沒有分數。
加上音高判斷之後，「小聲但唱的是另一個音」被正確地認成第二個人，
而「小聲且音高一樣」仍然被判成串音。這是兩件事第一次真的被分開。

### 判定要在計分之前，不能在計分之後

實作上有一個順序問題：判定需要兩支麥克風的電平，而電平是在音高偵測裡量的。
照原本的流程（`tick()` 裡面自己量、自己計分）就會變成
「先計分，再判定這一幀該不該計分」—— 已經加進去的分數要再減回去，
Combo 與段落統計也要回捲，那是找不完的 bug。

所以改成兩階段：

1. `measureRms()` 兩支各量一次（只量電平，不做自相關）。
2. `duet.decide()` 判定這一幀算誰的。
3. `tick(t, { credit, reuseRms: true })` 各自計分 ——
   `reuseRms` 讓它沿用剛才填好的波形緩衝，不重抓一次
   （自相關是整條 60fps 迴圈裡最貴的一步，多抓一次純粹是浪費，
   而且兩次抓到的樣本不一樣，除錯時會非常困惑）。

`credit: false` 的幀**照樣偵測音高**（判定本身需要它）但不計分、
不進段落統計、不畫軌跡。

### 兩種接法（因為它們對應兩種真實的硬體）

- **兩個輸入裝置**：兩支 USB 麥克風。最便宜。
- **同一裝置的左右聲道**：兩支麥克風接一台音效介面／混音器，
  L = A、R = B。這是包廂真正的接法，也只有這條路能用真正的動圈麥克風。
  A 麥的串流要重開成立體聲，再用 `ChannelSplitter` 分兩路。

立體聲那條路有一個必須擋下來的失敗模式：**介面只給單聲道**。
悄悄退回單聲道的話，B 麥拿到的是 A 的完美複製品，
兩個人的分數會一模一樣 —— 又是一個「看起來正常」的假分數。
所以拿到串流後檢查 `track.getSettings().channelCount`，
不到 2 就明確拒絕並要求改選兩個裝置。

### 只有一個人唱的時候不要亂比

對唱開著、但另一支麥克風放在桌上，是很常見的情況。
這時候亮出「A 勝 B（領先 40000 分）」不是比賽，是誤會。
所以 `verdict()` 先看兩位各自被算到的時間（各要 ≥ 10 秒）才進對戰判定，
否則退回那一位的單人成績單。同理，分數差在 3% 以內算平手 ——
逐幀評分本來就有雜訊，差 1% 就宣布勝負只會讓人覺得分數是隨機的。

### 現場排查得出來

串音判定調不好的症狀是「我明明在唱，分數卻不動」。所以：

- 舞台計分板上被判成串音的那一列會變淡並寫「串音靜音中」。
- 結算畫面會標出「有 XX% 的時間被判為串音」（超過 30% 才顯示）——
  那不是唱不好，是兩支麥克風靠太近或門檻設太高，分數本身已經不公平。
- 門檻放在系統設定頁（3~24 dB），照上面那個比例調。

### 後端

- 控制參數 `duet_enabled` / `duet_name_a` / `duet_name_b`（共享狀態，暱稱截 12 字）。
- 系統設定 `default_duet_enabled`、`duet_crosstalk_margin_db`。
- `POST /api/scores/duet`：兩位一起記、一起廣播一則通知。
  刻意不是呼叫兩次 `/api/scores` —— 分兩次寫，中間斷線就會在歷史裡留下
  「一場只有一個人的對唱」，那筆資料之後永遠說不清是誰的問題；
  而且會廣播兩次，包廂裡每支手機都跳兩則。
- 評分歷史多了「某人在某首歌的個人最佳」（`singer_bests`，與 `bests` 分開存）。
  有名字的人「刷新紀錄」指的是刷新自己的紀錄；拿全機器最高分去比，
  等於每次都跟包廂裡唱最好的那個人比。
- 平手門檻在前後端各定義一次但註解互相指名（`DUET_TIE_RATIO` ↔ `TIE_RATIO`）：
  畫面說平手、手機通知說 A 贏，是最糟的那種不一致。

### 測試（前端 25 條 + 後端 18 條）

## 2026-09-08（第 2 輪）— 和聲 / 雙聲部（v1.3.0「Second Voice」）

**目標**：ROADMAP「後續想做的 → 音訊」清單裡的第一項「和聲效果（雙聲部疊加）」。
商用點歌機（金嗓的 HARMONY、音圓的雙聲部、DAM 的ハモリ）都有這顆鍵，
而我們原本連移調的能力都沒有 —— 這是曲庫、評分、練唱都齊了之後，
**唱起來的爽度**上最大的一塊空白。

### 為什麼「升 4 個半音再疊回去」是錯的

這個功能最容易被做壞的地方，是把它當成「把麥克風升幾個半音」。
三度和聲的「三度」是**音階上的度數**，不是固定的半音數。以 C 大調為例：

| 旋律音 | 上三度 | 相差半音 |
|--------|--------|----------|
| Do | Mi | **+4** |
| Re | Fa | **+3** |
| Mi | Sol | **+3** |
| Fa | La | **+4** |
| Sol | Ti | **+4** |
| La | Do | **+3** |
| Ti | Re | **+3** |

固定 +4 有四分之三的音是錯的（Re 會唱出 Fa♯，那是 G 大調的音）。
在包廂裡，那不是「效果比較差」，那是**當著客人的面走音**。

所以和聲必須先知道「現在是什麼調、這個音是第幾度」。這也決定了模組怎麼切：
判斷（純資料）與移調（DSP）分成兩個檔案，前者才守得住。

### 調性怎麼估：權重看時間，不看次數

`estimateKey()` 拿導唱音符做音級直方圖，跟 Krumhansl-Kessler 的大小調感知輪廓
做 12 個旋轉 × 2 種調式的 Pearson 相關，取最高的。兩個實作上的決定：

- **權重用時間長度而不是出現次數**：主音與屬音通常是長音，經過音又快又多。
  照次數算會把裝飾音當成調性骨幹。
- **單一長音上限 2 秒**：尾奏那個拖了 12 秒的長音不該一個人決定整首的調。
  （這一條是寫測試的時候想到的 —— 造了一個「60 秒的 F♯ + 一小段 C 大調」
  的資料，沒有上限的版本直接被那個長音帶去別的調。）

然後是**兩道拒絕作答的門檻**：有效音符不足 8 秒、或相關係數低於 0.45，
就**不給調性**，需要音階的聲部一律退成低八度疊唱。
八度在任何調、任何音都不會錯 —— 寧可少一點花樣，
也不要有一半機率唱出調外音。念白曲、饒舌、還沒處理好歌詞的歌都走這條路。

### 移調自己寫：Web Audio 沒有這個節點

`playbackRate` 只能對 buffer 用（麥克風是即時串流）、`detune` 只有 oscillator 有。
所以移調是自己算的（`harmony-worklet.js`，跑在 AudioWorklet 的音訊執行緒上）：

```
output(t) = input(t - d(t))      瞬時頻率比 = 1 - d'(t)
```

延遲量以固定斜率變化就等於固定比例移調。問題是延遲不能無限縮短，
走到底要跳回去，而那是波形的斷點。解法是兩條讀取頭（延遲相差半個視窗），
快跳到底的先淡出、另一條淡入接手，兩條增益永遠加起來等於 1。

**踩到的坑：交叉淡接會產生梳型濾波。** 第一版用整個週期的 Hann 窗做交叉，
測「音量守恆」時發現 330Hz 的正弦掉了 **27%**（220Hz 與 440Hz 幾乎沒掉）。
原因是兩條讀取頭相差 depth/2，同一個聲音以兩個延遲相加就是一個梳型濾波器，
notch 落在哪個頻率取決於 depth —— 剛好 330Hz 附近。

修法不是換窗形，而是**把交叉區間縮短到一輪的 30%**：其餘七成的時間只有一條
讀取頭在出聲，訊號完全乾淨。同樣的 330Hz 掉不到 8%，主觀上從「聲音悶掉」
變成聽不出來。（拿掉交叉淡接不是選項 —— 那個跳點會變成每秒好幾次的爆音。）

這個坑值得記下來的理由是：**它只有數值測試抓得到**。
用耳朵聽「和聲的音量有沒有隨頻率起伏」，在有伴奏、有殘響的包廂裡根本不可能。

### 沒人唱就不出聲

和聲是把麥克風訊號移調再疊回去，所以沒人開口時疊出來的是**升高八度的呼吸聲、
椅子聲與空調聲**。這不是小瑕疵：升高八度會把那些低頻噪音搬到人耳最敏感的頻段，
比原本明顯得多。所以 `sang` 是硬性條件，另外需要音階資訊的聲部在
前奏／間奏（`hasNote` 為假）也安靜。

還有一道「不要抖」的門檻：同一個音符不重算移調量，換音符也要隔 80ms。
音符邊界上前後兩個音會交替被判為 active，沒有這道門檻的話移調量會在
+3／+4 之間每幀跳一次 —— 聽起來像和聲在發抖。

### 接在音訊圖的哪裡：和聲屬於人聲

```
… → micGain ─┬→ monitorGain → masterGain / reverb / echo
              └→ 和聲移調 ×2 → 和聲音量 ─┘
```

接在 `micGain` **之後**（麥克風音量滑桿一起帶動和聲，音量比例不會跑掉）、
`monitorGain` **之前**（跟主唱吃同一個「人聲外放」總開關與同一組殘響回音）。

副作用是**單人模式聽不到和聲**。這是刻意接受的：和聲從喇叭出去會被麥克風收回來
再移調一次，那條路徑會一路往上疊（每繞一圈升高一次），比單純的回授更難止。
單人模式的存在理由就是物理性切斷那條路徑，和聲不該打破它。
所以 UI 與說明書都直接把這件事寫出來，而不是讓使用者以為按鈕壞了。

### 舞台徽章要顯示調性

🎶 徽章寫的是「和聲 上三度（**C 大調**）」。調性寫在畫面上是刻意的：
和聲聽起來不對的時候，「機器把這首歌判成什麼調」是**唯一有用的線索**。
沒有它，客訴只會是「和聲很難聽」，而那句話裡沒有任何可以debug的資訊。
沒人唱的時候徽章補一句「· 等你開口」，否則「按了和聲卻沒聲音」會被當成故障。

### 測試

- `frontend/tests/harmony-planner.test.js`（27 條）：七個音級的上三度半音數
  逐一釘死、跨八度、非音階音吸附、小調、調性判定的兩道門檻、
  壞資料（缺欄位／負音高／時間反了）、出聲時機、音量上限、
  換歌重估調性、換風格不被保持時間擋住。
- `frontend/tests/harmony-shifter.test.js`（12 條）：**真的量頻率** ——
  輸入 220Hz、要求升八度，用零交越計數量出來必須是 440Hz（±2%）；
  和聲會用到的 +3/+4/+6/+7/−3/−4/−5 全部量過；直流輸入驗證兩條讀取頭
  增益恆為 1；五個頻率 × 四個移調量的音量守恆（守住那個 8% 的梳型上限）；
  分 128 樣本區塊處理與一次處理的結果一致（worklet 就是 128 一塊）。

## 2026-09-08 — 排程預處理（v1.2.0「Night Shift」）

**目標**：ROADMAP「後續想做的」清單裡的「預先排程處理」。挑它的理由是它針對的是
這個系統**架構上唯一的硬傷**：隨選處理很好，但第一次點一首新歌就是要等好幾分鐘，
而那幾分鐘剛好發生在「大家都想唱」的時刻。商用點歌機沒有這個問題，
因為它的曲庫是**事先備好**的 —— 那就把「事先備好」這件事做出來。

### 為什麼一次只跑一首

第一版寫的是「進到時段就把整批跑完」。想了一下這是錯的：
包廂的使用是隨機的，半夜兩點也可能有人推門進來。批次一旦開跑就佔著 GPU 不放，
現場點的第一首歌要排在批次後面等 —— 那正是這個功能想解決的等待，只是換了個時間發生。

改成 `run_once()` **處理一首就回來**，由外層迴圈重新問一次「現在可以跑嗎」。
代價是每首之間多幾秒的判斷延遲（一晚上跑 40 首也才多幾分鐘），
換到的是「最多再忙一首歌的時間，機器就會讓開」這個上限。這個交換划算得沒有懸念。

### 「為什麼還沒開始」要一直寫在畫面上

這種背景功能最常被問的問題不是「它做得對不對」，而是
**「都兩點了它到底在幹嘛」**。所以 `run_decision()` 回的不是布林值，
而是 `(能不能跑, 給人看的理由)`，理由常駐在分頁的狀態列上：
等時段（還有幾分鐘）／有人在唱歌／功能被關掉／根本沒歌要處理。

四種情況長得很像（都是「沒在動」），但處理方式完全不同 ——
第一種是等，第二種是正常，第三種要去開設定，第四種是使用者誤會了。
不寫出來的話，四種都會變成同一則客訴。

### 跨午夜的時段不是特例，是常態

`in_window()` 一開始寫成 `start <= hour < end`，然後才想到最想設的時段
就是 23:00–06:00 —— 那是**跨午夜**的。跨午夜不是邊角案例，是主要用途，
所以判斷式分成兩支（`start < end` 照常、否則 `hour >= start or hour < end`），
並且讓「起訖同一小時」= 全天候（使用者想關掉時段限制時最直覺的表達方式）。

### 三個「不要太聰明」的決定

- **展開播放清單在 API 層做，不在排程器裡做。** 排程器只認「已經展開好的歌曲清單」，
  所以它完全不碰網路，測試可以用純資料把整個生命週期跑完。
- **`watch?v=xxx&list=yyy` 不算播放清單。** 使用者從清單裡複製某首歌的網址時，
  想點的是那一首。只有 `playlist?list=` 才展開整張 —— 那是 YouTube「分享整個播放清單」給的網址。
- **取消不中斷正在處理的那一首。** 中途砍掉留下的是半成品資料夾，
  下次還要靠「快取管理」去清。讓它跑完幾分鐘，比留一個坑給未來的自己好。

### 只看 metadata 會漏掉要補跑的歌

「已經在曲庫裡就略過」原本用 `get_song_metadata()` 判斷，這是錯的：
metadata 是流水線**早期**就寫下的，處理到一半中斷的資料夾照樣有 metadata。
那種歌會被永遠標成「略過」，也就永遠不會被補跑 —— 而它正是最需要被補跑的那種。
改用新增的 `is_song_complete()`（四個必要檔案都在），跟「快取管理」分頁的完整性徽章同一套標準。

### 重開機要記得的不只是清單

任務清單持久化是理所當然的，比較容易漏的是 **`force_run`（使用者按過的「立即開始」）**：
半夜按下去然後機器重開，如果只還原清單不還原這個旗標，它就會安靜地退回等時段，
使用者隔天早上發現一首都沒跑。意圖也是狀態。
反過來，處理到一半的 `RUNNING` 項目要退回 `PENDING` 重跑 —— 那首歌八成只完成了一半。

### 前端：即時重畫不能吃掉正在輸入的字

分頁會收 `BATCH_UPDATE` 廣播即時重畫（每處理完一首歌一次）。
第一版直接重寫 `innerHTML`，結果是使用者貼了 30 行清單、還沒按送出，
背景跑完一首歌就把整框字清空了。現在重畫前先接住 textarea 的內容、選取範圍與焦點，
畫完再放回去 —— 用 Playwright 實測過「打字 → 收到廣播 → 字還在」。

顯示邏輯（上百首時挑哪 8 首上畫面、時段字串、狀態燈優先度）抽到
`frontend/js/batch-view.js` 用 `node --test` 守著。這類錯誤不會拋例外，
只會讓畫面看起來正常但其實在騙人 —— 比方說挑錯項目，正在跑的那首沒被顯示出來，
使用者就會以為機器沒在動。

### 驗證

- 後端 264 條（新增 27 條排程 + 6 條端點）、前端 75 條（新增 8 條）全綠，ruff 乾淨。
- 起了一台真的伺服器：塞入示範任務 → 按「立即開始」→ 觀察迴圈確實每 20 秒醒來、
  一次處理一首、失敗的標記錯誤後繼續下一首、待處理數確實下降。
  （這個環境連不到 YouTube，所以每首都失敗 —— 剛好把失敗路徑走了一遍。）

**下一步**：ROADMAP 剩下的選配項目（和聲效果、對唱模式、情境背景、多包廂）。

## 2026-09-07（第三輪）— 麥克風自動增益（v1.1.0）

**目標**：ROADMAP 的對照清單在 v1.0.0 已經全數打勾，這一輪開始做「後續想做的」
第一項 —— 麥克風自動增益。挑它先做的理由很實際：包廂裡最常聽到的抱怨不是音準
也不是效果，而是「換人唱又要重調麥克風音量」。上一位貼著麥克風吼、下一位離 20 公分
小聲哼，輸入電平差 20 dB 以上，這件事每首歌都會發生一次。

### 為什麼用前饋，不用回授

analyser 本來就接在 `micSource` 上（音高評分要的是原始訊號），
所以量到的電平天生就在增益節點之前 —— 直接拿來當前饋量測，一行都不用改。

反過來（量已經放大過的訊號）會變成「放大 → 量到更大 → 少放大 → 量到更小」的
呼吸迴路。更麻煩的是那個迴路的時間常數會跟房間殘響耦合在一起：
同一組參數在小包廂與大廳的行為完全不同，現場根本調不出來。前饋沒有這個問題，
代價是它不知道最終輸出多大聲 —— 所以削峰保護要自己用「輸入 + 目前增益」推估。

### 三條安全規則（順序就是優先度）

1. **沒人唱的時候絕不加增益**（噪音閘門 -45 dBFS）。這條最重要：安靜的房間也有底噪，
   照著「拉到目標音量」算下去會一路加到上限，然後第一個字進來直接爆掉，
   多人模式還會當場嘯叫。所以閘門以下只累計靜音時間，什麼都不動。
2. **要降立刻降（0.25s）、要升慢慢升（3s）**。降是保護、升是舒適；
   升太快會讓句與句之間的空隙把底噪一起抬起來，那個聲音很像機器在呼吸。
3. **範圍夾住**（+9 / -12 dB），而且**多人模式的加成上限收到 +6 dB**。
   人聲外放時每多加 1 dB 就離回授近 1 dB，這是物理，軟體只能選擇不要去踩。
   `configure()` 收到更小的上限時會**立刻**把現有增益夾回去（不等下一幀趨近）——
   收緊範圍是安全動作。

### 兩個寫錯了才發現的地方

- **容忍區不能寫成死區**。第一版是「差不到 1 dB 就不動」，結果增益永遠停在
  離目標 1 dB 的地方：趨近是指數的，一路靠近到剩 1 dB 就被死區凍住，
  等於系統性地永遠差一格（測試直接抓到 6 dB 只補到 5.0）。
  改成**遲滯**：差 1 dB 以上才「開始」調，一開始調就一路調到位（剩 0.15 dB 收手）。
- **削峰保護線是速度地板，不是「不准再降」的地板**。第一版把保護判斷寫在
  電平判斷的 `else` 前面，於是貼著麥克風吼的時候，增益被鎖在「剛好不削峰」的 -5 dB，
  而目標電平其實要求 -12 dB —— AGC 等於整首歌都沒作用。
  現在兩個目標都算出來取較小（降得多的）那個，只是用保護的時間常數去追。

### 換裝置歸零、換歌不歸零

- 換麥克風要 `reset()`：動圈換成電容，靈敏度差很遠，學到的增益是上一支的。
- 換歌只 `resetStats()`：一個人常唱兩三首，把增益丟回 0 dB 只會讓他每首歌的
  第一句都先小聲三秒。副作用是 `voicedSeconds`（同時是暖機計時器）歸零，
  所以換歌後會重新暖機 1.2 秒 —— 這剛好是想要的：換歌很可能換人，
  前奏那一兩句先維持現有增益、聽清楚新的人有多大聲再動。

### 電平表（意外地是最有用的部分）

舞台按 `S` 的音訊面板多一條收音電平表。原本只是 AGC 的除錯工具，
做完發現它解決的是另一個問題：**麥克風到底有沒有在收音**。
沒插好、選錯裝置、筆電實體靜音鍵沒開 —— 以前要開唱才發現，現在三秒就看出來。
三段顏色（灰／青／粉）對應的是「軟體幫不了、只有人能動」的兩種狀況：
太遠（加到上限也只是放大底噪）與太近（削峰救不回來）。

渲染迴圈在暫停時就 `return` 了，所以表會凍住 —— 面板開著且沒在唱的時候
另外跑一個 66ms 的試音迴圈，用新開的 `measureRms()`（只算 RMS，
不跑自相關音高偵測 —— 那是整條迴圈裡最貴的一步）。

### 刻意沒做的事

**沒有讓自動增益影響評分**。音高偵測的噪音門檻（RMS 0.015）還是照原始訊號判，
所以自動增益加得再多，分數還是照實際唱的算 —— 分數會因為音量被機器調過而改變，
是最難解釋的一種 bug。實務上這個門檻也很少擋到真的在唱歌的人：
它相當於 -36 dBFS，而 AGC 要出手的「小聲」通常在 -30 dBFS 上下，本來就過得了門檻。

### 測試

`frontend/tests/mic-agc.test.js` 24 條，全部是純資料邏輯（不碰 DOM、不碰 Web Audio）：
靜音餵一分鐘不加增益、暖機、遲滯收斂到位、不對稱曲線（0.4 秒內降得比升得多兩倍以上）、
削峰保護、長時間安靜放回中性、30fps 與 120fps 一致、分頁切回來的超大 dt、
壞資料（NaN / 負 RMS / 沒有 frame）不會讓增益變 NaN。
後端加一條設定範圍測試。合計後端 232 條、前端 67 條。

## 2026-09-07（第二輪）— Docker 一鍵部署 + 正式發布（v1.0.0）

**目標**：ROADMAP 只剩「系統」那兩項，做完就是可以發布的系統。
這一輪不新增演唱功能，全部在處理「別人怎麼把這台機器架起來、
以及三個月後怎麼知道他跑的是哪一版」。

### 版本號：唯一真相來源
- 新增 `backend/version.py`（`__version__` + codename + `KARATUBE_BUILD`）。
  FastAPI 的 `version=`、`/api/version`、設定頁頁尾、release 打包全讀這一個常數。
- 新增 `GET /api/version` 與 `GET /api/health`。
  健康檢查刻意不碰模型也不碰磁碟 —— 拿它當容器 HEALTHCHECK 才不會在
  處理歌曲吃滿 CPU 時被誤判成掛掉。
- 新增 `CHANGELOG.md`。`tests/test_version.py` 守住
  「CHANGELOG 最上面那一筆 == version.py」與版本順序遞減；
  release workflow 再比對 git 標籤。發出去的東西版本號對不上是最難追的問題，
  三道檢查都很便宜。

### 部署設定環境變數化
- `config.py`：`KARATUBE_HOST` / `KARATUBE_PORT` / `KARATUBE_PUBLIC_HOST` /
  `KARATUBE_PUBLIC_PORT` / `KARATUBE_CACHE_DIR`，值壞掉一律退回預設 ——
  機器可以印錯網址，但不能因為一個環境變數打錯就開不起來。
- **`public_base_url()`**：QR code 與「手機點歌」網址原本是
  「自動偵測本機 IP + 監聽 port」。容器裡偵測到的是 bridge 網段（172.17.x.x），
  手機掃了根本連不進去；反向代理後面對外的 port 也不是容器監聽的那個。
  現在設了 `PUBLIC_HOST/PORT` 就以它們為準，80/443 不寫進網址。
- `run.py`：容器裡不開瀏覽器（偵測 `/.dockerenv` 或 `KARATUBE_IN_CONTAINER`），
  否則開機日誌會被 xdg-open 的錯誤洗版、看起來像壞了。banner 印出版本號。

### Docker
- `Dockerfile`：依賴分兩層（改程式碼不用重裝 PyTorch，那層要幾分鐘）、
  內建 ffmpeg、非 root（uid 10001）、`/data` 為 volume、`/api/health` HEALTHCHECK。
  GPU 版只要換 `BASE_IMAGE` build arg 成 CUDA 映像。
- **踩到的坑**：`~/.cache` 必須先在映像裡建好並 chown。
  Docker 掛 named volume 時會沿用映像裡那個目錄的擁有者，
  沒先建的話 volume 是 root 的，非 root 行程下載不了 Whisper / Demucs 權重，

## 2026-09-07 — 導唱音量自動 ducking（唱穩了導唱自己退場）

**目標**：ROADMAP「音訊」剩下的最後一項。商用機（DAM 的 *ガイドボーカル自動フェード*、
金嗓的「導唱漸弱」）早就不把導唱人聲當成開／關兩檔的開關 ——
它跟著唱的人走：唱穩了退到背景，走音或忘詞時回來扶一把。
KaraTube 原本只有一支「導唱人聲 0~100%」的滑桿，等於要使用者自己在
「怕忘詞」與「怕唱不出自己的味道」之間二選一。

### 新模組：`frontend/js/guide-ducker.js`

不做任何新的音訊分析：**逐幀判定沿用評分心跳已經算好的結果**
（這一幀有沒有導唱音符、有沒有唱出聲、準不準），
`PitchEngine.tick()` 從「不回傳」改成回傳這份判定，段落評分與 ducking 共用同一份 ——
音高偵測是整條 60fps 迴圈裡最貴的一步，而且兩邊各自偵測一次的話，
算出不同結果時會非常難查。

這個功能錯了會非常明顯地毀掉體驗，所以三個參數都是照失敗模式訂的：

- **不對稱曲線**：淡出時間常數 1.6 秒、淡回 0.22 秒。
  退得太快 → 副歌唱準兩個字導唱就消失，第三個字忘詞當場裸奔；
  回得太慢 → 已經走音兩秒才聽到導唱，那時人早就放棄這一句。
- **Schmitt 遲滯門檻 0.55 / 0.35**：命中率在門檻附近抖動時維持現狀。
  沒有遲滯的話導唱會一直忽大忽小，那比全開還吵。
  門檻是照逐幀判定的實際手感抓的（逐幀命中比直覺嚴格，唱得不錯的人落在 0.5~0.7，
  照直覺設 0.8 會永遠不退）。
- **暖機 3 秒**：沒有這道門檻，前奏後第一個音唱準就會觸發 —— 那是運氣不是穩定。
- **間奏不改變狀態**：`hasNote=false` 的幀不更新信心度也不重新判定。
  那段本來就沒有導唱人聲可退，硬要衰減只會讓副歌一進來導唱先大聲一下再退，變成幫倒忙。
- **深度上限 0.95**：永遠留一點導唱在背景當安全網，不給「完全消音」這個選項。
- 命中率用時間常數而不是幀數的 EMA，所以 30fps 的機器不會變成兩倍慢
  （測試直接比對 30fps 與 120fps 的收斂位置）。

### 音訊圖：導唱倍率與導唱音量分成兩個節點
`sourceVoc → guideDuckGain → gainVoc → normGain → masterGain`。
刻意不把倍率乘進 `gainVoc`：使用者拉的導唱音量與機器的自動退場是兩件事，
混在同一個 gain 上，自動退場後再去動滑桿，滑桿刻度就會跟實際音量對不起來。

### 舞台與結算
- 舞台右下角新增 🎚️ **導唱自動淡出 XX%** 徽章（練唱徽章正上方，同一欄不會疊）。
  沒有這個提示的話，導唱變小聲只會被當成「機器把導唱吃掉了」。
  文字每 250ms 才更新一次 —— 60fps 直接寫 `textContent` 會每幀重排版面。
- 結算畫面新增 **🎚️ 導唱獨立度 XX%**（導唱自動淡出的時間比例）。
  這個數字比總分更能看出進步：分數會被歌難不難影響，
  「上週副歌整段靠導唱，這週導唱退場了七成」才是直接的回饋。
  導唱沒開、或有效演唱不到 20 秒就整行不顯示 —— 兩句歌的比例只是雜訊。

### 設定
- `settings.py` 新增 `guide_duck_enabled`（預設開）與 `guide_duck_depth`（預設 0.6，上限 0.95）。
- 點歌台系統設定頁多一組「🎚️ 導唱自動淡出」（表單照後端欄位規格自動長出來）。
- 改設定不重置狀態：唱到一半調深度不該讓導唱跳回全開；
  但開關切換兩個方向都重來（關掉要立刻放掉導唱，打開要重新暖機）。
- 導唱音量本來就是 0（純伴奏）時整段邏輯不跑，徽章也不亮。

### 測試（後端 219 條 + 前端 43 條，全綠）
- 新增 `frontend/tests/guide-ducker.test.js`（17 條）：暖機門檻、退場深度與漸進、
  救援速度（走音六秒內回到接近全開）、遲滯區間不翻轉、間奏不改變狀態與不計入統計、
  關閉時完全不作用、深度夾限、唱到一半改設定、`reset()`、獨立度統計的守門、
  更新頻率無關性（30fps vs 120fps）、分頁切回來的巨大 dt、非法輸入不產生 NaN。
- `tests/test_settings.py` +1：導唱淡出預設值與深度夾限（上限刻意不到 1.0）。

### 文件
- README（核心特色 19、目錄結構、測試條數）、USER_GUIDE（系統設定新章節、
  導唱獨立度、常見問題「導唱自己變小聲是壞了嗎」）、ROADMAP 打勾、STATUS.yaml。

## 2026-09-06 — 段落評分（哪一段唱得最好／最差）＋ 前端單元測試基礎建設

**目標**：ROADMAP「演唱體驗」剩下的最後一項。總分是娛樂，段落評分才是能拿來練歌的資訊 ——
「62 分」只讓人沮喪，「副歌 2 只有 31%、主歌都在 70% 以上」直接指出下一輪要練哪裡。
順手把「前端單元測試」那一格也補掉：這次新增的邏輯剛好是可以脫離瀏覽器測的純資料邏輯。

### 新模組：`frontend/js/section-scorer.js`

沒有新增任何分析：**分段沿用練唱模式已經在算的曲式**
（`chorus_detector` 由歌詞重複結構切出的前奏/主歌/副歌/間奏/尾奏），
**判定沿用評分心跳每幀已經算好的結果**（有沒有導唱音符、有沒有唱出聲、準不準）。
段落評分做的事只有一件：把同一幀的結果依時間歸到所屬段落再累計一份。

- `normalizeSections()`：濾掉前奏／間奏／尾奏（沒有導唱音符，列出來只會是一排 0%）、
  丟掉時間軸壞掉的資料、依起點排序，並丟掉與前一段**重疊**的段落 ——
  重疊會讓「一個時間點只對到一段」的前提失效，寧可少評一段也不要對錯段。
  用「排除清單」而不是「白名單」，後端日後多切出 bridge 之類的段落會自動納入。
- `sectionIndexAt()` 用**二分搜尋**，不用「記住上一段往前掃」的游標：
  A-B 循環與進度條跳轉會讓時間任意前後跳，線性游標在那些情境下會退化成每幀重掃整首。
- `summary()`：每段命中率 = 該段命中幀 ÷ 該段有導唱音符的幀。
  這個定義讓 A-B 循環唱三輪也算得對（整段累計的比例，不是最後一輪覆蓋前面）。
- `gradeForAccuracy()`：等級門檻從 `pitch-engine.js` 抽出來共用，
  單段評語與整首總評的手感才一致（原本門檻寫死在 `getFinalResult()` 裡）。

### 兩道「不亂下結論」的守門（這個功能真正的難點）

功能本身只是加總，難的是**什麼時候該閉嘴**：

1. **太短的段落不參加評分**：導唱音符不足 30 幀（60fps 下約 0.5 秒）的段落標成未評分。
   一兩幀的運氣不該決定誰是「最差的段落」。
2. **表現太平均就不點名**：最佳與最差差距 < 5 個百分點時 `best` / `worst` 都回 `null`，
   前端只畫長條圖不下結論。整首均勻地唱到 55% 時說「副歌 2 是你最差的段落（54%）」
   是在製造焦慮，不是回饋。
   —— 這條的邊界踩到浮點雷：`0.6 - 0.55` 在 IEEE 754 裡是 `0.049999…`，
   直接比門檻會讓「剛好差 5 個百分點」隨機失效（測試先抓到，才改成先四捨五入再比）。

同分時最佳取先唱到的那一段，讓結果不隨排序演算法的實作而變。

### 舞台結算畫面

- 成績單中間新增 **📊 段落表現**：每段一條命中率長條（最佳標黃、待加強標粉），
  上方點名 💯 最佳段落 / 📈 待加強；點不出來時寫「整首表現平均，沒有明顯拖分的段落」。
- 可評分段落不到兩段（沒歌詞、只唱一段就切歌）整塊收起來 ——
  段落評分是加分項，總分與等級不受影響。
- 長條從 0 長出來的動畫和分數滾動一起跑，維持商用機結算畫面的儀式感；
  段落多的歌超過高度就在卡片內捲，不會把卡片撐出畫面。
- 段落預覽（首句歌詞）進 `title` 提示，且所有插進 `innerHTML` 的文字都跑過 `escapeHtml()`。

### 貫穿的接線

- `player.js` 載歌時多抓一次 `/api/songs/{id}/sections`，
  用 `.catch()` 兜住 —— 段落是附加資訊，抓不到不能擋播放（歌詞還沒好的歌就是沒有曲式）。
  順序上 `setPitchData()`（會歸零評分）必須在 `setSections()` 之前。
- `pitch-engine.js` 的 `evaluateSingingScore()` 改成回傳 `{hit, perfect}`，
  段落評分沿用同一個判定，不重算也不會兩邊算出不同答案。
- 結論（「副歌 1」/「主歌 2」兩個標籤）跟著成績寫進 `cache/score_history.json`：
  長條圖是現場資訊，但「這首歌我老是哪一段唱壞」是回頭看歷史才有用的東西。
  空值一律存成空字串而不是 `None`，前端才能一律用 `if (r.best_section)` 判斷。
- 點歌台／手機的結算通知加上「💯 副歌 1 / 📈 主歌 2」。

### 工程品質：前端單元測試上線

- 新增 `frontend/tests/section-scorer.test.js`（26 條，`node:test` + `node:assert`）：
  等級門檻的每個邊界、段落清單正規化（壞資料、重疊、排序、未知種類）、
  時間→段落（邊界、空隙、負時間、NaN）、逐幀累計、reset/換歌歸零、

## 2026-09-06 — 曲庫分類瀏覽（語言 / 歌手）＋ 新歌榜 ＋ 推薦歌單

**目標**：補上 ROADMAP「點歌體驗」剩下的兩項。搜尋很好用，但商用點歌機的主畫面
從來不是只有搜尋框 —— 使用者常常是「想唱台語歌，但一時想不起歌名」，
這時要能用**語言別**和**歌手**把曲庫縮小到看得完的範圍。

### 新服務：`backend/services/library.py`

曲庫是使用者點過的歌自然長出來的，而 YouTube 只給我們標題與頻道名，
沒有語言標籤、也沒有真正的歌手欄位。所以分類得自己判：

**語言判定**（`detect_language`，純函數）依序：

1. **明示標記**最準 —— 歌名／頻道名出現「台語」「粵語」「日文歌」直接採用。
2. **諺文**：≥ 3 字，或諺文 × 2 ≥ 漢字 → 韓語。
3. **假名**：≥ 3 字，或假名 × 2 ≥ 漢字 → 日語。
   用比例而不是「有假名就算」，是因為華語歌名很愛夾一個「の」
   （「我の愛」不該被丟進日語分頁）。
4. **方言用字**：漢字 ≥ 2 時數粵語／台語專用字**出現了幾種**，
   要 ≥ 2 種才定案 —— 單一個「厝」或「係」在國語歌詞裡也會出現，
   一個字就判定的話誤判率高到分類沒有意義。用字表只收辨識度高的
   （所以不收「係」「仲」這種國語文本也常見的）。
5. 其餘漢字 → 國語；拉丁字母 ≥ 3 → 英語；都不符合 → 其他。

判語言只讀歌詞前 600 字：整首讀進來對結果沒有幫助，只是白花 I/O。

**歌手正規化**（`normalize_artist`）：先去掉 YouTube 的機器後綴
（`- Topic`、`VEVO`、`官方頻道` / `Official`）；剩下的名字若含唱片公司／
音樂頻道字樣（Records、娛樂、音樂、頻道…），改從「歌手 - 歌名」「歌手｜歌名」
的標題前半段取；都失敗歸「未知歌手」——
讓判不出來的歌聚成一堆，比每首各自成為一位「歌手」好用得多。

**快取策略**：判定結果寫回該首歌的 `metadata.json`（`language` / `artist_name`），
每首只算一次，之後瀏覽都是純讀檔。不另外存索引檔 ——
刪快取時分類跟著消失，不會留下對不上的孤兒資料。

### 新 API

## 2026-09-05 — 練唱模式：A-B 段落循環 + 自動副歌偵測 + 段落跳轉

**目標**：補上商用 KTV 點歌機的「副歌重播」。這是 ROADMAP「演唱體驗」剩下的最後一項，
也是一般人真正拿伴唱機來練歌時最常用的功能 —— 沒有它，練副歌只能整首重唱。

### 新功能：🔁 練唱模式（A-B 區段循環）

- **共享狀態**：`QueueManager` 新增 `loop_enabled` / `loop_start` / `loop_end` 三個欄位，
  跟其他調音參數走同一條 `/api/control`，所以點歌台、手機、舞台看到的圈選範圍永遠一致。
- **收斂規則**（`_normalize_loop`）：
  - A、B 按反了自動對調 —— 聽到一半才想圈這段，先按 B 再按 A 是很自然的操作，不該報錯。
  - 區間缺一角、或短於 1 秒時一律關掉循環：零長度的區間會讓舞台在同一秒鐘上瘋狂 seek。
  - 換歌時清空（`clear_loop()` 掛在 `play_next`）：A-B 點屬於某一首歌，
    留著會讓下一首在莫名其妙的地方跳回去。
- **跳轉指令**：新增 `POST /api/seek` → `CONTROL_COMMAND: SEEK`。
  伺服器不持有播放位置（媒體在舞台端），所以只送指令、不改自己的狀態。

### 新功能：🎯 自動副歌偵測（`backend/pipeline/chorus_detector.py`）

**問題**：「副歌在哪裡」沒有人會替每首歌手動標記，但沒有這個資訊，
「一鍵副歌重唱」就只能退化成使用者自己聽著抓時間。

**作法**：純文字重複結構分析，不碰音訊。歌詞時間軸在流水線裡已經對齊好了，
而副歌的定義本來就是「整段歌詞重複出現的區塊」，所以拿逐行文字找
「最長、重複最多次的連續區塊」就夠了 —— 比做音訊自相似矩陣便宜好幾個數量級，
而且找到的行可以直接對回它自己的時間。

1. 每行正規化（去標點、空白、轉小寫）：不同來源的 LRC 標點寫法不一，
   不正規化會把同一句判成兩句。
2. 對每組起頭相同的行往下延伸取最長共同區塊，並把它的每個前綴也收進候選 ——
   四行副歌可能只有後兩行在尾聲又多唱一次，那個兩行版本的重複次數比較高，值得參加評分。
3. 評分：先看涵蓋的總行數（重複次數 × 每次行數），同分時偏好「一次比較長」的區塊。
4. 時間守門：低於 5 秒（跳針）或超過 100 秒（抓到整段主歌+副歌）的候選淘汰，換下一名。
5. 全部落空時退一步找「重複三次以上的單行鉤子」（口水歌），
   單行本來就只有兩三秒，時間門檻要跟著放寬到 2.5 秒，否則這條退路等於沒有。
6. 再找不到就回 `None`，前端退回手動 A-B，不會壞。

段落切分（`detect_sections`）則靠唱句之間的靜默：空超過 6 秒算換段，
切出 前奏 / 主歌 N / 副歌 N / 間奏 N / 尾奏，副歌段用偵測結果標記。
新端點 `GET /api/songs/{song_id}/sections` 即算即回，不寫檔、不需要快取。

### 前端

**點歌台（`controller.js` / `index.html`）**
- 調音台新增「🔁 練唱模式」區塊：`A` / `B` 設點鍵（顯示目前時間）、開始/停止循環、清除、
  **副歌重唱** 一鍵鍵，以及自動切好的段落膠囊列（點標籤跳轉、點 🔁 循環該段）。
- 兩點都設好就自動開始循環 —— 商用點歌機按完 B 就跳回 A，不會要你再按第三顆鍵。
- 進度條改成可點擊跳轉，並在上面用黃色區塊畫出目前的 A-B 區間。
- 曲式分析結果依 `song_id` 快取，同一首只跟伺服器要一次。

**舞台（`player.js` / `player.html`）**
- `renderLoop` 每幀檢查是否唱過 B 點，過了就 `seekMedia(A)`。
  200ms 冷卻是必要的：mp3 的 seek 只能落在解碼區塊邊界，跳回去之後補間時鐘
  要一兩幀才重新錨定，沒有冷卻會在 B 點瘋狂連續跳。
- `seekMedia()` 三條軌（伴奏、人聲、MV）一起搬並重新錨定時鐘；
  卡在最後 0.15 秒之外，避免使用者想跳到尾奏卻直接被 `ended` 結算掉。
- 右下角常駐 🔁 練唱徽章並標出區間 —— 沒有這個標示，台上的人只會覺得機器在跳針。
- `PitchEngine.clearTrail()`：跳轉後清掉使用者音高軌跡（舊點的時間都在新位置的未來，
  留著會在導唱線上畫出鬼影），但**分數與統計保留** —— 那些幀是真的唱過的。

### 測試（185 條，全綠；本輪 +30）

## 2026-09-04 — 自動音量平衡（EBU R128）+ 系統設定頁 + pipeline 純函數測試

**目標**：把「發布給別人用的機台」還缺的兩件事補上 ——
使用者不改程式碼就能調整機台行為（設定頁），
以及不用每首歌手動轉音量（自動音量平衡）。順帶補齊 pipeline 的單元測試防線。

### 新功能：🔊 自動音量平衡（EBU R128 / ITU-R BS.1770-4）

**問題**：YouTube 來源的響度差距極大 —— 官方 MV 母帶常壓到 -8 LUFS，
個人上傳的現場版可能只有 -22 LUFS。中間差 14 dB，主觀上大約是「三倍大聲」，
所以每換一首歌就要重新轉音量，這是包廂裡最煩人的體驗之一。

- 新增 `backend/pipeline/loudness.py`：自己實作 BS.1770-4 的
  **K 加權（高頻棚 + RLB 高通）→ 400ms/75% 重疊區塊 → 絕對閘 -70 LUFS
  → 相對閘 -10 LU → 整合響度**。
  - 濾波器係數依類比原型在任意取樣率重新推導，在 48kHz 會退化成規格書列出的參考係數
    （測試直接比對到小數第 9 位）。
  - 不直接抓 pyloudnorm：只需要一個數字卻要多帶一層相依，而且純函數
    （吃 numpy 陣列、吐一個數字）才好用合成訊號在 CI 上測。
  - 濾波優先用 scipy，沒有 scipy 時走純 numpy 備援 —— CI 只裝 numpy 也跑得動。
- 流水線最後（分離、對字幕、抽音高之後）量一次 **伴奏軌** 的響度，
  把 `lufs` / `peak_dbfs` / `gain_db` 存進 metadata。量測失敗只是沒有這筆資料，
  不會讓整首歌處理失敗。
- 新 API `GET /api/songs/{id}/loudness`：回傳**依當下設定重算**的增益 ——
  目標響度改了不用重跑流水線。metadata 沒有響度資料的舊歌會現場量一次並補寫回去，
  所以既有曲庫不必整批重處理。
- 播放端 `audio-effects.js` 新增正規化增益節點 `normGain`：
  `gainInst / gainVoc → normGain → masterGain`。
  **麥克風與氣氛音效直接接 masterGain，不經過這個節點** ——
  換歌調整音量平衡時，唱歌的人不會覺得自己的聲音忽大忽小。
- 三重保險，寧可少調也不要調壞：量不到 → 0 dB；增益夾在 ±12 dB；
  峰值保護（拉完不超過 -1 dBFS）。

### 新功能：⚙️ 系統設定頁

- 新增 `backend/services/settings.py`：以 `SETTINGS_SPEC`（型別／範圍／選項）為單一事實來源，
  存成 `cache/settings.json`。
  - **越界夾回合法值、未知欄位忽略**，不丟例外 —— 設定頁是給人用的，
    手機上滑錯一格不該讓伺服器回 500，舊版前端送新欄位也不該壞。
  - 設定檔壞掉退回預設值，不阻擋開機（機台不能因為一個 JSON 壞掉就唱不了歌）。
- 新 API：`GET/POST/DELETE /api/settings`、`POST /api/settings/apply-defaults`。
  改動透過 WebSocket 廣播 `SETTINGS_UPDATE`，所有裝置即時同步；
  舞台端一連上就會收到（片頭卡秒數、結算開關都在裡面）。
- 可設定的五類：
  1. **開機預設調音** —— 開機時自動套進共享狀態；也可一鍵「套用到現在」不必重開。
  2. **自動音量平衡** —— 開關與目標響度。
  3. **快取上限與自動清理** —— 每處理完一首檢查一次，超過就從最舊的刪，
     `storage.enforce_cache_limit()` 會跳過演唱中與佇列裡的歌。
  4. **AI 模型** —— Whisper / Demucs 模型改成可選；模型在啟動時載入，
     UI 明示「要重開伺服器才生效」並顯示目前實際運行中的模型。
  5. **舞台演出** —— 片頭卡與結算畫面的開關與秒數（原本是寫死的常數）。
- 前端表單是照後端回傳的 `spec` 長出來的：後端加一個欄位，
  controller 只要補一行標題文字就會自動多一列，不用同時改三個地方。
  滑桿 350ms 防抖才送 API；自己剛動過的 2 秒內不吃廣播重畫（否則手上拖的滑桿會被換掉）。
