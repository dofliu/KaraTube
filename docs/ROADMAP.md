**v1.26.0 起，連「後續想做的」那一張清單也清空了** —— 多包廂是上面唯一
剩下的一項。到這裡為止，商用點歌機上找得到的功能與「放得進店裡」需要的
結構（本機曲庫、櫃檯管理鎖、多包廂）都補齊了。

之後每一輪補的不再是「清單上少了哪一項」，而是**回頭看包廂裡實際會發生什麼**：
推不亮的聲音（1.31 的三段等化器）、沒有人說話的那二十秒（1.32 的間奏倒數）、
唱不準的那幾個字（1.33 的智能修音）。這一類的共同點是它們在功能表上看不見
—— 看得見的時候，它已經被講成「這台機器壞了」。

## 💡 後續想做的（非必要，想到就補）

### 舞台演出
- [x] 間奏倒數與跳過長前奏 *(2026-10-02)* —— 商用點歌機在**沒有歌詞的那一段**
      都會說話（「間奏 ♪ 18」），而這台機器在這一版之前那一段是**一片沉默**。
      功能的形狀很清楚（空檔表加一個數字），難的全部在**交棒**、**兩條時間軸**
      與**跳到哪裡**。
      為什麼值得做：沉默在包廂裡有三種讀法 —— 還在前奏（再等二十秒）、
      字幕壞了（該按重算）、機器卡住了（該切歌）—— 三種在螢幕上長得一模一樣，
      而猜錯的那一次，被切掉的是一首沒有壞的歌。
      **交棒**是最容易被忽略、但在包廂裡最明顯的一個決定：畫面上永遠只能有
      一套倒數在跑。數到 0 才交給每一句自己的預備光點的話，使用者會先看到
      「3、2、1」的數字，接著又看到三顆點再數一次 —— 兩套本來就不是同一個基準
      （數字是整數、光點是連續的），對不起來的時候他會開始懷疑哪一套才是真的，
      然後兩套都不信。所以倒數剩三秒就收掉，而那個數字與 renderer 的光點視窗
      有測試釘在一起。同理，**十秒以下的空檔不算間奏**（那是樂句之間的換氣，
      而會閃的東西會一直把看歌詞的餘光拉走），**短到只能閃一下的倒數整段不顯示**，
      而且那個判斷只看空檔的兩端、不看現在幾秒 —— 不然會「數到一半自己決定消失」。
      **兩條時間軸**是唯一會無聲出錯的地方：空檔表活在歌詞時間軸上，
      `audio.currentTime` 活在音訊時間軸上，中間差著這首歌的 LRC 偏移與兩點校正
      解出來的速度 —— 而那個差**正是使用者調過的那個數字**，也就是說越是被調整過
      的歌（最需要幫忙的那幾首）直接拿去 seek 錯得越多，症狀是「跳完之後第一句
      已經唱到一半」。所以補了一個反函數 `audioTimeFor()`，並且讓點歌台那顆按鈕
      **不自己算落點**（`POST /api/skip-interlude` 不帶秒數）。
      **跳到哪裡**：跳到還剩三秒，不是跳到第一個字 —— 跳到第一個字等於把人推上台，
      沒有吸氣的時間，第一句必漏而且評分照實算。其餘三個都是同一個形狀：
      **只在倒數跑著的時候有作用**（做成「往前跳 N 秒」會跳掉一整句歌詞，
      而按它的人並不會先確認現在是不是間奏）、**省不到三秒就不給按**
      （按了只前進半秒的鍵會被當成壞掉，然後他會再按五次）、
      **尾奏不倒數也不給跳**（數到 0 之後沒有東西要唱；要結束這首歌那顆鍵叫切歌）。
      最後一件：倒數帶與跳過鈕都浮在版面之上，**不推動任何東西** ——
      排進版面的話歌詞會在開唱前最後三秒跳一下，而點歌台那一側的鄰居是「切歌」。
      詳見 CHANGELOG 1.32.0。

### 麥克風與現場
- [x] 智能修音 *(2026-10-03)* —— 新一代點歌機與手機 K 歌 App 都有的那顆鍵
      （金嗓的「美聲」、全民K歌與唱吧的「智能修音」）。這台機器在這一版之前，
      麥克風到喇叭之間**完全沒有碰過音高** —— 對「唱不準」只有唱完那個分數的
      事後講評，沒有當下幫忙，而包廂裡「差一點點」才是常態。
      功能本身不難（偵測音高、算誤差、移調器移過去），內容全部在**什麼時候
      不要動**：
      最重要的一個決定是**目標音是這首歌的導唱音符，不是最近的半音**。
      吸附到最近的半音（市面上最常見的那種修音）十行就寫得完，而且不需要
      知道任何關於這首歌的事 —— 但一個人唱低 70 cent 的時候，離他最近的半音
      **就是他唱的那個錯音**，修完之後走音的地方反而更明顯、更有自信。
      推論出來的那一條同樣重要：**沒有導唱音符的時刻一律不修**（前奏、間奏、
      念白、笑聲、講話）—— 機器不知道「該唱什麼」的時候最好不要動。
      第二件是**差超過一個半音半就放手**：那通常不是唱不準，是根本不是在唱
      這一句（唱錯行、整段低八度、麥克風收到的是伴奏），硬修會變外星人；
      而放手是滑回去的，不是瞬間歸零（瞬間歸零等於在字的尾巴上製造一個
      跟修正量一樣大的反向跳音）。
      第三件是**「修多快」就是「抖音活不活得下來」**：三段強度調的是修正量
      滑過去的時間常數（輕 150ms／中 90ms／強 45ms）—— 瞬間到位會把抖音
      與轉音抹平，那是一種效果，不是伴唱機該預設的事。
      第四件是**分數永遠看不到修過的訊號，而且是接線上的保證**：音準偵測
      直接接在 micSource 上，修音在整條前級鏈的最後面。接反了的症狀是
      所有人都一百分，而那一天之後這台機器的分數就再也沒有意義了。
      另外兩個：跟和聲共用同一顆移調器（修音的移調量是它最輕鬆的工況，
      另寫一顆相位聲碼器換來的差異在包廂的喇叭上量不出來，卻多一份遲早會
      分家的 DSP），以及關著的時候乾路上只有一顆增益 1.0 的節點
      （不為沒開的功能背著 22ms 的監聽延遲）。詳見 CHANGELOG 1.33.0。
- [x] 三段音色等化器 *(2026-10-01)* —— 商用 KTV 擴大機面板上一定有的那三顆旋鈕
      （高音／中音／低音），而這台機器在這一版之前只有一顆**單向**的「高頻柔化」：
      它只能把聲音變悶，不能把聲音變亮。所以包廂裡最常見的兩句抱怨
      （「我的聲音好悶」「這首歌的低音太轟」）**沒有任何一顆旋鈕回答得了**，
      唯一能動的是音量 —— 而動音量會把另一個人也一起改掉。
      功能的形狀很清楚（三顆 BiquadFilter），難的全部在**放在鏈上的哪裡**、
      **推完之後音量怎麼辦**，以及**它跟防嘯叫的關係**。
      位置：等化器在**限幅器之前**。放在它之後的話，+12 dB 的提升會直接越過
      這條鏈上唯一一道削峰保護，而那一聲破音是在喇叭上發生的 ——
      限幅器看起來還是好好的，沒有人查得到。音樂那一套同理放在自動音量平衡
      之後、升降 Key 的分岔**之前**（分岔之後要接兩條，而那兩條遲早會分家，
      症狀是「升 Key 之後低音不見了」）。
      補償：三段都拉 +10 的人不是想要大 10 dB，他只是想要「亮一點」。
      所以後面跟一顆補償增益，但它**只看滑桿、不看訊號** —— 看訊號的話就是
      第二個自動增益，兩個會互相追著跑，症狀是音量以一兩秒為週期上下呼吸，
      而且沒有人查得出來。而且補償是**不對稱的**：提升往下補到 −12 dB，
      削減往上只補 +3 dB —— 補回去的增益會原封不動回到回授迴路裡，
      於是「把高音砍掉來壓嘯叫」這個最直覺的動作會變成完全沒有效果。
      防嘯叫：中高音的提升是**直接加進迴路增益**的（回授幾乎都在 1.5k~6kHz），
      所以推高時會提醒 —— 但**只說、不自動把滑桿拉回去**，一個會自己改掉
      使用者剛推上去的滑桿的系統是包廂裡最難查的那種壞法。低音不計入風險分
      （200Hz 以下幾乎不會自激，算進去只會讓「厚實」那一組預設一直在示警，
      而示警多了就沒有人看）。一鍵乾聲則會把麥克風那一套歸零（按下它的那一刻
      通常正在叫），音樂那一套不動。
      最後兩個決定：**兩套而不是一套**（混在一起的話「我的聲音太悶」會被調成
      「整首歌的低音一起轟」），以及**六個欄位分開送**（滑桿一次只推一段，
      送整包要先合併舊值，而兩支手機同時調音時，合併正是「另外兩段被歸零」
      的來源，而且兩邊畫面上看起來都是對的）。詳見 CHANGELOG 1.31.0。
- [x] 防嘯叫（回授抑制）*(2026-09-28)* —— 商用擴大機面板上都有那一顆
      「防嘯叫」，而這台機器在這一版之前只有**繞過**它的辦法（切單人模式、
      把柔化拉到底、把麥克風轉小聲），沒有一個是「繼續唱，而且不會叫」。
      功能的形狀很清楚（找出自激的頻率，在那一點上挖一個很窄的凹槽），
      難的全部在**怎麼分得出「人唱的長音」與「嘯叫」**，以及**什麼時候放掉**。
      分辨：兩者在頻譜上都是一根突出的窄峰，分得開的只有時間上的行為 ——
      嘯叫釘死在同一個 bin（它是房間的共振，不是人）、只會越來越大
      （迴路增益 > 1 就是指數成長）、而且是一根孤峰（人聲是一整列諧波）。
      這裡有一個寫了才發現的坑：光靠「漏太久就作廢」擋不住抖音 ——
      5 Hz 的抖音離開某一格的時間約 0.1 秒，剛好落在對 FFT 抖動的容忍值裡面，
      於是它會斷斷續續地累積，唱久了照樣鎖定。真正在自激的頻率**一幀都不會漏**，
      所以改成「漏一幀賠三幀」，間歇性的東西就永遠到不了門檻。
      諧波剔除也只能**往下看不往上看**：嘯叫被喇叭推到失真時自己也會長出
      二次諧波，照「有泛音就是人聲」去判的話，被放掉的正好是要抓的那根基頻。
      放掉：這是整個功能最違反直覺的一點 —— 凹槽一挖下去，嘯叫就從麥克風的
      **輸入**消失了（迴路斷了，房間裡不再有那個音），所以機器**永遠看不到**
      「麥克風已經拿開了」。沒有任何訊號能證明原因已經排除，唯一的方法是
      放掉一格試試看。所以回退是定時的（每 45 秒一格），而且同時只有一個
      凹槽在試 —— 全部一起放的話，原因還在的房間會當場四個頻率一起叫回來。
      誤判的代價不對稱也決定了判準要保守：漏判是繼續叫（兩秒後還會再抓到），
      誤判是在人聲上挖了一個洞而且**沒有任何人查得出原因**。
      最後一個決定是**壓不住的時候只舉手，不自己把麥克風轉小聲**：
      音量莫名變小、而且沒有人碰過滑桿，是包廂裡最難查的一種「機器壞了」；
      而那一刻唯一有效的動作（把麥克風拿離喇叭）只有人做得到。
      詳見 CHANGELOG 1.28.0。

### 選歌與調性
- [x] 音域檢測與建議 Key *(2026-09-29)* —— 商用點歌機上那一顆「男調 −4 ／
      女調 +4」是一個**對所有人都一樣的猜測**；JOYSOUND 的「音域チェック」與
      DAM 的推薦 Key 做的是先認識這個人，再對每一首歌說一句話。這一輪補的是後者。
      起點是一個這台機器獨有的優勢：**麥克風的音高每一幀都在偵測**（評分本來
      就要用），所以不必請客人對著機器唱音階做測驗 —— 音域是唱歌的副產品。
      這件事的價值不在省事，在於**測驗會被跳過**：包廂裡沒有人願意在朋友面前
      對著機器「啊————」，而一個沒有人做的測驗等於沒有這個功能。
      難的全部在**哪些幀可以收、那幾個數字怎麼算**：
      音域的兩端是「你真的唱住過的音」（一格要有支撐才算數）而不是 min/max
      —— 自相關法的八度誤判只要有一幀，min/max 的音域就寬了 12 個半音，
      而且之後一直在；滑上去的轉音一格都不留（一段要連續穩住約 0.13 秒），
      但**判準必須看整段的擺幅而不是「這一幀離平均多遠」**，寫完才發現後者
      會被抖音鑽過去 —— 擺幅 ±0.5 的抖音第二幀就離「平均」（只有第一幀的那個
      波峰）整整 1.0 個半音，於是一個唱了四秒的長音一幀都收不到；
      電平太小的不收，因為多人模式下**喇叭裡的原唱也是一個人在唱歌**，
      而音高偵測分不出那是誰。
      建議那一側同理：一首歌要求的高度**不是它最高的那個音**（橋段那兩秒的
      飆高音佔全曲人聲不到 1%，拿它判的話九成的歌都會被說「你唱不上去」，
      而那句話說多了就沒有人看），所以用照**時長**加權的分位數；成本函數裡
      「超出上緣」的權重是「低於下緣」的三倍（唱不上去是唱不出來，唱太低
      只是變悶）；而「不調」要贏平手 —— 差一點點就叫人去調 Key 的系統，
      第三次之後連真的該調的那一次也會被忽略。
      最後兩個決定跟今晚擂台同一條線：**認暱稱、沒取暱稱的不建檔**
      （一桌八個人混成一份檔案，算出來的舒適音域會寬到對每一首歌都說
      「不必調」—— 一個永遠說不必調的功能等於沒有這個功能，而且看不出它壞了），
      以及**資料不夠就說「還在認識你的聲音」**，一個數字都不給。
      詳見 CHANGELOG 1.29.0。

### 排名與成績
- [x] 今晚擂台（包廂歌王榜）*(2026-09-27)* —— 商用點歌機上都有的那一張榜，
      而且是這台機器**已經有全部素材、只差一個定義**的功能：每一次演唱的命中率
      都已經在 `score_history` 裡了。所以難的一件事都不在資料上，全部在
      **那個數字要怎麼算**。
      最重要的一個決定是**不能用結算畫面上那個四位數的分數**：它是一個累加器
      （每命中一幀 +15），同時量到「唱得準不準」與「這首歌有多長」——
      五分鐘的抒情歌唱到 70% 會遠高於兩分半的快歌唱到 95%，於是選出來的歌王
      是「挑最長的歌的人」，而那個榜還會反過來教大家專挑長歌。用命中率排名，
      並且把它叫成另一個名字（擂台分），才不會有人問「我唱了 3,480 分，
      為什麼榜上寫 78」。
      第二個決定是代表分＝**最好的三首不同的歌的平均**。想過的另外三種各有
      各的壞法：加總是唱最多的贏（而那正是公平輪唱在約束的那個人）、
      單曲最高是一首運氣好就封王、**全部平均則會懲罰參與** —— 唱滿門檻之後
      就不敢再唱，因為下一首唱壞會把自己拉下來，而一個會讓人停止唱歌的榜
      放在卡拉OK機器上是自相矛盾的。取幾首與門檻刻意是同一個數字，不然
      「只唱兩首」等於少一次犯錯的機會。
      第三是**沒取暱稱的不進榜**：公平輪唱把未具名的全算同一個人（那是對的，
      那讓輪唱在沒有人取暱稱時等於沒開），但榜的全部意義就是指出一個人，
      而那位「無名氏歌王」其實是一群人。
      其餘都是邊界：同一首只算最好的那一次（不然三首會是同一首唱三次）、
      沒有導唱音符的歌是「沒得算」不是 0 分、一場照空檔切（跟輪唱與整晚打包
      同一個定義）、而且**讀榜也會換場**（不然一早開機看到的是昨晚的歌王）。
      詳見 CHANGELOG 1.27.0。

### 系統
- [x] 備份與還原 *(2026-09-30)* —— 前面二十九版補的都是「包廂裡的那一晚」，
      這一項補的是**那一晚之後**：硬碟會壞、機器會換、店會從單機換成一台
      伺服器帶十間包廂。在這之前，這台機器上累積出來的每一樣東西
      （歌號簿、最愛、成績、音域、字幕校正、設定）都只存在 `cache/` 底下
      那十幾個 JSON 檔裡，**沒有任何一條路可以帶走它們**。
      所以這個功能的主體是一張**清單**，以及每一條為什麼在（或不在）上面的
      理由 —— 它刻意不是 `tar cache/`。
      最重要的一條是**歌號簿**：它是整份備份裡唯一沒有第二個來源的東西。
      曲庫可以重下載（來源網址記在 metadata 裡）、最愛與成績重唱會再長出來、
      設定按幾下就調回去，但歌號是一個承諾（「100237 永遠是稻香，或者什麼
      都不是」）。號碼簿沒跟過去，新機器會照自己的入庫順序重新發號，
      於是客人記了三年的那六個數字指到別首歌 —— **而且沒有任何人會收到通知**。
      **不進備份的三類**同樣是設計的一部分：曲庫本體（幾十 GB，而且是清單上
      唯一可重建的東西 —— 改放一張唯讀的曲庫清單，還原後才講得出「其餘 272 首
      重新處理就會拿回原本的號碼」，不然那幾百個號碼會無聲地變成墓碑，
      而使用者的結論是「還原失敗了」）、錄音與櫃檯密碼（備份檔會被 email、
      丟進雲端硬碟，而 PIN 是這台機器唯一的安全邊界 —— 這是整個功能唯一一個
      安全等級的錯，而且沒有症狀，所以有測試釘死）、以及「現在正在發生的事」
      （包廂計時、未結案的服務鈴、今晚的擂台 —— 搬機器的那一刻沒有人在唱歌）。
      **還原不是現在做，是下次開機做**，這是寫到一半才看清楚的：每一個服務
      都在 `__init__` 就把 JSON 讀進記憶體了，直接覆寫檔案的話，記憶體裡那份
      舊資料會在下一次寫入時把還原的內容蓋回去 —— 而且完全無聲（還原看起來
      成功，五分鐘後有人按一下收藏，那一份就沒了）。所以驗過的內容攤進
      `restore_pending/`，在任何服務被建立之前套用。
      其餘三件事都是同一個形狀：**套用前先把現況打包**（慌的時候最容易做的
      錯事是還原錯一份備份），**現況打包失敗就整個不做**（沒有退路的還原
      不值得做），**只還原不合併**（兩台機器各自從 100001 發號，合併的結果是
      同一個號碼對到兩首歌）。詳見 CHANGELOG 1.30.0。
- [x] 多包廂 *(2026-09-26)* —— ROADMAP 上最後一項，也是「家裡那台」與
      「放得進店裡那台」之間剩下的最後一條線。功能的形狀很清楚（每一間一組
      佇列、一組計時、一支舞台），難的全部在**分界**與**那顆共用的 CPU**。
      分界：分房的是「這一組客人現在正在做的事」（佇列、輪唱、額度、計時、

      索引、排程、排行、最愛、錄音、設定、櫃檯鎖）。分錯邊的代價不對稱 ——

      在這之前曲庫只有一個入口（YouTube），而那讓整套東西**放不進店裡**：

      主體，因為三個月後加路由的人不會記得有那個檔案。上鎖不需要密碼
      （關門不需要鑰匙）、閒置自動上鎖（櫃檯忘記鎖是常態）、解鎖綁裝置
      （櫃檯的平板解開不等於包廂每支手機都解開）、壞檔 fail-closed，
      而且忘記密碼一定有解（環境變數／刪檔案，兩條都要碰得到伺服器 ——
      那正是安全邊界）。詳見 CHANGELOG 1.20.0。
- [x] 自動接歌（待機時自己接一首）*(2026-09-20)* —— 商用點歌機的「沒有安靜這個
      狀態」。功能本身三行就寫得完（隨機挑一首播），難的全部在**機器什麼時候
      該閉嘴**：只挑已經備好的歌（不趁大家在聊天時去下載新歌把 CPU 吃光）、
      空了要先等二十秒（別跟正在找歌的人搶）、有人點歌時看「有沒有人已經唱
      進去了」再決定當場讓位還是唱完（45 秒為界）、連著接三首沒人接手就安靜
      （沒有人點歌通常代表沒有人在了）。而且機器接的歌不算任何人的一首 ——
      尤其不進點唱排行，否則照排行挑歌、播出來又計進排行，那條排行三個晚上
      之後就只剩機器自己的回音。詳見 CHANGELOG 1.18.0。

### 字幕對齊
- [x] 每首歌自己的字幕偏移 *(2026-09-22)* —— 「字幕對不上」有兩種原因
      （這台裝置的喇叭延遲、這首歌的 LRC 偏差），以前塞在同一個數字裡，
      所以為某一首爛 LRC 調的 +300ms 會跟著機器走，下一首反而多錯 300ms，
      而且那個錯誤**無聲、無界、會自我增強**。拆開之後最重要的決定是
      「方向鍵動哪一個」：預設動這首歌，因為它的失敗模式**大聲、有界、
      會自己報到**（同方向、差不多的量、每一首都這樣）—— 機器因此看得見它，
      可以主動說「這比較像喇叭的延遲」，但只提示不自動套用。
      另外一個不能錯的地方：偏移只移動字幕，**絕不移動評分**（導唱音符活在
      音訊時間軸上）。詳見 CHANGELOG 1.22.0。
- [x] 對齊品質徽章與「只重算歌詞」*(2026-09-22)* —— 診斷檔一直都在寫，
      只是從來沒出現在畫面上；而「字幕整首歪掉」唯一的修法是那顆貴的
      「重新處理」。難的是**判讀**：沒有診斷檔是「未知」不是 0 分、
      whisper 的 score 恆為 0 是「沒有 LRC 可對」不是「對得爛」、
      placeholder 才是真的該紅；而且分數沒有對人校準過，所以文字是主體、
      數字退到 tooltip。詳見 CHANGELOG 1.22.0。
- [x] 「兩點校正」*(2026-09-23)* —— 解的是第三種症狀「越唱越歪」（抓到的歌詞
      來自變速過的上傳版本）。數學是兩點一線，十行就寫得完；難的全部在
      **那條線值不值得相信**。
      最重要的一個數字是「兩點至少隔 60 秒」：按鍵的反應時間雜訊會被跨距
      **放大**成速度誤差（誤差 ≈ 雜訊 ÷ 跨距），跨距 20 秒時 0.15 秒的手誤
      在四分鐘的歌片尾是 1.8 秒 —— **比不校正更糟**，而且歪在片尾（沒有人
      在那裡盯著字幕）。所以太近的第 2 點當成「重新標記第 1 點」而不是錯誤
      （按錯的人本來就會立刻再按一次，當成錯誤的話那個錯的點就拔不掉了）。
      第二件事是**機器猜得到、猜不準的那一步交給人看**：按下去時只能用時間
      配對「他指的是哪一句」，而字幕正歪著（那就是他按鍵的原因）—— 所以把
      配對到的那一句原文印出來，對錯了再按一次就重標。
      其餘都是「寧可拒絕也不要算出一條錯的直線」：速度不在 0.85×~1.15×、
      先後對不起來、偏移超過 ±2 秒、按鍵離所有句首超過 8 秒，一律拒絕並說出
      下一步。而人的反應時間**刻意不補** —— 那是對兩點都一樣的常數，相減時
      整個消掉，只落在偏移上，而偏移本來就是按一下方向鍵就修得掉的東西。
      詳見 CHANGELOG 1.23.0。

### 查歌
- [x] 歌號點歌（六位數）*(2026-09-21)* —— 商用點歌機上最快的一條點歌路，
      也是包廂裡唯一可以用喊的那一條。功能本身三行就寫得完（給每首歌一個
      流水號），全部的內容是一個**承諾**：這組號碼永遠不會變成別首歌。
      所以刪快取不回收號碼（留墓碑，打進去說「這首已經不在曲庫了」而不是
      給出別人的歌）、同一首回來拿回原號（綁 song_id）、只發給已經備好的歌、
      發號順序照入庫時間所以可重建、號碼簿壞掉寧可整個功能停掉也不重發一套。
      數字鍵刻意**不**照注音鍵盤那樣變灰 —— 變灰的話已下架的號碼打不完，
      而使用者正是為了那句「它去哪了」才來打的。詳見 CHANGELOG 1.19.0。
- [x] 歌星注音索引（歌星查歌）*(2026-09-19)* —— 商用點歌機的「歌星點歌」。
      難的不是鍵盤（跟歌名查歌共用同一副），是**誰跟誰是同一個人**：同一位歌星
      在曲庫裡會長出「周杰倫」「Jay Chou」「周杰倫 Jay Chou」三種寫法，不併的話
      清單上會出現三個周杰倫，每一個手上只有他一部分的歌。併的規則刻意保守
      （整段比、漢字不同就不准併、沒有證據就不猜）：錯併的代價是歌單裡混進別人
      的歌，比漏併嚴重得多。詳見 CHANGELOG 1.17.0。

- [x] 每人的點歌上限 *(2026-09-15)* —— 「滿了之後怎麼辦」的答案是**別做成「今晚

### 包廂與櫃檯之間
- [x] 服務鈴（包廂呼叫櫃檯）*(2026-09-22)* —— 舞台訊息的反方向，補完包廂與櫃檯
      之間的另一條路。功能本身三行就寫得完（存一筆需求、亮給櫃檯看），難的全部在
      **按下去之後**：一顆沒有回音的鈴會被按第五次，因為按的人分不出「櫃檯看到了、
      正在弄」跟「這顆鍵根本沒作用」。所以同時只有一張未結案的單（再按是併進去，
      櫃檯看到的是一列與「按了 3 次」，不是五列一樣的東西）、併單**不重設等待
      時間**（等最久的那一桌不該因為按最多次而排到最後面）、狀態分四種而且
      一直留在畫面上（跳一下就消失的「已送出」等於沒有回應）、客人可以自己取消
      而且取消與完成在紀錄上分得開。服務鈴的字**一個都不上舞台** —— 台上那個人
      沒有點那份冰塊。詳見 CHANGELOG 1.20.0。

### 商用點歌機還有、這裡還沒有的（下輪可挑）
- [x] 包廂計時與「剩下多久」提醒 *(2026-09-16)* —— 「時間到之後怎麼辦」的答案是
      **不要停正在唱的那一首**：時間到讓它唱完，唱完之後不再播下一首，佇列
      一首都不刪。超時的上限因此是一首歌的長度（可預期），而不是停在副歌那一句
      （不可預期的難堪）。設定頁刻意沒有「立刻停掉」這個選項。詳見 CHANGELOG 1.14.0。
- [x] 舞台跑馬燈訊息 *(2026-09-17)* —— 「它會蓋住歌詞的哪一區」的答案是
      **一區都不蓋**：訊息帶做成版面裡的 flex 元素，出現時把整排 HUD 往下推，
      而不是絕對定位疊上去；歌詞與音準線那半邊完全不動。大字卡只在沒有人
      唱歌的時候出現，播歌中（連緊急訊息也）一律降級成上緣那一條。
      而且它**不捲動** —— 會動的字會一直把餘光拉過去，而唱歌的人正需要那個
      餘光看歌詞。詳見 CHANGELOG 1.15.0。
- [x] 歌名字數／注音首字查歌 *(2026-09-18)* —— 商用點歌機的實體鍵盤查法。
      「查什麼」的答案是**只查已經備好的曲庫**（列出來的每一首都是快取秒播），
      而難的不是鍵盤，是**索引要建在哪一串字上**：YouTube 標題不是歌名
      （「周杰倫 Jay Chou - 稻香 Rice Fields【Official MV】4K」照整串字算，
      字數是二十幾個、注音從「ㄓ」開始），所以先萃歌名本體再建索引；
      多音字則每個讀音都存 —— 只留一個的話，另一半使用者永遠查不到那首歌，
      而且他會以為曲庫裡沒有。詳見 CHANGELOG 1.16.0。

### 下一輪看得到的兩個洞
- [ ] **介面只有中文**。這台機器已經放得進店裡，但放不進有外國客人的那幾間。
      難的不是翻譯，是**哪些字不能翻**（歌名、歌星、客人取的暱稱）、
      **語言是誰的屬性**（舞台是包廂的、手機是那個人的 —— 同一間包廂裡
      兩支手機各自看自己的語言才合理，但舞台只有一塊螢幕），
      以及**字長差一倍之後版面還成不成立**（「插播」兩個字的那顆按鈕，
      英文是 "Play Next"）。
- [ ] **對唱模式下的修音**（兩支麥克風各自偵測、各自修）。這一版只有一條
      修音路徑接在 A 麥上，所以對唱時整個停用。要補的話需要第二顆移調器與
      第二條偵測，而且串音判定要從「事後算誰的分」變成「當下該不該修」——
      後者沒有延遲可用，是真正難的那一半。
