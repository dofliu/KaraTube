## 2026-09-20 — 自動接歌：機器什麼時候該閉嘴（v1.18.0「Know When to Shut Up」）

**目標**：商用點歌機沒有「安靜」這個狀態 —— 一首唱完、佇列空了，機器會自己接上
下一首。對照清單上剩下的都是大工程（多包廂），這一輪補的是這件小而有感的事：
包廂裡真正被那段安靜傷到的是氣氛，一首唱完之後那三十秒沒有聲音，
所有人會同時低頭滑手機，那一桌就散了。

### 一開始就知道這個功能的程式碼很短

「從快取裡隨機挑一首播」三行就寫得完。所以這一輪從頭到尾都在寫另一半：
**一台會自己發出聲音的機器，只要挑錯時機就會變成包廂裡最吵的那個東西。**
`backend/services/autofill.py` 大半是註解，因為這個功能真正的內容是一串
「不要在這時候出聲」的規則。

### 決定一：只挑已經備好的歌

去 YouTube 抓一首要下載＋人聲分離＋歌詞對齊，是幾分鐘的 GPU 工作。
而觸發自動接歌的時機正好是「大家在聊天、等下一首」—— 等於機器趁包廂安靜的
時候把運算資源吃光，然後真的有人點歌時那一首跑不動。挑快取裡的歌則是零成本。

### 決定二：空了要先等一下下（預設 20 秒）

第一版寫成「佇列一空就接」，自己試的時候立刻發現不對：按了切歌想換一首，
手機還在搜尋頁上打字，機器已經放起了別的歌。使用者的下一個動作是按切歌 ——
一個需要人動手關掉的貼心功能就是不貼心。

順手修掉一個相關的坑：空閒的起算點放在「這一刻沒歌可播」，不是「上一首唱完」。
佇列裡還有一首在跑流水線時不算空閒（那首跑完會自己接上，機器不該搶在它前面），
而且要在有歌在播時把空閒計時清掉 —— 不清的話，一首三分鐘的歌唱完會被算成
「已經空閒三分鐘」，歌一唱完機器就當場接上，決定二等於沒寫。

### 決定三：有人點歌時，看「有沒有人已經唱進去了」

這一題想最久。兩種寫法都會有人不滿意：

- **一律立刻讓位**：跟著哼那首歌的人會被切掉。
- **一律唱完再換**：點歌的人要等最多五分鐘，而那首歌根本沒有人點。

最後照**已經播了多久**分：開播 45 秒內（大概還在前奏與第一段）就讓位，
超過就唱完再換。代價不對等 —— 唱到一半被切掉比多等兩分鐘難堪得多，
而且多等的上限是一首歌的長度（可預期）。這跟包廂計時的決定一是同一個原則：
機器可以決定下一首播什麼，但不該去停一個正在唱歌的人。

實作上只要在 `play_next()` 記下「機器接的那一首是什麼時候開播的」，
`add_song()` 收到新歌時比一次時間就夠（`auto_yield_due()`）。
時鐘用單調時鐘並且抽成 `_now()`，測試才不必真的等 45 秒。

### 決定四：它必須有一個會自己停下來的理由

「沒有人點歌」最常見的原因不是大家都想聽機器放歌，是**沒有人在了**
（去廁所、出去買東西、其實已經散場）。所以連著接滿設定的首數（預設 3 首）
就安靜下來，有人點一首就歸零。沒有這一條的話，一間沒有人的包廂會整夜自己
唱歌到隔天早上 —— 而這種壞法沒有人會回報，他們只會再也不打開這個功能。

### 決定五：機器接的歌不算任何人的一首

不進點唱排行、不進已唱歷史、不佔輪序與額度、不會把包廂的錶打開。

排行那一條是硬性的，不是風格問題：自動接歌**照排行挑歌**，播出來的歌如果
又計進排行，那條排行就變成機器自己的回音 —— 熱門的被接得更多、被接得更多
所以更熱門，三個晚上之後榜上只剩它愛放的那五首，而且沒有人看得出來是怎麼
變成這樣的。計時那一條同理：自動開錶認的是「這一場開始了」，一間沒有人的
包廂不該自己把三小時的錶按下去。

`play_next()` 因此分成兩條路：人點的歌照舊記統計、開錶、算輪序；
機器接的歌只記一個開播時間。

### 順手做的：🎲 來一首

挑歌規則既然已經寫好了，就多接一顆鍵。「想唱歌但想不到要唱什麼」跟搜尋
是兩件事 —— 搜尋要先想得出關鍵字。🎲 用同一副規則挑，但**算人點的**：
計入排行與歷史、佔輪序與額度，照樣會被歡唱時間與點歌上限擋下來。

寫測試時踩到一個小坑：`random_pick()` 原本先挑歌再讓 `add_song()` 擋額度，
於是「曲庫兩首都在佇列裡」與「額度滿了」會回同一句「沒有歌可以挑」。
改成**先擋再挑**：那兩句話的下一步完全不同（去點別的歌 vs. 等一首唱完）。

### 測試（後端 +49 條、前端 +12 條，全綠：後端 712、前端 360）

- 新增 `tests/test_autofill.py`（24 條）：來源池、權重、加權抽樣、硬排除
  （佇列裡的歌任何情況下都不挑）與軟排除（小曲庫寧可重複也不安靜）、
  來源池空了退回整個曲庫、挑歌理由。亂數全部注入，每一條都是決定性的。
- `tests/test_queue_manager.py` 加 15 條：空閒門檻、不算任何人的一首、
  不開錶、接滿就停、佇列有歌時不接、45 秒內讓位／超過唱完、不重複剛接過的、
  散場之後不接，以及 🎲 的三條。時鐘用 `manager._now` 換掉，跑得比真實時間快。
- `tests/test_api.py` 加 7 條、`tests/test_settings.py` 加 3 條。
- 新增 `frontend/tests/autofill-view.test.js`（12 條）：那幾句話有沒有講清楚
  （它為什麼挑這首、還會接幾首、有人點歌會怎麼樣），以及壞掉的狀態不該
  在畫面上印出 NaN。

## 2026-09-19 — 歌星查歌：注音首字查歌星（v1.17.0「One Singer, Not Three」）

**目標**：對照清單上商用點歌機鍵盤的最後一條路 —— **歌星**。上一輪補了歌名的
注音與字數，這一輪補按歌星名字查。包廂裡更常用的其實是這一條：想不起歌名的人，
一定記得自己要唱誰。

鍵盤是現成的（跟 `song_index` 共用 `title_keys` / `match_keys` / `normalize_query`），
所以這一輪從頭到尾都花在一件事上：**誰跟誰是同一個人**。

### 一開始就看到的問題：同一位歌星有三種寫法

曲庫的 `artist_name` 是 `library.normalize_artist()` 從頻道名與標題還原的，
同一位歌星因此會長出好幾種字串：

| 這首歌的來源 | 存進 `artist_name` 的 |
|:---|:---|
| 官方頻道「周杰倫 - Topic」 | `周杰倫` |
| 上傳者就叫「Jay Chou」 | `Jay Chou` |
| 頻道是唱片公司 → 改抓標題前半 | `周杰倫 Jay Chou` |

照原字串建索引，歌星清單會出現**三個周杰倫**，每一個手上只有他的一部分歌。
這個壞法跟上一輪「字數算成 23 個字」是同一種：使用者按 ㄓ ㄐ ㄌ 進去看到兩首，
不會想到旁邊還有兩個同名項目，他會認定曲庫裡就這兩首，
然後回頭去 YouTube 把已經有的歌再下載一份。

### 決定一：合併，但規則保守到近乎不合作

寫了 `merge_tokens()`：一個寫法拆成**整段漢字**與**整段英文**兩個片段，
共用任一段就併。幾個刻意的限制，每一個都是為了「寧可漏併，不要錯併」：

- **比整段，不比子字串**：不然「張惠妹」會被「張惠」吃掉。
- **漢字不同就不准併**（union 時檢查合併後的漢字集合大小）：英文名撞名時
  ——「林俊傑 JJ」與「林宥嘉 JJ」—— 漢字那一關擋得住。
- **少於兩個字的片段不拿來比**：一個字母誰都可能撞到。
- **「周杰倫」與「Jay Chou」沒有共用字段時就不猜**。這一條掙扎最久，因為它代表
  清單上還是可能出現兩筆。但錯併的代價是歌單裡混進別人的歌，使用者會當成系統
  壞了；漏併的代價只是清單多一筆，而且曲庫裡一旦出現一首混寫的
  （`周杰倫 Jay Chou`），兩筆自己就串起來了。這個賭注方向很清楚。

顯示名取有漢字的、短的那個（介面是中文的），其餘當別名；索引則每一種寫法都建，
所以按 ㄓ ㄐ ㄌ 或按 J C 落在同一位、翻開同一份完整歌單。

### 決定二：查到歌星之後，畫面要自己往前走一步

商用機上「按完注音 → 歌星清單 → 點一位 → 歌單」的最後那一下點擊，在只剩一位
歌星的時候沒有任何資訊量。所以只剩一位就自動選起來（`auto_selected`）。

但自己跳掉的畫面不解釋就像壞掉，所以歌單標題寫著「**只剩這一位，直接翻開歌單**」。
同一類的說法還有兩處：

- 別名「也寫作 Jay Chou」**印在歌星鈕上**而不是只放 hover 的 title ——
  包廂那台是觸控螢幕，沒有 hover，看不到的解釋等於沒解釋。
  （按英文查到中文名字的人，第一個念頭是「我是不是查錯人了」。）
- 選定一位之後再多按一個鍵，那位歌星**留在畫面上**（`match_kind: picked`），
  使用者看得到自己選的是誰，才知道要退一格。

### 決定三：「未知歌手」不進索引，但也不藏起來

它不是名字，按注音永遠不該撈到它；可是它底下的歌是真的存在的。
所以：不建注音索引、不出現在 `next_keys`、排序一律墊底，但照樣列出來並標明。
藏起來的話，曲庫總數與歌星清單加起來的數字會對不上，那是另一種「看起來壞掉」。

### 接線與驗證

- 新模組 `backend/services/artist_index.py` 接在 `SongFinder` 後面而不是自己掃曲庫：
  歌星清單、歌名索引與分類瀏覽共用同一份資料（也就順便拿到萃好的歌名本體）。
  不另外寫檔 —— `artist_name` 分類瀏覽早就算好並快取在 `metadata.json` 了。
- API 兩支：`/api/library/artists/keys`、`/api/library/artists/find`。歌星清單與
  歌單放在同一包回應裡：分兩支會讓自動翻開歌單多閃一次空畫面。
- 測試：`tests/test_artist_index.py`（21 條，釘合併規則與自動選取）、
  `tests/test_api.py` 三條、`frontend/tests/artist-search.test.js`（16 條，
  釘「畫面上那幾句話」）。實際跑了一次瀏覽器：按 ㄓ → 只剩周杰倫 → 歌單自動
  翻開、其餘的鍵只剩 ㄐ 可按，符合設計。
- **既有的守門測試當場抓到一個只有瀏覽器裡才會發作的坑**：`artist-search.js` 的
  `queryLabel` / `resultSummary` / `emptyHint` 跟 `library-search.js` 同名。
  這些檔案是 `<script src>` 一支一支載進**同一個全域作用域**的，後載入的那一份
  會默默蓋掉前面的（函式重複宣告是合法的），而 `node --test` 給每支模組獨立
  作用域，兩邊的單元測試都會是綠的。改成 `artistQueryLabel` 之類的內部名、
  對外的鍵名不變。這正是 `script-scope.test.js` 當初被寫出來的理由。

**下一步**：對照清單早就全數完成，選配清單只剩 **多包廂**（一台伺服器帶多組
舞台與佇列）—— 那是唯一一項會動到系統架構的，需要先把「一組佇列/一台舞台」
這個到處都在的隱含假設攤開來看。

## 2026-09-18 — 曲庫查歌：注音首字 / 歌名字數（v1.16.0「Two Symbols Find The Song」）

**目標**：ROADMAP 上最後一項沒打勾的對照功能 —— 商用點歌機實體鍵盤上的
「注音首字查歌」與「歌名字數查歌」。那一項掛著的備註寫得很準：
「這裡是打字搜尋 YouTube，所以真正缺的其實是**只在已快取的曲庫裡查**的那條路」。

這一輪一開始看起來像是「畫一個注音鍵盤」的工作，結果鍵盤是最快的部分。

### 決定一：索引不能建在 YouTube 標題上

曲庫裡一首歌的標題長這樣：

```
周杰倫 Jay Chou - 稻香 Rice Fields【Official MV】4K
```

先在紙上用這串字跑一次兩種查法，兩種都當場廢掉：

| 查法 | 照整串標題算會怎樣 |
|:---|:---|
| 歌名字數 | 23 個字。沒有人會去按「23 個字」，而按「2 個字」的人查不到稻香 |
| 注音首字 | 首碼從「ㄓ」（周）開始。按「ㄉㄒ」的人永遠查不到 |

所以整支模組的第一段其實是 `title_core()`：把歌手、括號附註、宣傳字樣、
尾巴的英譯剝掉，萃出歌名本體。剝的順序與幾個刻意的取捨：

- `《稻香》`「稻香」**先認**：中文標題標歌名的慣例，比任何猜測都準。
- 用 ` - ` `｜` 切開時留「不是歌手」的那半 —— 歌手是誰分類瀏覽已經判過了
  （`artist_name`），不必再猜一次，兩邊也才不會打架。
- 空白隔開的歌手名（「江蕙 甲你攬牢牢」）也剝，但**只認完整相同的那一段**：
  〈朋友〉就是周華健的歌名，模糊比對會把歌名整個剝掉。
- 剝完只剩歌手（或一個漢字都不剩）時改用括號裡的：「五月天 Mayday【入陣曲】」
  這種標題，歌名是關在括號裡的。中文歌手的英文名還是歌手。
- 萃不出東西時回原標題，**絕不回空字串**。曲庫裡出現一首沒有名字的歌，
  比查不到更糟。

尾巴的英譯（`稻香 Rice Fields` → `稻香`）是最後才加的一條，而它是被畫面逼出來的
——見決定三。

### 決定二：多音字存集合，不存一個答案

`char_initials("重")` 回 `"ㄓㄔㄊ"`，比對時只要使用者按的那一鍵落在該格的候選裡
就算命中（`pypinyin` 的 `heteronym=True`）。

只留字典排第一的讀音省事得多，成本卻是這個功能最糟的失敗方式：另一半使用者
**永遠**查不到那首歌，而且他不會知道為什麼。他不會想到是多音字，他會結論
「曲庫裡沒有這首」，然後回去用搜尋框把一首已經在硬碟上的歌再下載、再跑一次
AI 流水線。查歌功能做出來是為了省掉那件事，結果反而製造那件事。

同樣的理由讓比對做成**連續子序列**而不是只比開頭：使用者記得的常常是中間
那幾個字（〈甲你攬牢牢〉記得的是「攬牢牢」）。開頭命中的排前面就好，
不必把中間命中的排除掉。

### 決定三：全灰的鍵盤等於沒給資訊

商用機會把「按下去必定落空」的鍵變灰，所以伺服器多回一個 `next_keys`
（這一串後面還接得下哪些鍵）。做完用瀏覽器實際點一遍，按完「ㄉㄒ」之後
**整個注音鍵盤 37 顆全灰**。

技術上完全正確：「稻香 Rice Fields」的下一格是英文單字 `Rice`，沒有任何注音
接得下去。但畫面上那是一片死掉的鍵盤，任何人看到都會認定它壞了。

修了兩個地方，因為那一片灰其實同時暴露了兩件事：

1. **資料**：尾巴的英譯根本不該進索引（它讓字數也錯）。剝掉之後「稻香」的
   索引就是 `ㄉㄒ` 兩格，按完就是按完。
2. **呈現**：`usableNextKeys()` —— 會讓整個鍵盤一起變灰時，一顆都不變灰。
   全灰畫面沒有給任何資訊，只有嚇人的效果。

這一條是這輪唯一靠「真的打開瀏覽器點一遍」才發現的問題。單元測試全綠、
API 回的 JSON 也對，錯的是那個 JSON 在畫面上長出來的樣子。

### 決定四：查不到的時候要講得出是誰擋的

空白畫面配一句「找不到」，使用者的下一個動作就是回搜尋框重下載一次。
所以 `emptyHint()` 照「最可能的誤會」排序回答：曲庫是空的 → 字數條件還開著
（按了注音又看到空白時，十次有八次是這個）→ 注音字典沒裝 → 真的沒有這首
（順便說明注音查的是「每個字的第一個符號」）。

這一段跟點歌額度、歡唱時間、舞台訊息是同一種語氣：每一句「沒有」後面都要
接得出下一步。

### 其他決定

- **一個輸入框吃三種查法**。注音鍵盤、字數、直接打字都寫進同一個 `q`
  （伺服器本來就三種都吃），使用者不必想「我該打在哪一格」。
- **索引寫回 `metadata.json` 的 `find_index`**，跟語言/歌手分類同一個做法：
  算一次就好，刪快取跟著消失。帶 `INDEX_VERSION`，規則改了自動重算 ——
  不然使用者會拿著新鍵盤去查用舊規則建的索引，查不到還找不出原因
  （這一輪自己就踩到：改了萃取規則之後，舊索引的「稻香 Rice Fields」還在）。
- **兩支端點都丟到 executor**。第一次查要替整個曲庫建索引，那是幾百次讀檔，
  跟上一版把 ffmpeg 探測丟進執行緒是同一個理由：不能佔住 event loop 讓別人
  點不了歌。
- **`pypinyin` 沒裝也不會壞**：`bopomofo_available` 回 `false`，鍵盤收起來並
  說明原因，字數與打字查詢照常；裝上之後索引會自動補建注音那一段
  （索引記得自己是在哪種環境建的）。

### 測試（後端 +31、前端 +20，全綠）

- `tests/test_song_index.py`（31 條）：歌名本體萃取的七種標題形狀、多音字、
  一格一個字（英文以單字為單位）、連續子序列與排序、字數桶、壞掉的 metadata、
  `next_keys`。沒有 `pypinyin` 的環境只跳過注音那幾條，其餘照跑 ——
  那種環境下字數與打字查詢仍然必須是好的。
- `frontend/tests/library-search.test.js`（20 條）：按鍵累加與上限、退格、
  條件列的說法、查不到時的四種說法、全灰鍵盤的那條例外。
- `tests/test_api.py` +3 條：兩支端點的形狀與參數範圍。

## 2026-09-17 — 舞台訊息／跑馬燈（v1.15.0「Word From The Front Desk」）

**目標**：商用點歌機的「櫃檯把字打到包廂螢幕上」。ROADMAP 上這一項掛著的
理由寫得很清楚：「**要想清楚它會蓋住歌詞的哪一區**」。功能本身三行就寫得完
（存一段字、推出去、顯示），所以這一輪的工作幾乎全部在那一句備註上。

### 決定一：一區都不蓋 —— 用「推開」而不是「疊上去」

先把舞台那面螢幕現在有什麼列出來：

| 位置 | 現在是什麼 | 可以讓嗎 |
|:---|:---|:---|
| 最上緣 | （空的）| ✅ 唯一的空地 |
| HUD 那一排 | 歌名、歡唱倒數、分數 | ⚠️ 可以被推開，不能被蓋 |
| 中段 | 音準導唱線 | ❌ |
| 下半整片 | 歌詞 | ❌ 台上那個人正在看它唱歌 |

只剩最上緣。但「放在最上緣」還有兩種寫法，而它們的差別正是這個功能的成敗：
絕對定位的浮層（`position: absolute; top: 0`）與版面裡的一個 flex 元素。

浮層寫起來比較快，而且**在開發機上看起來一模一樣**。差別要等到包廂裡、
等到訊息真的跳出來的那幾秒才看得到：它會壓到某個字。所以訊息帶做成
`.stage-wrapper` 的第一個 flex 子元素 —— 它出現時版面把整排 HUD 往下推，
不可能疊到任何東西。這跟上一版把歡唱倒數排進 HUD 的 flex 裡是同一個理由，
只是那次是「角落已經有東西了」，這次是「連角落都不夠」。

### 決定二：同一則訊息有兩種身體

櫃檯要的是「一定看得到」。但那句話在副歌那一句等於「一定擋到」。

所以訊息分成兩種呈現：沒有人在唱歌時是置中的大字卡（64px，看一眼就知道），
正在播歌時降級成上緣那一條（26px）。**緊急訊息也一樣降級** —— 想過讓 ⚡ 可以
用大字卡（畢竟叫「緊急」），但寫下去之後那顆勾選框就變成「可以蓋住正在唱的
那個人」的開關，而它就在每一支手機上。緊急換到的優待因此只有兩樣：
排到最前面、停留久一點（×1.5）。真的那麼急的事，走到包廂門口敲門比較快。

設定頁同理只有「沒在播歌時用大字卡」這個開關，**沒有**「播歌時也用大字卡」。
跟上一版「沒有立刻停歌這個選項」是同一條原則：不要把要消滅的那個畫面
做成一個選項留在那裡等人選到。

### 決定三：它不跑

叫它跑馬燈是因為大家都這樣叫它。但實作上刻意**不捲動**：會動的字會一直把
餘光拉過去，而唱歌的人正需要那個餘光看歌詞。只有一次 0.45 秒的淡入，
然後停著讓人讀完。

40 字的上限就是從這個決定來的 —— 不捲動的話，一行讀得完就是硬條件。
反過來說，如果允許一百字，就非得捲動不可，然後上面那個決定就被推翻了。

### 決定四：會自己消失，而且沒有「永不過期」

「您的餐點到了」在四十分鐘之後才出現在螢幕上，不是「舊資訊」，是**錯誤資訊**，
比沒有訊息更糟。所以每一則預設 10 分鐘後自己消失。

要留久一點的得明講「📌 釘住」，而釘住的天花板是 4 小時：散場之後還掛在
螢幕上的生日祝福，是下一桌客人看到的第一個東西。

消失做成**兩道**：畫面自己會濾掉過期的（伺服器心跳五秒一次，而「十分鐘後
消失」差五秒就不叫十分鐘了），伺服器的心跳也會清掉並廣播 —— 後者不是為了
舞台，是為了讓點歌台的清單跟舞台上跑的是**同一份**。

### 決定五：不落地

上一版的計時要存檔（客人買了多久，不該因為重開機而重算）。訊息剛好相反：
伺服器重開之後最可能的狀況是「那件事早就處理完了」，而一則沒有人記得的舊
訊息自己跳到螢幕上，看起來就像機器壞了。釘住的祝福重打一次只要五秒。

所以 `MarqueeBoard` 連 `state_file` 參數都沒有 —— 不是「先不做」，
是這個功能不該有那個東西。

### 時間怎麼算（沿用計時那一套）

存活時間在畫面上是**相減**算出來的：快照裡的 `updated_at` 與 `expires_at`
相減，再減掉「收到快照之後過了多久」。兩個時間都出自同一台伺服器，
所以完全沒有時鐘問題 —— 舞台那台機器的時鐘常常跟伺服器差好幾分鐘，
比對絕對時刻的話訊息會提早消失或不肯消失。

輪播的相位則交給舞台自己算：跟倒數那個數字不一樣，「現在輪到第幾則」沒有
兩個畫面對不起來的問題（只有舞台在顯示它）。

### 實作

- `backend/services/marquee.py`：`MarqueeBoard`（送出、列出、撤掉、過期清理），
  字數 40／則數 8／秒數 3~30／存活 1~240 分／釘住上限 4 小時全部夾限在這裡。
  擋下來丟 `MarqueeRejected(reason, detail)`，帶著現況一起丟 —— API 層才講得出
  「最多八則，等一則播完或撤掉一則」，那句話是畫面的工作不是服務層的。
- `backend/main.py`：四支端點 + `MARQUEE_UPDATE` 廣播；
  `room_timer_loop` 改名 `stage_heartbeat_loop`，多負責清掉過期訊息。
- `frontend/js/marquee-view.js`：純邏輯（輪到哪一則、band 還是 card、剩多久、
  擋下來說什麼），舞台與點歌台載同一支 —— 兩邊各寫一次的話，同一則訊息會在
  兩個畫面上講出不同的說法。
- 點歌台：最上排 📺 舞台訊息（右上角帶「現在有幾則」的數字）、常用句、
  ⚡／📌 兩個選項、現有訊息清單（誰送的、剩多久、可單獨撤掉）。
  訊息文字一律 `textContent` 放進 DOM —— 那段字是包廂裡任何一支手機打進來的。

### 測試（後端 605 條、前端 312 條，全綠）

## 2026-09-16 — 包廂計時（v1.14.0「Finish This Song」）

**目標**：商用點歌機的「歡唱時間到」。ROADMAP 上這一項掛著的理由跟上一版
（「滿了之後怎麼辦」）是同一類的題目：**難的不是倒數，倒數是減法**。
難的是時間到之後那一分鐘。

### 決定一：時間到不停歌，停的是「下一首」

先把商用機的做法寫出來看：時間到，正在唱的那一首**直接切斷**。

那個畫面是這樣的 —— 被切掉的那個人正站在包廂中間、麥克風在他手上、
他剛唱到副歌最高的那一句，然後畫面黑掉。他不會覺得「時間到了」，
他會覺得「機器在我唱到一半的時候把我關掉」。一個本來可以好好收場的晚上，
最後一個畫面是難堪。

換成「讓這一首唱完，然後不再播下一首」：超時的上限變成**一首歌的長度**
（三到五分鐘），而且是可預期的、講得出來的（提醒的時候就先講）。
相對的，停在副歌那一句是不可預期的。拿三分鐘換掉那個畫面很划算。

這個決定最重要的一半在**設定頁**：那裡只有「唱完這一首再停」與
「只提醒，不停歌」兩個選項，**沒有**「立刻停掉」。想過要不要加（商用機都
這樣做，加了比較「完整」），但那正是這個功能要消滅的畫面 ——
把它做成一個選項，等於把它留在那裡等人選到，而選到的人不會知道自己選了什麼。

實作上這條規則只有一行：`play_next()` 開頭先問 `room_stops_playback()`。
它必須擋在「找下一首」之前、而且**不碰 `current_song`** ——
這是整個功能唯一真正重要的那一行，`test_time_up_stops_the_next_song_not_the_current_one`
就是釘著它（正在唱的那一首不被動到、佇列一首不少）。

### 決定二：佇列一首都不刪

時間到之後佇列原封不動留在畫面上。

想過「時間到就清空佇列」（看起來乾淨）。但「時間到」與「佇列被清空」在畫面上
是**同一秒**發生的，那看起來就像機器當掉了；而且續時之後大家得重點一輪，
沒有人記得剛剛排了什麼。停下來的是**播放**，不是資料。

這件事要講出來才有用，所以散場畫面的第二行就是它：
「佇列裡還有 4 首歌留著，續時之後接著唱。」—— 看到那個畫面的人，
下一個念頭一定是「那我排的歌呢」。

### 決定三：提醒要講「時間到會發生什麼事」

提醒最容易寫成「⏳ 剩 10 分鐘」就結束。那句話少了最重要的一半。

包廂裡的人聽到「剩十分鐘」時真正想知道的是：**那最後一首會不會唱完**。
沒講的話，最後一首的點歌者會以為自己被偷走一首歌（然後不敢點）；
講了的話，剩下的十分鐘他們會自己安排誰唱最後一首 —— 那本來就是包廂自己
會排好的事，機器只要把規則講清楚。

所以每一句提醒都固定講滿：剩多久、時間到會怎樣、怎麼續時。三段話分別由
`roomDuration()`、`roomExpiryPolicyNote()`、`roomExtendHint()` 產生，
`frontend/tests/room-view.test.js` 一句一條釘著。

次數也是決定的一部分：預設**只有兩次**（剩 10 分、剩 3 分）加上時間到。
每 30 秒跳一次的提醒會被當成雜訊直接無視，然後真正重要的那一次
（時間到）也一起被無視。

### 決定四：續時要自己接回去

續時 30 分鐘之後，如果機器是停著的，它**自己播下一首**。

第一版寫成「續時只加時間」，然後在瀏覽器裡試的時候愣了一下：按了續時，
倒數變成 30 分，畫面……還是停在散場。那顆鍵看起來就像沒有反應
（而使用者的下一個動作是再按一次，於是變成 60 分）。

「結束計時」也一樣：那顆鍵的意思是「不要再管時間了」，如果按完還停在散場畫面
不肯播，沒有人找得到怎麼救回來。所以它也解除停播旗標並接回去
（`test_stop_releases_the_halt`）。

### 踩到的四件事

**一次跨過三個門檻，三句話一起跳出來。**
寫測試時把開場時間挪到 11 分鐘前，`tick()` 一次回了 `warn` / `last_call` /
`expired` 三個提醒。真實情境也會遇到：伺服器剛重開、心跳被卡住、或是有人開了
一場比提醒門檻還短的。三句話在同一秒鐘互相蓋掉，而真正該被看到的是最後那一句。
改成**只回最急的那一個**，其餘標記為已講過。

**舞台的倒數疊到了分數上。**
本來把它絕對定位在 `top: 28px; right: 40px`，理由寫得很漂亮（「右上角是唯一
一塊不會有歌詞也不會有分數的地方」）—— 然後截圖一看，正好疊在 KTV SCORE 上面。
改成排進 HUD 那一排的 flex（歌名與分數之間）：版面只會把它們推開，
不會互相蓋住。角落的絕對定位遲早會疊到東西，而且只有在包廂裡、
只有在最後十分鐘才看得到。

**散場畫面差一點蓋掉最後一位演唱者的分數。**
最後一首唱完時，舞台會先亮九秒的結算畫面（伺服器也是等結算跑完收到
`SONG_ENDED` 才真的停住）。散場畫面的 z-index 因此刻意壓在結算底下 ——
今晚最後一個分數是最該被看到的那一個。

**倒數不能靠廣播。**
第一版想過每秒廣播一次狀態讓畫面直接顯示。那是拿包廂的網路換一個本來就
算得出來的數字（而且舞台正在串影片）。改成伺服器五秒一次心跳（只在有事發生時
廣播），畫面自己用「拿到快照時的剩餘秒數 ＋ 從那之後過了多久」補齊每一秒。

### 實作

- 新增 `backend/services/room_timer.py`：`RoomTimer`（start / pause / resume /
  extend / stop / tick / snapshot，時間一律從外面傳進來所以測試不必等三小時）
  與 `RoomTimeUp`。存檔放 `cache/room_timer.json` —— 佇列不持久化，但計時對應的是
  「客人買了多久」，不該因為伺服器重開就重算；擺超過 12 小時才丟掉（機器關過一晚）。
  時間倒退（NTP 校時）時那一段算 0：少算對客人有利，倒扣回去會變成爭執。
- `QueueManager`：`play_next()` 開頭的停播閘門、`add_song()` 的時間到擋下
  （擋在額度之前）、`room_state()`（快照 ＋ 現在生效的規則，畫面要靠規則
  決定講哪一句話）、續時／結束時自己接回去播、第一首歌自動開錶
  （按過「結束計時」之後就不再自動開）。

## 2026-09-15 — 每人待唱上限（v1.13.0「Three Songs Each」）

**目標**：上一版（公平輪唱）解掉了包廂裡最會吵的那件事 —— **順序**。
這一版解掉它的另一半 —— **量**。

輪唱會把一個人連點的五首攤開來排，但那五首**還是在佇列裡**。包廂裡十個人、
佇列裡二十首歌、其中十二首是同一個人點的，這時候輪序只是把它們攤開，
散場前佇列還是清不完，而且排在後面那幾首的點歌者早就走了 —— 歌照唱，沒人上台。

這一項在 ROADMAP 上掛了很久，掛的理由寫得很清楚：
「要先想清楚**滿了之後怎麼辦**」。這一版就是那一題的答案。

### 決定一：算「待唱」，不算「今晚總共」—— 這就是那一題的答案

先寫下直覺的那一種：「每人今晚最多五首」。然後想它的收尾長什麼樣子：

有人第五首唱完，麥克風還在他手上，站在包廂中間。他想再點一首，
機器說「你不能再點了」。而且是**永久**的 —— 今晚剩下的三個小時都不行，
除非有人去後台按重設。那不是規則，那是懲罰，而且是一台機器對一個人執行的。

換成「同時最多排三首」，同一個場景變成：他排滿了，等自己其中一首唱完，
那一格就空出來，馬上又能點。**沒有人需要介入**，也沒有人被鎖在今晚之外。
機器講得出「什麼時候可以再點」，而且那個時間點馬上就到（下一首唱完）。

而且它才是包廂真正在抱怨的那件事。沒有人會說「你今晚唱太多首」——
時間還夠就多唱幾首，本來就沒關係；大家會說的是「佇列整排都是你的歌」。

實作上這句承諾只有一個依據：**額度只看佇列，不看正在唱的那一首**
（`pending_counts()` 吃的是 `queue`，`current_song` 不在裡面）。
把已經上台的也算進去的話，唱完之後額度不會回來，這個功能就默默退化成
上面那個永久額度 —— 而且從畫面上完全看不出來。
`test_singing_a_song_frees_a_slot` 就是釘這一條的。

### 決定二：沒取暱稱的那一桶照樣算一份額度（而且刻意就是一份）

輪唱把所有沒取暱稱的人算成**同一位**。額度沿用同一個身分定義，
於是「沒取暱稱」＝ 整桶共用一份額度。

第一版其實寫成相反的：沒取名的不受限（想法是「連名字都沒有，怎麼算他的額度」）。
寫完才發現那等於在畫面上公告：**把暱稱刪掉就無限點**。額度會在第一個發現
這件事的人手上當場失效，而且那個人還會覺得自己很聰明。

改成現在這樣之後，刪掉暱稱是把自己丟進一個**已經被別人塞滿**的桶子，
嚴格比較差。額度因此變成整個系統裡唯一一個「取暱稱**有好處**」的功能
（輪唱只是讓你排得比較公平，沒好處也沒壞處），拒絕的那句話也就直接
講出解法：「到右上角取個暱稱，就有屬於自己的 3 首」——
而不是一句沒有下一步的「不行」。

`test_naming_yourself_gets_you_your_own_allowance` 釘的就是這個方向不能反過來。

### 決定三：插播不受限，但照樣佔額度

跟輪唱對插播的處理完全一致，理由也一樣：插播是現場有人**按下去**的決定
（生日歌、朋友要走了想唱最後一首），機器的規則不該推翻現場的人剛做的決定。

但它照樣算進待唱數 —— 不算的話，插播就變成「繞過額度」的那顆按鈕，
而那顆按鈕就在每一張歌卡上（`⚡ 插播`）。

### 決定四：只擋新的，絕不回頭刪

把上限調低（或本來關著、中途才打開）時，已經排進去的歌一首都不動。

另一種寫法是「超過的從後面砍掉」，而且它很好寫。但那會是這個系統最嚴重的
一次背叛：佇列是所有人盯著看的東西，有人動了一個設定，別人排好的歌就消失了 ——
而且畫面上完全看不出是誰、為什麼。寧可規則生效得慢一點。

這一條在測試裡是**用介面形狀釘的**，不是用行為：
`test_lowering_the_limit_never_implies_removal` 檢查 `check()` 的結論裡
根本沒有「該刪什麼」這種欄位。沒有那個東西，上層就沒有東西可以拿來刪。

### 決定五：被擋下來的那句話要講滿三件事

這是整個系統裡**唯一一個對使用者說「不行」的地方**。說不清楚的話，
使用者的下一個動作是再按一次（然後再被擋一次，然後認定點歌壞了）。

所以那句話固定講滿：誰、現在幾首、什麼時候可以再點。

> ⚠️ 小明 已經排了 2 首待唱（上限 2 首）。你的下一首排在第 1 位，唱完就空出一格。

沒取暱稱的人講的是**完全不同的一句話**，因為他的處境也完全不同 ——
他不是自己排太多，是跟所有沒取名的人共用一份額度。這件事不講明白，
他看到的是「我明明只點了一首，它說我排了三首」，那看起來就是個 bug。

API 上這是 **409** 而不是 429：擋下來的理由不是「按太快」，
是「佇列現在的狀態不收這一首」。回應帶著整份結論，畫面才不必從一句字串裡
把它剖回來（而且點歌台與手機端可以用不同的說法）。

### 踩到的兩件事

**`check()` 與 `state()` 差一首，一開始共用了同一個函式。**
兩者問的是不同時間點的問題：`check()` 問「再加一首可不可以」（所以剩餘量要
扣掉正要加的那一首），`state()` 問「現在站在哪」（剩餘量就是上限減現有的）。
共用的結果是點完歌之後回報的剩餘量**固定少一首** —— 而使用者會拿那句話
跟畫面上那一行「2/3」對照，對不上就不會再相信任何一邊。拆成兩個函式，
各自有測試釘著（`test_check_counts_the_song_about_to_be_added` / `test_state_reports_where_they_stand_now`）。

**`showNotification()` 只有 2.5 秒而且不換行。**
額度那句話有六十幾個字，2.5 秒剛好夠讀到一半然後消失，而且原本的樣式沒有
寬度上限，長句在手機上會被推出畫面右邊。加了可指定秒數與
`max-width` / `line-height` —— 一句看不完的說明等於沒寫。

## 2026-09-14 — 公平輪唱（v1.12.0「Everyone Gets a Turn」）

**目標**：前面十一版都在處理「唱得怎麼樣」——音準、和聲、錄音、帶走。
這一版處理的是包廂裡**真的會吵起來**的那一件事：**順序**。

一個人連點五首，其他人就得等五首。後到的朋友想唱一首，排在最後面，
等到散場都還沒輪到。商用點歌機沒有解這一題（它們的佇列就是先到先唱，
誰手快誰先唱），真正在解的是卡拉OK 酒吧的 KJ：每個人輪流唱一首，
唱完排到隊伍後面去。這一版就是把那個 KJ 寫進機器裡。

### 決定一：只決定「插進哪裡」，不重排既有順序

第一個念頭是「每次狀態變動就照輪次把整個佇列重排一次」。寫之前先想了一下
畫面會變成什麼樣子：佇列是包廂裡**所有人盯著看**的東西（「我那首還有幾首
就到了」），每多一首歌整排就跳一次位置。而且重排會把兩件使用者剛剛做過的事
一起吃掉 —— **手動拖曳**的結果，以及**插播**。

所以輪序只在點歌的那一瞬間決定插入位置：插在「第一首輪次比我大的歌」前面。
插進去之後那一首就待在那裡不動了。

同輪次之間維持**先到先唱**。這一條看起來理所當然，但它決定了「大家各唱一首」
的那一輪裡順序是穩定的 —— 否則同一輪的四首歌會變成每次廣播都換順序。

### 決定二：插播對輪序免疫（但照樣佔掉他的一輪）

插播是現場**有人按下去**的決定：生日歌、朋友要走了想唱最後一首。
機器的排序規則不該推翻剛剛發生的那件事，所以輪序永遠不插到佇列最前面
那一段連續的插播前面。

反過來，插播**要算進**那個人的輪次。不算的話它就變成一個漏洞：
插播多唱一首，而且完全不影響自己在輪序裡的位置。

### 決定三：身分只認暱稱，不認裝置

用裝置 id 或 IP 當身分很好寫，也很快就會錯：包廂裡的手機是**傳來傳去**的
（「欸你手機借我點一首」是這個場景的常態），同一支手機背後是好幾個人；
反過來同一個人也可能一邊用點歌台、一邊用自己的手機點。

所以身分就是他自己打的那個暱稱，收斂空白（手機輸入法很容易多打一個）、
不分大小寫（Amy / amy）之後比對。

**沒取暱稱的人全部算同一個人。** 這件事看起來粗糙，但它其實是這個設計裡
最重要的一條安全網：一整間都沒取暱稱時，輪唱的行為就**完全等於沒開**
（一路往後排）—— 不會有人發現「我點的歌莫名其妙跑到後面去」卻不知道
發生什麼事。這種狀況佇列上方會直接寫出來：「現在沒有人設暱稱，
所有人算同一位 —— 等於先到先唱」。

### 決定四：輪次要算「已經唱過的」

第一版只算佇列裡待唱的首數。單元測試當場抓到它壞在唱完之後：

  * 小明唱完自己那首，佇列裡剩小美的一首；
  * 小明再點一首 → 他「待唱 0 首」＝ 第 1 輪 → 排到小美前面。

而「小明連唱兩首、小美一首都還沒唱」正是這個功能要消滅的那件事。
所以輪次 = 今晚已經唱過的 + 佇列裡待唱的 + 1，「已經唱過的」在
`play_next()` 真的上台時才記一筆（與點唱排行同一個時機：排進佇列又被刪的不算，
被切歌的算 —— 麥克風確實輪到他手上了）。

### 決定五：「一場」只能有一個定義

「今晚唱了幾首」要有歸零的時候，否則昨晚唱了八首的那個暱稱，今晚第一首就被
排到所有人後面。門檻直接**共用整晚打包的 `recording_session_gap_hours`**，
而不是另外開一個設定 —— 兩個各自可調的話，使用者會看到「打包說這是同一場、
輪序說換了一場」這種自己打自己臉的畫面。

統計刻意**只活在記憶體裡**：佇列本來就不持久化，輪序沒有理由比佇列活得久。
重開機後佇列空空如也、輪序卻還記得「你已經唱了五首」，第一首歌就會被排到
莫名其妙的位置，而且沒有任何人看得出為什麼。

時間**倒退**（NTP 校時）時不算換場：差值是負的，本來就不會超過門檻。
寧可少切一場，也不要把同一場切成兩半 —— 這一條有測試釘著。

### 決定六：一定要講出「你被排到哪」

輪唱唯一會讓人愣一下的地方，就是他點的歌沒有出現在佇列最後面。
不講的話那看起來跟**壞掉**一模一樣，而使用者對「壞掉」的反應是再點一次 ——
然後佇列裡就多一首沒人要的歌。

所以 `POST /api/queue/add` 多回一個 `placement`（第幾位、第幾輪、插到幾首前面），
點歌台直接說出來：「🎤 已加入：🔁 排在第 2 位（小美的第 1 輪），插到 3 首前面」。
被插到的人也在同一個包廂裡，所以這句話刻意不含糊 —— 含糊只會變成
「怎麼換它先」。

`placement` 是**事後從現在的佇列讀出來**的，不是點歌當下算好的固定值：
兩支手機同時點歌時，先算好的位置在回應送出去之前就已經不對了。

## 2026-09-13 — 整晚打包下載（v1.11.0「Take the Night Home」）

**目標**：分享連結解決的是「一個人帶走自己那一首」。散場的時候還有另一句話，
而且是急著問的（大家已經在門口穿外套了）——**「今天晚上的通通給我一份」**。

一首一首按下載是二十三次另存新檔，而且存出來散在下載資料夾裡：檔名各自為政、
分不出誰唱的、更看不出今晚唱的順序。這一版把一整場包成一個 zip。

### 決定一：一場不是一天

第一版的切法是「照 `created_at` 的日期分組」。寫完自己試了一次就知道不能用：
**包廂的一場是「九點唱到凌晨兩點半」**。照日期切的話那一場會被剖成兩半，
而且後半 —— 真正唱到嗨、破音、有人開始點慢歌的那一段 —— 會被標成「隔天」。
使用者按「今天」拿到的是半場，而且是比較無聊的那半場。

改成照**空檔**切：相鄰兩次演唱相隔超過 6 小時就算換了一場。空檔法在另一個
方向也對 —— 同一天下午兩點與晚上九點各唱一輪（兩桌不同的客人），
日期法會把它們算成同一場。

門檻用「超過」而不是「大於等於」，而且時間戳壞掉的那一筆**不製造斷點**：
切下去只會多出一場只有一首的鬼場次，而使用者看到的是「今晚」突然變成三場。

場次的 key 用**開始時間**（`20260913-2105`）而不是流水號。流水號會因為前面的
場次被配額清掉而整批位移 —— 使用者剛剛複製的那個網址，隔天就指到別場去了。

畫面上跨午夜的那一場寫成 `今晚 21:05 – 隔天 02:30`。「隔天」那兩個字是後來才
補的：只寫 `21:05 – 02:30` 看起來像時間打反了。

### 決定二：邊包邊送，所以刻意沒有 Content-Length

第一版是「先在 `cache/temp/` 生一個 zip，再用 FileResponse 送出去」。
算一下就知道這個寫法自打嘴巴：一場 200 MB 的話，打包的瞬間磁碟要**另外**
吃掉 200 MB —— 而錄音配額這整套機制存在的理由，正是「這顆磁碟會被塞爆，
而塞爆之後失敗的是歌曲下載，沒有人會聯想到錄音」。打包下載不該是那個
把磁碟塞爆的人。

改成串流：`zipfile` 寫進一個只有 `write()` 與 `tell()`、**沒有** `seek()` 的
sink，generator 一邊讀錄音檔一邊把累積的位元組 yield 出去。沒有 `seek` 是關鍵 ——
`zipfile` 發現回頭寫不了，就會改用 data descriptor 把 CRC 與大小寫在檔案資料
**後面**，而不是先留白、事後回頭補。已經送出去的位元組是改不了的。

接下來是一個想了很久才決定「不做」的東西：**Content-Length**。
ZIP_STORED 的長度其實是算得出來的（本地標頭 + 檔名 + 資料 + 中央目錄…），
但那個數字只在「打包過程中沒有任何一筆消失」時才成立。中間被配額擠掉一筆，
實際送出的位元組就對不上宣告的長度，而瀏覽器對這種情況的處理是把整包
判定為**下載失敗**。沒有進度條百分比只是不方便；下載到 99% 被判定失敗，
使用者會重按第二次、第三次。所以不宣告，改成在清單端點先報一個預估大小，
畫面上寫「整包大約 186 MB」。

### 決定三：不壓縮

錄音是 Opus / AAC —— 已經壓縮過的資料。再 deflate 一次省下來的是零點幾個
百分點，換來的是把一整晚重壓一遍的 CPU，而那顆 CPU 同時在放歌、算音準、
跑下一首的人聲分離。唱歌永遠優先，所以音檔一律 stored；只有最後那份
純文字的 `曲目.txt` 用 deflate（省七成，而它只有幾 KB）。

### 決定四：檔名是給別的作業系統看的

zip 解開的地方多半不是這台機器：Windows 的下載資料夾、車上的 USB、
傳給朋友的手機。所以檔名這一段花的力氣比想像中多：

  * **序號與時間在最前面**（`01 21-05 …`）。車機、隨身碟播放器與檔案總管
    都是照檔名排序的 —— 沒有序號的話，「今晚唱的順序」在解開之後就永遠
    找不回來了，一整晚會變成照歌名筆劃排。
  * 時間寫成 `21-05` 不是 `21:05`：冒號在 Windows 是非法字元。
  * 結尾的點與空白要砍掉 —— Windows 會自己吃掉，然後曲目清單上寫的檔名
    就跟資料夾裡的對不起來。
  * 長度照 **UTF-8 位元組**裁，不照字數：中文一個字 3 bytes，而檔名上限
    是位元組數。照字數裁的話，40 個字的歌名會裁出一個存不進去的名字。
  * 同名要讓開成 `(2)`，而且比對要**不分大小寫**（Windows 與 macOS 的檔案
    系統預設不分）—— 同一首唱兩次很常見，覆蓋掉的是一次真的演唱。

反而有一件事查過之後決定**不做**：Windows 的保留裝置名稱（`CON`、`NUL`、
`COM1`）。那些名字只有在「整個主檔名就是它」時才是保留的，而每個檔名前面
一定掛著序號與時間，所以一首叫《AUX》的歌出來是 `03 22-10 AUX.webm`。
寫了也永遠不會執行到的分支，不如寫一行註解說明為什麼不需要。

### 決定五：曲目清單放最後，因為它要講實話

`曲目.txt` 是打包**完**才生出來的，而且刻意是 zip 的最後一個項目。
理由是打包的當下某一首有可能剛好被配額擠掉（或有人手動刪了檔）：

  * 先寫清單的話，清單會列出一首資料夾裡沒有的歌 —— 使用者的結論是
    「解壓縮壞掉了」；
  * 最後寫的話，它講的就是實際包進去的東西，連「以下這幾首沒有包進來」
    都寫得出來。

同理，打包途中開不起來的那一筆是**跳過並記一筆**，不是整包放棄：
少一首加一行說明，比一個下載到 80% 斷掉的檔案有用得多。
另外，檔案是**先開起來再讀**的 —— POSIX 上開著的檔案描述子不會因為
別人 unlink 就消失，所以打包途中被配額清掉也不會讀到一半斷掉。

### 決定六：同時只打一包，而且租約要有期限

一包是幾百 MB，而那條網路正是舞台端串影片與 WebSocket 在走的。
所以整台機器同時只打一包，第二個人拿到 429 與一句「正在打包另一份」。

寫到一半發現一個洞：位子是在 generator 的 `finally` 裡還的，
但 generator **有可能從來沒被跑過** —— 使用者按了下載又立刻關掉分頁，
連線在第一個位元組之前就斷了。那種情況下沒有任何程式碼會執行到 `finally`，
這個位子就永遠空不出來，而症狀是「整晚打包從此再也按不動」。
所以鎖改成有期限的租約：超過 15 分鐘沒還，下一個人直接接手。

### 這一版刻意不做的兩件事

1. **整包轉 MP3**。一整晚三十首要轉三十次，等於拿正在放歌的 CPU 去換檔案 ——
   而上一版做 MP3 時的整個論證就是「用到才轉」。要 MP3 的話按那一首自己的
   🎧 MP3（`曲目.txt` 裡也寫了這句話）。
2. **整晚打包掛在分享 token 底下**。一個 zip 是整場所有人的聲音，
   那不是掃 QR 的人該拿得到的東西 —— 這條路只在點歌台（包廂內網）出得來。

### 測試（後端 471 條 + 前端 249 條，全綠）

  門檻剛好不切、壞掉的時間戳不切、檔名清洗與不分大小寫的去重、
  UTF-8 位元組裁切、stored/deflate 的分工、串流真的分多塊吐、
  打包途中檔案不見了要跳過並寫進清單、1970 年的時間戳不會讓 zip 爆掉、

## 2026-09-13 — 錄音轉 MP3（v1.10.0「Plays Anywhere」）

**目標**：上一版讓人把那一次演唱帶走，這一版讓它**在帶去的地方打得開**。

錄音是瀏覽器的 MediaRecorder 錄的，容器由瀏覽器決定（Chrome/Firefox 是
webm/Opus、Safari 是 mp4/AAC）。在包廂裡用同一台瀏覽器播完全沒問題 ——
但錄音真正的去處是別的地方：車上的 USB 播放清單、長輩手上的舊手機、
傳到群組裡讓對方直接點開。那些地方多半只認 MP3。

分享連結解決了「怎麼傳給我」，這一版解決的是**傳過去之後打不打得開**。

### 決定一：用到才轉，而且轉出來的東西是可以丟的

第一個念頭是「錄完就轉一份 MP3 放著」。算一下就知道不行：一個晚上錄三十首，
會被帶走的大概三首，其餘二十七次轉檔是拿**正在放歌、算音準、跑人聲分離**
的那顆 CPU 去換沒有人要的檔案。所以改成按下去才轉，轉好的留著當快取。

接下來是真正棘手的一題：**這份 MP3 算誰的空間？**

最直覺的寫法是「算進錄音配額」—— 然後就會發生這件事：有人按了一下下載，
包廂裡最舊的那一次演唱被擠掉了。使用者完全無法把這兩件事連起來，
而且**演唱刪掉就沒有，MP3 再轉一次就有**。兩邊的可挽回性根本不對等。

所以 MP3 快取是獨立的一塊：

| | 錄音 | MP3 快取 |
|---|---|---|
| 放在哪 | `cache/recordings/` | `cache/recordings/mp3/` |
| 上限 | 設定頁（預設 50 首 / 512 MB） | 錄音配額的 1/4，**額外**佔用 |
| 滿了刪誰 | 最舊、沒有標記保留的 | **最久沒用到**的那一份 |
| 刪掉的後果 | 那一次沒了 | 下次按 MP3 重轉一份 |

「額外佔用」等於在說磁碟總量最多是錄音配額的 1.25 倍 —— 這件事不能藏，
所以設定頁的說明與清單上的那一行都把數字寫出來
（`MP3 快取 3 首・6.0 MB / 128.0 MB（另外佔的空間，刪掉可以重轉）`）。

### 決定二：LRU 用遞增序號，不用時間戳

第一版拿 `mp3_used_at`（ISO 字串，秒解析度）排 LRU，單元測試當場抓到：
同一秒內接連轉好的四份，`min()` 比的是同一個字串，誰被刪掉變成看字典順序。

寫成毫秒只是把問題變小。真正的問題有兩個，而且第二個更糟：

  * 同一秒內連按兩次在真實使用下很常見（一桌人同時掃 QR）；
  * **時間會倒退** —— NTP 校時、有人改系統時間。剛用過的那一份會突然
    變成「最久沒碰的」而在下一次清理時第一個被刪。

改成單調遞增的序號（`mp3_seq`），兩個問題一起沒有。序號跟著索引一起存，
重開機時接在最大值之後 —— 重設成 0 的話，開機後新轉好的那一份會跟舊檔案
並列最小值，快取一滿第一個被刪的就是它（有測試釘著這條）。

### 決定三：ffmpeg 不在，就把按鈕收起來

ffmpeg 是本專案的硬需求（下載與人聲分離都要），但「硬需求」不等於「一定在」：
有人是手動裝的，有人的 ffmpeg 是精簡版**沒有 libmp3lame**（為了授權把 lame
拆出去的發行版是真的存在的，失敗的樣子是轉了兩秒吐一個看不懂的錯）。

所以先探測再決定畫面：問 `ffmpeg -encoders`，看叫不叫得動、有沒有 libmp3lame。
兩種不能要分開講，因為使用者要做的事完全不同 ——

  * `disabled`：設定頁把它關掉了 → 去打開；
  * `not_installed` / `no_lame`：機器上沒有（完整的）ffmpeg → 去裝一個。

分享頁上更乾脆：轉不了就連按鈕都不長出來。拿到連結的人不是這台機器的
管理員，給他一顆按下去會壞的按鈕沒有意義。裝好之後按「重新偵測」即可
（探測結果成功會一直記著，失敗只記 60 秒 —— 不該為了這個重開伺服器）。

### 真的跑一次 ffmpeg 才發現的那個 bug

單元測試全綠、假的 ffmpeg 演得很好，然後把真的 ffmpeg 裝起來跑一次：

```
Error initializing the muxer for .../xxx.mp3.part: Invalid argument
```

**ffmpeg 是看副檔名決定輸出格式的**，而為了原子換檔（轉一半失敗不可以留下
一個「看起來是 MP3、播到一半斷掉」的檔案），我們寫的是 `xxx.mp3.part`。
它認不出 `.part` 是什麼格式，直接收場。加上 `-f mp3` 明講就好。

這一條假的 ffmpeg 永遠測不到 —— 假的那支不在乎輸出叫什麼名字。
所以現在有一條測試盯著指令裡的 `-f mp3`，並且在註解裡寫清楚為什麼。

### 兩道關卡（同一筆只轉一次、整台機器只轉一個）

  * **同一筆**：使用者按了沒反應（其實在轉）於是又按一次，沒有這道關卡的話
    同一個目標檔會有兩個 ffmpeg 同時在寫。排在後面的那一個進來時檔案通常
    已經好了，直接用，不重轉。
  * **整台機器**：一桌人同時掃 QR 下載，五個 ffmpeg 一起跑會把 CPU 吃光 ——
    而那顆 CPU 正在放歌。唱歌永遠比轉檔重要，寧可讓第五個人多等十秒。

排不進去時回一句「現在忙，稍候再試」而不是一直等：一個轉不完的請求掛在那裡，
使用者看到的是轉圈圈的瀏覽器，那比一句話更糟。

（真的開四條 curl 同時打同一筆驗證過：四個都拿到 200、同樣的檔案大小，
伺服器 log 裡只有一行「轉檔完成」。）

### 兩個 async 細節

  * 轉檔是 `subprocess.run`，**會阻塞**。直接寫在 async 端點裡的話，那十幾秒
    整台伺服器的 WebSocket 都會停住 —— 症狀是「有人按了下載，舞台上的歌詞
    就卡住了」。所以走 `asyncio.to_thread`。
  * 前端不用 `<a download>` 直接指過去：第一次按的時候伺服器真的要跑一次
    ffmpeg，`<a>` 在那幾秒裡看起來完全沒反應，使用者的下一個動作一定是
    再按一次。改成 fetch + blob，按鈕當場變成「⏳ 轉檔中…」並鎖起來。
    檔名從 `Content-Disposition` 挖（RFC 5987 的 `filename*` 優先，中文歌名
    走的是那一條），挖不到就退成 `<id>.mp3`。

### 順手修掉的一件事

分享連結的「下載幾次就失效」原本是在動作**開始**時計次。轉檔失敗的話，
等於這個連結被一個沒有拿到檔案的動作燒掉了。計次移到真的拿到檔案之後。

  失敗／逾時／空輸出不留 `.part`、兩道關卡的並行行為。

  「MP3 永遠不擠掉錄音」、刪除與配額清理帶走 MP3、孤兒 MP3 清理、

## 2026-09-13 — 錄音分享（v1.9.0「Take It Home」）

**目標**：上一版把每一次演唱錄了下來，但錄音只活在包廂那台機器上。
唱完之後的下一句話一定是**「傳給我」**—— 商用點歌機與線上 K 歌 App 都有這一步：
產一個連結或 QR，當事人自己把那一次帶走。沒有這一步，那一次遲早會被配額擠掉。

### 決定一：「一次性連結」是個會害到使用者的名字

原本的路線圖寫的是「一次性連結」。實作到一半才發現，如果照字面做
（第一個請求就把 token 燒掉），**壞掉的是當事人自己的播放**：

播一個音檔不是一次 HTTP 請求。`<audio>` 拖進度條會發 Range 請求、
Safari 為了拿 metadata 會對同一個檔案再發一次、手機切到背景再回前景也可能重連。
第一個請求燒掉連結的話，使用者看到的是「歌播到一半死掉，而且重整也救不回來」。

所以「一次性」在這裡重新定義成**時效性**：

  * 預設 24 小時自動失效（時間到是真的打不開，不是畫面上不顯示）；
  * 隨時可以撤銷（送錯人才是按撤銷的理由，所以按下去要立刻生效）；
  * 可以另外設「下載幾次就失效」，但**只算明確的下載**（按下載鈕，`download=1`），
    播放時的那幾個請求一律不算。

順帶決定了一件事：**沒有「永不過期」這個選項**。錄到的是包廂裡所有人的聲音，
一個永遠有效、不需要登入的公開連結是事後想收也收不回來的東西。
上限訂 30 天 —— 少一個選項換這個，划算。

### 決定二：失效要分四種原因講

第一版寫完只有一句「這個連結無效」。自己拿手機測的時候立刻發現問題：
**拿到連結的人不知道下一步該做什麼**。現在分四種：

| 原因 | 畫面上的話 | 他該做的事 |
|---|---|---|
| `not_found` | 這個分享連結不存在（可能是網址少了幾個字） | 檢查網址 |
| `expired` | 已經過期，請原點歌的人重新分享 | 去要一個新的 |
| `revoked` | 已經被撤銷 | 去問對方為什麼 |
| `gone` | 這一次的錄音已經不在那台機器上了 | 沒救了，別再掃了 |

最後一種是真正容易漏的：錄音被**配額無聲擠掉**時沒有人按過任何按鈕。
所以 `prune()` 對帳時不是把那些連結整筆刪掉（刪掉的話點進去會變成
「連結不存在」＝ 被理解成網址打錯，於是他會一直重掃），而是標成
「錄音不在了」留七天，讓他看得到那句話。

### 決定三：分享頁是獨立的一頁，而且不嵌任何資料

`/share/<token>` 回的是**靜態 HTML**，資料由頁面自己打 `/api/share/<token>` 拿。
兩個理由：

  1. **歌名是從 YouTube 抓回來的字串**。伺服器端把它拼進 HTML 就等於把
     別人取的標題當程式碼跑；交給前端用 `textContent` 塞，這個洞不存在。
  2. 分享頁幾乎一定是在手機上、用行動網路打開的。它不載入點歌台那 1500 行
     後台樣式（`share.css` 只有一張卡片要的東西）。

公開端點只交出這一筆看得到的欄位：`song_id` 之類的內部識別碼、檔案路徑、
其他錄音的存在與否都不從那裡出去。

### 踩到的兩個坑

**分享索引差一點放進錄音資料夾。** `RecordingLibrary._reconcile()` 會把錄音
資料夾裡「不在索引上」的檔案當成斷電留下的孤兒檔**刪掉** —— `shares.json`
放進去會在下一次開機時無聲消失，所有已經發出去的連結一起死。
改放 `cache/recording_shares.json`。

**彈窗用錯 class 名。** 分享視窗第一版寫 `classList.add("active")`，
但這個專案的彈窗慣例是 `open`：單元測試全綠、`node --check` 全過，
真的開瀏覽器按下去才發現「什麼都沒有發生」。跟 v1.4.0 那次
（`SILENCE_DB` 重複宣告）是同一類問題 —— 靜態檢查看不到的接線錯誤，
所以這一版照樣用 Playwright 真的把三個畫面跑過一遍（分享頁、失效畫面、
點歌台的分享視窗），確認 QR 真的畫出來、連結真的長對。

### 這一版的測試

後端 394 條（新增 25 條 `test_share_links.py` ＋ 13 條分享端點的 API 測試）、
前端 228 條（新增 13 條 `share-view.test.js`）全綠。
`script-scope.test.js` 的守備範圍加入 `share.html`。

### 下一步

路線圖只剩兩項選配：錄音轉檔成 mp3（webm/Opus 在部分車機與舊播放器打不開 ——
而「帶回家聽」正是這一版做出來的情境，所以它的優先度被這一版推上去了），
以及多包廂（一台伺服器帶多組舞台與佇列）。

## 2026-09-13 — 錄唱回放（v1.8.0「Second Listen」）

**目標**：商用 KTV 與線上 K 歌 App（全民K歌、唱吧）都有、這套一直沒有的那一塊 ——
**把剛剛唱的那一次留下來**。分數說的是「唱得好不好」，錄音說的是
「唱起來是什麼樣子」，而後者才是隔天還會被打開來聽的東西。

### 決定一：錄音要接在音訊圖的哪一點

最省事的做法是接在 `masterGain` 之後（那裡已經是最終的混音）。
接上去才想清楚 `masterGain` 是**喇叭音量**：有人接電話把喇叭轉小，
錄下來的就跟著變小；轉到靜音，那一首就沒了。而錄音要的是
「這首歌唱成什麼樣子」，跟包廂當下開多大聲是兩件事。

所以音訊圖多了一層 `mixBus`：伴奏＋導唱＋麥克風＋效果＋罐頭音效全部先匯到
這裡，再進 `masterGain` → `destination`。錄音接 `mixBus`。改動本身只是把
六處 `connect(this.masterGain)` 換成 `connect(this.mixBus)`，但它讓
「喇叭音量」與「這次演唱的混音」從此是兩個東西。

`MediaStreamDestination` 只建一次並留著重複用。每首歌建一個新的會在
AudioContext 裡累積節點（只要還連著就不會被回收），唱一整晚之後
`mixBus` 身上會掛著幾十個沒人讀的目的節點，每一個都在跑重採樣。

### 決定二：「唱了多久」不是「錄了多久」

哪些錄音該留？第一版用「錄了多久」，結果是前奏放到一半被切歌的那些
全部留了下來 —— 它們一樣佔配額，而且會把真正想找的那一次擠掉。

改成用**真的有人在唱**的累計時間（沿用評分心跳每一幀的判定，
對唱時兩支麥克風有一支在唱就算）。這裡刻意累計**時間**而不是幀數：
評分引擎的 `sangFrames` 是每個 render frame 加一，同一首歌在 30fps 的機器
與 120fps 的螢幕上會差到四倍 —— 一邊留下來、一邊被當成沒人唱丟掉。
單幀差距夾在 100ms，否則分頁被切到背景（rAF 降到每秒一次）那一大段空白
會被整個算成「在唱」。

### 決定三：配額滿了要刪誰

錄音跟歌曲快取共用同一顆磁碟。沒有上限的話，幾個月後失敗的會是
「歌曲下載不下來」，而沒有人會聯想到是錄音吃光的。所以有兩道上限
（預設 50 首 / 512 MB），超過就從最舊的開始刪。

但「最舊的先刪」會刪掉唱得最好的那一次 —— 所以每一筆可以標記保留（📌），
保留的不會被自動清掉，「清空」也預設留著它們。

這裡踩到一個坑，而且是**單元測試先抓到的**：舊的全被標記保留、配額又滿了時，
「先存進去再跑一輪清理」的寫法會發現唯一可刪的就是剛存進來的那一筆 ——
回報存檔成功，使用者回頭卻找不到那一次。清理時要把「剛存進來的這一筆」
排除在候選之外，發現刪不動就當場拒絕並說明原因。

配額提醒設在九成而不是滿：滿了才講已經來不及，下一首唱完就有一筆舊的
被刪掉了，而那一筆很可能就是想留的。

### 在真的瀏覽器裡跑一次（沿用上一版的教訓）

v1.7.0 是在真的開瀏覽器時才發現舞台頁面整支不執行的，所以這一版同樣用
Playwright 開了舞台與點歌台，實際錄一段、上傳、再讀回來播。三件事因此被抓到：

1. 舞台的每一支腳本都確實執行（新加的兩支沒有跟誰撞到全域名稱）。
2. `pause()` 之後再 `start()` 是**接回去**而不是開新的一段，長度也正確
   扣掉暫停的時間（量到 2001ms，實際牆上時鐘 2.4 秒）。
3. **錄音的進度條拖不動**：`audio.duration` 讀出來是 `Infinity`。

第三件是這一版最值得記的。`MediaRecorder` 產生的 webm 標頭裡**沒有 Duration**
—— 它是串流容器，開始錄的時候還不知道會錄多久。後果是想重聽副歌只能從頭放。
解法是第一次播放時先 seek 到一個不可能的時間點，瀏覽器為了回答「到底有多長」
會把檔案掃過一遍，`durationchange` 就帶著真正的長度回來，這時再跳回 0。
只做一次，而且只在真的要播的時候做 —— 一開分頁就掃五十個檔案，
使用者只會看到一串轉圈圈卻不知道在等什麼。

清單上顯示的長度則完全不依賴容器：那是錄的時候用時鐘量好、跟著上傳存起來的。

### 隱私：這是唯一不開就完全不動作的功能

錄音錄到的是包廂裡所有人的聲音。預設打開等於替使用者決定要錄他們講的話，
所以 `recording_enabled` 預設是 `false`，而且：

* 舞台端錄著的時候左上角常駐紅點「錄音中」（呼吸週期 1.4 秒，
  遠低於光敏性癲癇的 3Hz 安全線）；
* 設定頁把開關關掉的當下就停手並丟掉手上那一段，不是等這首唱完；
* 歌暫停時錄音跟著暫停 —— 那時候包廂在講話，沒有人以為自己在被錄音。

### 上傳為什麼不用 multipart

要送的只有「一個檔案 + 幾個欄位」。走 multipart 得多裝一個
`python-multipart`（CI 的依賴集是刻意壓到最小的），所以音檔直接當 raw body、
metadata 走 query string。後端在讀 body 之前先看 `Content-Length` ——
Starlette 的 `request.body()` 會把整包讀進記憶體，等讀完才發現太大
就已經吃掉那些記憶體了。

### 安全性

錄音 id 由伺服器產生（`20260913-213045-a1b2c3`）並用嚴格的正規表示式檢查，
不接受外面給的檔名；路徑一律從索引裡的檔名組出來，組完再確認它還在錄音
資料夾底下。`/api/recordings/{id}/audio` 是直接把檔案送出去的端點，
id 若能塞進 `../` 就等於把整台機器的檔案系統開放出去。
測試裡把各種形狀的 id（`../../etc/passwd`、URL 編碼、`index.json`、大寫）
都釘了一遍。

### 測試（後端 357 條 + 前端 213 條，全綠）

- 新增 `tests/test_recordings.py`（24 條）：配額驅逐順序、保留不被刪、
  索引與資料夾對帳（手動刪檔留下的空項目、斷電留下的孤兒檔）、
  id 安全性、mime → 副檔名。

  raw body 上傳、路徑穿越回 404、設定頁的配額真的會被端點讀到。

  都不支援 / `isTypeSupported` 丟例外）、「要不要留」的每一道門與那句說明、
  配額摘要與提醒的門檻。

1. 錄音分享：產生一次性連結或 QR，讓當事人自己把那一次帶走
   （現在只能在包廂的點歌台下載）。

## 2026-09-12 — 跨場次段落趨勢（v1.7.0「Home Turf」）

**目標**：ROADMAP「後續想做的」剩下的那一項「跨場次的主場統計（這個人在這首歌
一向強在哪一段）」。段落評分（v0.9）唱完會說「副歌 2 只有 31%」，但那句話
**每次都不一樣** —— 今天掉的可能只是沒接上氣。能拿來練歌的是另一句：
「這首歌的副歌 2 你**一向**掉 13 個百分點」。

### 難處一：平均起來算出的是「嗓子好不好」，不是「哪一段弱」

第一版的想法很直覺：把每次的段落命中率平均起來，最低的那一段就是弱點。
拿種進去的假資料跑就發現這個做法回答的是另一個問題。

感冒那天每一段都掉 15 個百分點，平均下來**每一段看起來都是弱點**；
狀況好的那天每一段都是強項。整體嗓音狀況會把所有段落一起平移，
而那個平移量比段落之間的真實差異大得多。

所以每一場**先減去那一場自己的平均**再累積 —— 比的是一場演唱的「形狀」
而不是「高度」。測試 `test_bad_voice_day_does_not_make_every_section_a_weakness`
就是釘這件事：第三場整體掉 30 個百分點但形狀不變，結論必須完全一樣。

減平均時刻意**不照音符數加權**：加權的話最長的那一段（通常就是副歌）
會主導基準線，等於拿副歌跟副歌自己比，永遠顯示不出副歌是弱點。

### 難處二：平均值分不出「三次都掉一點」與「一次崩掉」

這兩件事的平均偏差可以一模一樣，但該講的話完全不同：
前者是「這一段要練」，後者是「那天狀況不好」。把後者講成「你一向掉副歌」
是在誣賴人，而且使用者會知道那不是真的 —— 然後整塊功能就不可信了。

所以除了平均偏差還要求**方向一致性**：至少三分之二的場次同一個方向。
偏差恰好為 0 的場次兩邊都不算（它沒有表態）。加上「至少三場」與
「幅度至少 5 個百分點」（沿用單場段落評分的 `MIN_SECTION_SPREAD`，
兩邊對「值得講出來的差距」是同一個手感），一共三道門。

### 難處三：「副歌 2」在重新處理過的歌裡不是同一段

歌曲重新處理（換模型、歌詞來源變了）之後 `chorus_detector` 切出來的曲式
可能多一段主歌，後面所有編號就往後挪一位。那時候把「副歌 2」跨版本相加，
等於把兩段不同的歌混成一筆統計 —— 而且**看不出來**，數字一樣很漂亮。

解法是給每一場存一份**曲式指紋**（可評分段落的標籤依序排成一列），
只比對指紋相同的場次。以**最新一場**的曲式為準，不是用舊曲式的多數決：
否則重新處理之後新資料永遠進不來，趨勢就凍在舊版本上。

### 順手撿到的重傷：舞台頁面從 v1.4.0 起就是壞的

為了看情境背景那一版做過的事（真的開瀏覽器把畫面截下來看），這次也用
Playwright 開了舞台頁面。Console 第一行是：

```
Identifier 'SILENCE_DB' has already been declared
DuetScorer is not defined
```

`mic-agc.js` 與 `duet-scorer.js` 都在最外層宣告了 `const SILENCE_DB`
（還有值不一樣的 `ENV_RISE_TAU` / `ENV_FALL_TAU`）。舞台的 JS 是用 `<script>`
一支一支載進**同一個全域作用域**的，重複宣告 `const` 會讓後載入的
`duet-scorer.js` 在**解析階段**就丟 SyntaxError 而整支不執行；接著
`player.js` 第 118 行 `new DuetScorer(...)` 炸掉 —— **從那一行以後的舞台程式
全部沒有執行**。也就是對唱模式上線（v1.4.0）那一刻起，舞台頁面就是壞的。

最值得記下來的是「為什麼三道檢查全都是綠的」：

| 檢查 | 為什麼沒抓到 |
|------|-------------|
| `node --check` | 一次只看一支檔案，每一支的語法各自都是對的 |
| `node --test` | `require()` 給每支模組獨立作用域，名字不會相撞 |
| 後端 pytest | 根本不碰前端 |

所以補了 `frontend/tests/script-scope.test.js`：照 HTML 實際載入的 `<script>`
清單，檢查同一頁的檔案之間沒有重複的最外層 `const`/`class`。它另外還釘住
一件事 —— `clamp`／`approach`／`dbFromRms`／`round3` 這幾支小工具在好幾個模組
裡各寫了一份。重複的 `function` 宣告**不會**丟錯，但後載入的那一份會默默
覆蓋前面的，所以瀏覽器裡大家其實都在用最後載入的那一份。目前每一份都
一字不差（確認過），這個測試不要求去重（為了幾行工具硬做一支共用模組反而
綁死載入順序），而是釘住「一樣」這個前提：哪天有人只改其中一份就會叫。
故意把衝突加回去跑過一次，確認測試真的會紅。

### 畫法：中線是自己的平均

長條圖沿用段落對決的**對拉**畫法，但中線的意義不同 ——
對決的中線是「兩個人之間」，趨勢的中線是「**這個人自己的平均**」，
往右是主場（青）、往左是弱點（桃紅）。畫絕對命中率的話看到的是
這首歌哪一段難唱，不是這個人哪一段弱，而後者才是要練的東西。

沒被點名的段落（幅度不夠或方向不一致）畫淡色而不是藏起來：
那一段是「還沒有結論」，不是「剛好等於平均」。

一句話上的小事但值得記：第一版寫成「一向低 **+13** 個百分點」——
方向已經由「低」講完了，正負號是第二次講，要讀兩次才懂。句子裡拿掉符號，
長條圖上留著（那裡沒有句子，符號就是方向）。另外 `Math.round` 往 +∞ 捨，
所以 −0.4 個百分點會顯示成「+0」：一個往下偏的段落顯示成正的，改成「±0」。

### 測試（後端 325 條 + 前端 192 條，全綠）

- `tests/test_api.py` 加 3 條：兩支新端點與 `trends` 不被當成 song_id。
- 新增 `frontend/tests/trend-view.test.js`（11 條）與
  `frontend/tests/script-scope.test.js`（5 條）。

## 2026-09-11 — 情境背景（v1.6.0「Never Black」）

**目標**：ROADMAP「後續想做的 → 演唱體驗」剩下的那一項「情境背景
（沒抓到 MV 時的動態視覺）」。商用點歌機（錢櫃的情境畫面、金嗓的背景影片、
JOYSOUND 的映像）都有這一套，而這個系統目前碰到沒有 MV 的歌就是**一片黑**。

黑畫面不只是「比較樸素」。在包廂裡它傳達的訊息是「**這首歌壞掉了**」——
使用者不知道是沒抓到 MV 還是機器當掉，而且整個房間只剩字幕在發光。

### 難處一：不是「有沒有 MV」，是「有沒有畫面」

原本以為這一項的判斷條件就一個：`metadata.video_path` 是不是 null。
實際去看快取才發現真正常見的情況是另一種 ——
YouTube 上大量的「音樂版／歌詞版」上傳其實是**一張靜態圖配四分鐘音訊**。
檔案真的下載到了，`video_path` 有值，所以「這首有沒有 MV」會回答「有」，
舞台就放一張凍結的畫面放整首。那正是情境背景要解決的情況，卻完全繞過判斷。

所以要真的去看畫面：每 1.2 秒把 `<video>` 縮成 32×18 畫進離螢幕 canvas，
算跟上一張的平均亮度差。門檻 2.0（0~255 的刻度）——
真正的靜止圖只有編碼雜訊（0~1），再慢的實拍畫面也遠超過這個值。
在真的瀏覽器裡用 MediaRecorder 現場錄了兩段影片驗證：

| 影片 | 取樣數 | 最大差值 | 判定 |
|------|--------|---------|------|
| 會動的 | 1 | 10.21 | moving（一筆就結案，MV 留著） |
| 整首同一張圖 | 6 | 0.00 | still（情境背景接手） |

門檻兩邊都留了五倍以上的餘裕，這個判定不需要調參。

三個實作上的陷阱，每一個都會讓功能悄悄出錯：

- **暫停中不能取樣**。暫停的畫面永遠跟上一張一模一樣，差值恆為 0 ——
  按個暫停回來就會發現 MV 被換成情境背景了，而且沒有任何錯誤訊息。
- **觀察窗要用牆上時鐘，不能用影片的 `currentTime`**。短片配長歌時
  `<video loop>` 會一直繞回 0，用它算「觀察了幾秒」會得到負數，判定永遠不成立。
  第一版就是這樣寫的，在瀏覽器裡跑才發現（單元測試餵的是遞增的時間戳，測不到）。
- **兩個方向都要閂鎖**。判定過就不再改：唱到一半背景在 MV 與情境之間來回切，
  比兩種都不完美更糟。

還沒判定完的那五秒先放 MV —— 還沒有證據說它是張圖之前，把真的 MV 換掉才是錯的。
判定時間（1.2 秒 × 4 筆 ≈ 5 秒）剛好落在片頭卡還亮著的時間內，切換看不太到。

### 難處二：三道「壓一點點」疊成一片全黑

背景不能跟字幕搶，這件事沒有爭議。實作時亮度被壓了三道：
主題自己的 `baseLuma`、設定頁的亮度上限、以及畫面下半字幕區的 vignette。
每一道單看都只是「壓一點點」。

第一版 render 出來是**全黑**。三道乘起來大約是 0.33 × 0.6 × 0.45，
整張圖只剩下極微弱的色偏 —— 而這件事在程式碼裡完全看不出來，
每個數字都很合理。是真的用 Playwright 把五個主題畫出來看了才發現。

修的方式不是把某個數字調大，是把責任分清楚：

- vignette 那一層的工作是「把任何一支亂七八糟的 MV 壓到字幕看得清楚」。
  情境背景的亮度是我們自己控制的（而且已經被限速器與上限壓過兩道），
  所以情境背景出場時 vignette 自動放輕（`.ambient-canvas.on ~ .stage-vignette`，
  純 CSS 兄弟選擇器，不用 JS 再去切 class）。字幕所在的下緣那一道不放。
- 亮度上限的預設從 0.6 改成 0.85，下限從 0.1 改成 0.3 ——
  滑到 0.1 等於背景被關掉，但模式還顯示「開著」，畫面說的跟看到的就對不上。

順帶：星空主題第一版是一片灰霧。畫布是半解析度、柔邊靠 CSS 的 `blur(6px)`，
漸層類的主題很吃這一套，星點卻被糊掉了。改成依 `data-motion` 分開設柔邊
（星空 2.5px），並在主題資料加 `density` 倍率（星空 ×1.9、燭火 ×0.75）。
這兩個值是看著圖調的，不是算出來的。

### 難處三：背景不准閃

背景跟著音樂動，最直覺的做法是「鼓點一來就把整個畫面打亮」。那是不能做的：
舞台螢幕在暗房間裡佔滿整面牆，高對比的亮度變化**一秒三次以上**就是
光敏性癲癇的誘發條件（一般安全建議是 3 Hz 以下）。

所以亮度與動態被拆成兩件事：

- 亮度走限速器，每秒最多變 `MAX_LUMA_SLEW = 0.45`，而且擺幅本來就小
  （每個主題 ≤ 0.25）。最壞情況（每一幀在全靜音與滿能量之間跳）也被測試釘住。
- 鼓點只推 `beatPulse`（粒子噴一下、波形推一下、線條粗一點），完全不碰亮度。

鼓點偵測本身還踩到一個：移動平均從 0 開始爬的那一秒，「比平均大聲」是必然成立的，
所以前奏一進來會連噴好幾下。修法是第一幀直接把平均值設成當下的值，再加 0.35 秒暖機。

### 成本：背景是最低優先

舞台那條 `requestAnimationFrame` 上還有逐字走字、音高偵測與評分。
那些掉幀所有人都會發現，背景掉幀沒有人會發現 —— 所以背景讓路：
30fps 上限、半解析度畫布（柔邊交給 GPU 合成的 CSS blur，比在 canvas 裡疊十層漸層便宜）、
`document.hidden` 就完全不畫、每幀量自己花多少毫秒，超過 8ms 就降級
（升回去要連續 90 幀都在 4ms 以下，遲滯免得在邊界跳）。

頻譜接的是 `normGain`（伴奏＋導唱），**不含麥克風與罐頭音效**：
背景跟著人講話與掌聲抖動，看起來不是「有反應」而是「壞了」。
另外 analyser 的位元組是 dB 對映，音樂幾乎永遠落在 0.35~0.85 之間，
直接拿 `bytes/255` 當能量會讓背景整首停在高檔，所以把那一段重新攤成 0~1。

### 同一首歌永遠是同一個背景

「自動」主題用 FNV 雜湊從 `song_id` 挑，不是隨機。
隨機看起來比較豐富，在包廂裡卻是反效果：同一首歌昨天是星空今天是霓虹，
第一個反應是「機器怎麼怪怪的」。背景是這首歌的一部分，它要是穩定的。

### 其他

- 佇列項目多了 `has_video`（後端從 metadata 讀）。沒有它的話舞台只能先載
  `original_video.mp4`、等 404 才知道沒有 MV，那一秒的黑畫面剛好落在第一句歌詞上。
  還沒處理過的歌是 `null`（不知道）而不是 `false` —— 當成沒有的話，
  每首有 MV 的歌都會先閃一下情境背景。
- 待機（沒有歌）時一樣走情境背景，只是能量固定在低檔。
- 主題選項在後端 SPEC 與前端 `THEMES` 各有一份，用一條測試（讀 JS 檔比對）
  把兩邊釘在一起：對不上的話設定頁會列出一個舞台端畫不出來的主題，
  選了之後背景不會變，而且完全沒有錯誤訊息。

## 2026-09-10 — 對唱的段落對決（v1.5.0「Home Turf」）

**目標**：上一輪自己留下的第 3 項「對唱的段落比較（哪一段誰比較強）」。
資料早就在兩邊的 `sectionScorer` 裡（兩位各有一份完整的段落成績），
所以這一輪的工作不是計算，是**決定哪些段落可以拿來比、以及怎麼畫**。

### 這一項真正的難處：分工不是勝負

一開始想的做法是「兩邊的段落命中率直接並排，誰高誰贏」。
把資料倒出來一看就知道這樣會出事：真正的對唱歌曲（《屋頂》那一類）
本來就是**主歌 1 你唱、主歌 2 我唱、副歌一起唱**。
B 沒唱主歌 1，他在那一段的 `note_frames` 是 0、命中率是 0%，
畫面就會宣布「A 以 68% 完勝 B 的 0%」——

那不是唱得比較好，那是**那一段根本不是 B 唱的**。而且被冤枉的人
在包廂裡沒有辦法反駁（畫面就是這樣寫的），這種錯比不做還糟。

所以每一段先過三道守門，才決定要不要給名次：

| 守門 | 門檻 | 不設會怎樣 |
|------|------|-----------|
| 兩邊都唱夠 | 各自被算到的導唱音符 ≥ 30 幀（約 0.5 秒） | 就是上面那個「68% 完勝 0%」 |
| 參與量相當 | 少的那一邊 ≥ 多的那一邊的一半 | 跟一句（40 幀）只要那一句準就有 100%，唱滿整段（400 幀）的人被自己的難處拉低 —— 這種「比較」比不比還糟 |
| 差距夠大 | 命中率差 ≥ 5 個百分點才點主場 | 61% 對 59% 宣布主場，是在幫他們製造爭吵而不是回饋 |

過不了前兩道的段落照樣列出來（那是有用的資訊：這首歌怎麼分工的），
但標成「由 X 主唱」、整列淡化、不計進比數，而且沒唱的那一邊顯示 `—` 而不是 0%——
畫成 0% 看起來像「唱了但完全沒中」，跟「沒唱」是兩件完全不同的事。

前兩道守門能成立，是因為**判定為串音的幀根本不會進段落統計**
（上一輪 `tick(credit)` 的設計）：所以 `note_frames` 剛好就是
「這一位在這一段被算到多少」，不必另外埋一個計數器。

### 門檻與段落評分共用

30 幀與 5 個百分點這兩個值不是新選的，是 `section-scorer.js` 裡
單人段落評分用的同一組（`MIN_SECTION_NOTE_FRAMES` / `MIN_SECTION_SPREAD`）。
兩邊用不同的門檻，會出現「單人成績單說這段有評分、段落對決說沒有」
這種說不通的畫面。兩個檔案是各自獨立的 script（沒有模組系統），
所以照 `DUET_TIE_RATIO` 的前例在 `duet-scorer.js` 再宣告一次、
註解互相指名，並且**用一條測試把兩邊的值釘在一起** ——
註解會被忽略，測試不會。

### 畫法：往中間對拉，而不是兩張圖

兩個人各畫一張獨立的長條圖是最直覺的做法，也是最沒用的做法：
「A 的副歌 1 是 68%」跟「B 的副歌 1 是 41%」分在兩張圖上，眼睛得自己配對。
改成**對拉**（左邊 A 桃紅、右邊 B 青綠、段落標籤釘在正中間），
比較這件事就畫進版面本身了，掃一眼就知道哪幾段偏一邊。

- 兩位的顏色（桃紅／青綠）原本在音準軌跡、計分板、CSS 各寫一次，
  這輪收成 `--duet-a` / `--duet-b` 兩個變數。三處各寫一組色碼的話，
  哪天換了顏色而其中一處沒改，畫面就開始騙人。
- 結算畫面只有九秒，所以最多列六段（超過就只留真的有對決的段落，
  並註明「另有 N 段未列出」），`.duel-rows` 再加 `max-height` 兜底。
- 用 Playwright 真的把這一塊 render 出來看過（從 `player.js` 直接切出
  `renderDuetSectionDuel` 的原始碼餵給預覽頁，不重打一份，
  否則預覽跟真的畫面會慢慢對不上）。第一版的「小明 的主場」多了一個空格，
  是看了圖才發現的 —— 中文字串的空格在程式碼裡看不出來。

### 入庫：只存主場段落

長條圖是結算畫面的現場資訊，不入庫（跟單人段落評分同一個判斷）。
但**主場段落**（領先最多的那一段）進了評分歷史的 `duel_section` 欄位：
「這首歌的副歌一向是我的主場」是回頭看歷史時真正有用的一句話，
一排百分比不是。點歌台與手機端的對唱結算通知也會帶上它
（兩位都沒有對決段落時整段不提 —— 硬湊一句「主場：無」比不講還糟）。

### 測試（前端 10 條 + 後端 3 條）

- `frontend/tests/duet-scorer.test.js`：門檻與段落評分一致（釘死那條）、

  參與量差太多退成主唱、兩邊都唱不夠的段落不列出、依歌曲順序排列與比數統計、
  段落編號對不齊時不會錯位、壞資料（null / 字串 / 缺欄位）不炸、
  `verdict()` 在只有一個人唱時形狀一樣。
- 後端：`duel_section` 跟著各自那一筆進歷史與 `singer_bests`、
  單人演唱一律空字串、標籤長度上限截斷。
- 後端 289 條、前端 149 條全綠；ruff 與部署檔驗證照樣過。

## 2026-09-09 — 對唱模式：兩支麥克風分別評分（v1.4.0「Two Mics」）

**目標**：ROADMAP「後續想做的 → 演唱體驗」的第一項「對唱模式（兩支麥克風分別評分）」。
商用點歌機（DAM 的デュエット採点、金嗓的男女對唱評分）都有這一套，
而包廂裡那句「這首我們對唱，看誰分數高」是這個系統目前完全接不上的需求。

### 這個功能真正的難處：串音（crosstalk）

寫兩個計分器很簡單。難的是**兩支麥克風在同一個房間裡**：
A 唱歌的時候，B 的麥克風也收得到 A 的聲音。

如果不處理，B 只要把麥克風舉著站在旁邊，分數就會跟 A 差不多。
而這件事最可怕的地方是 **它看起來完全正常** —— 兩邊的分數都在跳、
Combo 也在累計、音準線也在動。現場沒有任何人有辦法發現分數是假的
（除了「奇怪，我明明沒唱」這種沒人會講出口的疑惑）。

所以整個模組的唯一工作，是回答每一幀的那個問題：**這一幀該算誰的？**

| 規則 | 依據 | 為什麼需要 |
|------|------|-----------|
| 電平主導 | 兩支麥克風的原始電平差 ≥ 9 dB 就只算大聲的那一位 | 近距離收音的串音通常比本人小 12~20 dB |
| Schmitt 遲滯 | 進入獨佔差 9 dB、回到「兩邊都算」差 4.5 dB | 沒有遲滯的話門檻附近每幀都在換人，分數會亂跳 |
| 音高分歧例外 | 兩邊音高差 ≥ 1.5 半音就都給分 | 串音是同一個聲音的複製品，音高必然一樣；音高不同就是真的兩個人 |
| 訊號門檻 | 音高分歧只在被壓的那一邊高於底噪 12 dB 時生效 | 底噪的自相關結果基本上是隨機數，拿它比「音高不一樣」等於放串音進來 |

第三條是這次最值得記的一步。原本只有電平主導，那會系統性地冤枉
「唱得比較收的那一位」—— 他小 10 dB，就整首都沒有分數。
加上音高判斷之後，「小聲但唱的是另一個音」被正確地認成第二個人，
而「小聲且音高一樣」仍然被判成串音。這是兩件事第一次真的被分開。

### 判定要在計分之前，不能在計分之後

實作上有一個順序問題：判定需要兩支麥克風的電平，而電平是在音高偵測裡量的。
照原本的流程（`tick()` 裡面自己量、自己計分）就會變成
「先計分，再判定這一幀該不該計分」—— 已經加進去的分數要再減回去，
Combo 與段落統計也要回捲，那是找不完的 bug。

所以改成兩階段：

1. `measureRms()` 兩支各量一次（只量電平，不做自相關）。
2. `duet.decide()` 判定這一幀算誰的。
3. `tick(t, { credit, reuseRms: true })` 各自計分 ——
   `reuseRms` 讓它沿用剛才填好的波形緩衝，不重抓一次
   （自相關是整條 60fps 迴圈裡最貴的一步，多抓一次純粹是浪費，
   而且兩次抓到的樣本不一樣，除錯時會非常困惑）。

`credit: false` 的幀**照樣偵測音高**（判定本身需要它）但不計分、
不進段落統計、不畫軌跡。

### 兩種接法（因為它們對應兩種真實的硬體）

- **兩個輸入裝置**：兩支 USB 麥克風。最便宜。
- **同一裝置的左右聲道**：兩支麥克風接一台音效介面／混音器，
  L = A、R = B。這是包廂真正的接法，也只有這條路能用真正的動圈麥克風。
  A 麥的串流要重開成立體聲，再用 `ChannelSplitter` 分兩路。

立體聲那條路有一個必須擋下來的失敗模式：**介面只給單聲道**。
悄悄退回單聲道的話，B 麥拿到的是 A 的完美複製品，
兩個人的分數會一模一樣 —— 又是一個「看起來正常」的假分數。
所以拿到串流後檢查 `track.getSettings().channelCount`，
不到 2 就明確拒絕並要求改選兩個裝置。

### 只有一個人唱的時候不要亂比

對唱開著、但另一支麥克風放在桌上，是很常見的情況。
這時候亮出「A 勝 B（領先 40000 分）」不是比賽，是誤會。
所以 `verdict()` 先看兩位各自被算到的時間（各要 ≥ 10 秒）才進對戰判定，
否則退回那一位的單人成績單。同理，分數差在 3% 以內算平手 ——
逐幀評分本來就有雜訊，差 1% 就宣布勝負只會讓人覺得分數是隨機的。

### 現場排查得出來

串音判定調不好的症狀是「我明明在唱，分數卻不動」。所以：

- 舞台計分板上被判成串音的那一列會變淡並寫「串音靜音中」。
- 結算畫面會標出「有 XX% 的時間被判為串音」（超過 30% 才顯示）——
  那不是唱不好，是兩支麥克風靠太近或門檻設太高，分數本身已經不公平。
- 門檻放在系統設定頁（3~24 dB），照上面那個比例調。

### 後端

- 控制參數 `duet_enabled` / `duet_name_a` / `duet_name_b`（共享狀態，暱稱截 12 字）。

  「一場只有一個人的對唱」，那筆資料之後永遠說不清是誰的問題；
  而且會廣播兩次，包廂裡每支手機都跳兩則。

  等於每次都跟包廂裡唱最好的那個人比。

## 2026-09-08（第 2 輪）— 和聲 / 雙聲部（v1.3.0「Second Voice」）

**目標**：ROADMAP「後續想做的 → 音訊」清單裡的第一項「和聲效果（雙聲部疊加）」。
商用點歌機（金嗓的 HARMONY、音圓的雙聲部、DAM 的ハモリ）都有這顆鍵，
而我們原本連移調的能力都沒有 —— 這是曲庫、評分、練唱都齊了之後，
**唱起來的爽度**上最大的一塊空白。

### 為什麼「升 4 個半音再疊回去」是錯的

這個功能最容易被做壞的地方，是把它當成「把麥克風升幾個半音」。
三度和聲的「三度」是**音階上的度數**，不是固定的半音數。以 C 大調為例：

| 旋律音 | 上三度 | 相差半音 |
|--------|--------|----------|
| Do | Mi | **+4** |
| Re | Fa | **+3** |
| Mi | Sol | **+3** |
| Fa | La | **+4** |
| Sol | Ti | **+4** |
| La | Do | **+3** |
| Ti | Re | **+3** |

固定 +4 有四分之三的音是錯的（Re 會唱出 Fa♯，那是 G 大調的音）。
在包廂裡，那不是「效果比較差」，那是**當著客人的面走音**。

所以和聲必須先知道「現在是什麼調、這個音是第幾度」。這也決定了模組怎麼切：
判斷（純資料）與移調（DSP）分成兩個檔案，前者才守得住。

### 調性怎麼估：權重看時間，不看次數

`estimateKey()` 拿導唱音符做音級直方圖，跟 Krumhansl-Kessler 的大小調感知輪廓
做 12 個旋轉 × 2 種調式的 Pearson 相關，取最高的。兩個實作上的決定：

- **權重用時間長度而不是出現次數**：主音與屬音通常是長音，經過音又快又多。
  照次數算會把裝飾音當成調性骨幹。
- **單一長音上限 2 秒**：尾奏那個拖了 12 秒的長音不該一個人決定整首的調。
  （這一條是寫測試的時候想到的 —— 造了一個「60 秒的 F♯ + 一小段 C 大調」
  的資料，沒有上限的版本直接被那個長音帶去別的調。）

然後是**兩道拒絕作答的門檻**：有效音符不足 8 秒、或相關係數低於 0.45，
就**不給調性**，需要音階的聲部一律退成低八度疊唱。
八度在任何調、任何音都不會錯 —— 寧可少一點花樣，
也不要有一半機率唱出調外音。念白曲、饒舌、還沒處理好歌詞的歌都走這條路。

### 移調自己寫：Web Audio 沒有這個節點

`playbackRate` 只能對 buffer 用（麥克風是即時串流）、`detune` 只有 oscillator 有。
所以移調是自己算的（`harmony-worklet.js`，跑在 AudioWorklet 的音訊執行緒上）：

```
output(t) = input(t - d(t))      瞬時頻率比 = 1 - d'(t)
```

延遲量以固定斜率變化就等於固定比例移調。問題是延遲不能無限縮短，
走到底要跳回去，而那是波形的斷點。解法是兩條讀取頭（延遲相差半個視窗），
快跳到底的先淡出、另一條淡入接手，兩條增益永遠加起來等於 1。

**踩到的坑：交叉淡接會產生梳型濾波。** 第一版用整個週期的 Hann 窗做交叉，
測「音量守恆」時發現 330Hz 的正弦掉了 **27%**（220Hz 與 440Hz 幾乎沒掉）。
原因是兩條讀取頭相差 depth/2，同一個聲音以兩個延遲相加就是一個梳型濾波器，
notch 落在哪個頻率取決於 depth —— 剛好 330Hz 附近。

修法不是換窗形，而是**把交叉區間縮短到一輪的 30%**：其餘七成的時間只有一條
讀取頭在出聲，訊號完全乾淨。同樣的 330Hz 掉不到 8%，主觀上從「聲音悶掉」
變成聽不出來。（拿掉交叉淡接不是選項 —— 那個跳點會變成每秒好幾次的爆音。）

這個坑值得記下來的理由是：**它只有數值測試抓得到**。
用耳朵聽「和聲的音量有沒有隨頻率起伏」，在有伴奏、有殘響的包廂裡根本不可能。

### 沒人唱就不出聲

和聲是把麥克風訊號移調再疊回去，所以沒人開口時疊出來的是**升高八度的呼吸聲、
椅子聲與空調聲**。這不是小瑕疵：升高八度會把那些低頻噪音搬到人耳最敏感的頻段，
比原本明顯得多。所以 `sang` 是硬性條件，另外需要音階資訊的聲部在
前奏／間奏（`hasNote` 為假）也安靜。

還有一道「不要抖」的門檻：同一個音符不重算移調量，換音符也要隔 80ms。
音符邊界上前後兩個音會交替被判為 active，沒有這道門檻的話移調量會在
+3／+4 之間每幀跳一次 —— 聽起來像和聲在發抖。

### 接在音訊圖的哪裡：和聲屬於人聲

```
… → micGain ─┬→ monitorGain → masterGain / reverb / echo
              └→ 和聲移調 ×2 → 和聲音量 ─┘
```

接在 `micGain` **之後**（麥克風音量滑桿一起帶動和聲，音量比例不會跑掉）、
`monitorGain` **之前**（跟主唱吃同一個「人聲外放」總開關與同一組殘響回音）。

副作用是**單人模式聽不到和聲**。這是刻意接受的：和聲從喇叭出去會被麥克風收回來
再移調一次，那條路徑會一路往上疊（每繞一圈升高一次），比單純的回授更難止。
單人模式的存在理由就是物理性切斷那條路徑，和聲不該打破它。
所以 UI 與說明書都直接把這件事寫出來，而不是讓使用者以為按鈕壞了。

### 舞台徽章要顯示調性

🎶 徽章寫的是「和聲 上三度（**C 大調**）」。調性寫在畫面上是刻意的：
和聲聽起來不對的時候，「機器把這首歌判成什麼調」是**唯一有用的線索**。
沒有它，客訴只會是「和聲很難聽」，而那句話裡沒有任何可以debug的資訊。
沒人唱的時候徽章補一句「· 等你開口」，否則「按了和聲卻沒聲音」會被當成故障。

### 測試

- `frontend/tests/harmony-planner.test.js`（27 條）：七個音級的上三度半音數
  逐一釘死、跨八度、非音階音吸附、小調、調性判定的兩道門檻、
  壞資料（缺欄位／負音高／時間反了）、出聲時機、音量上限、
  換歌重估調性、換風格不被保持時間擋住。

  和聲會用到的 +3/+4/+6/+7/−3/−4/−5 全部量過；直流輸入驗證兩條讀取頭
  增益恆為 1；五個頻率 × 四個移調量的音量守恆（守住那個 8% 的梳型上限）；

## 2026-09-08 — 排程預處理（v1.2.0「Night Shift」）

**目標**：ROADMAP「後續想做的」清單裡的「預先排程處理」。挑它的理由是它針對的是
這個系統**架構上唯一的硬傷**：隨選處理很好，但第一次點一首新歌就是要等好幾分鐘，
而那幾分鐘剛好發生在「大家都想唱」的時刻。商用點歌機沒有這個問題，
因為它的曲庫是**事先備好**的 —— 那就把「事先備好」這件事做出來。

### 為什麼一次只跑一首

第一版寫的是「進到時段就把整批跑完」。想了一下這是錯的：
包廂的使用是隨機的，半夜兩點也可能有人推門進來。批次一旦開跑就佔著 GPU 不放，
現場點的第一首歌要排在批次後面等 —— 那正是這個功能想解決的等待，只是換了個時間發生。

改成 `run_once()` **處理一首就回來**，由外層迴圈重新問一次「現在可以跑嗎」。
代價是每首之間多幾秒的判斷延遲（一晚上跑 40 首也才多幾分鐘），
換到的是「最多再忙一首歌的時間，機器就會讓開」這個上限。這個交換划算得沒有懸念。

### 「為什麼還沒開始」要一直寫在畫面上

這種背景功能最常被問的問題不是「它做得對不對」，而是
**「都兩點了它到底在幹嘛」**。所以 `run_decision()` 回的不是布林值，
而是 `(能不能跑, 給人看的理由)`，理由常駐在分頁的狀態列上：
等時段（還有幾分鐘）／有人在唱歌／功能被關掉／根本沒歌要處理。

四種情況長得很像（都是「沒在動」），但處理方式完全不同 ——
第一種是等，第二種是正常，第三種要去開設定，第四種是使用者誤會了。
不寫出來的話，四種都會變成同一則客訴。

### 跨午夜的時段不是特例，是常態

`in_window()` 一開始寫成 `start <= hour < end`，然後才想到最想設的時段
就是 23:00–06:00 —— 那是**跨午夜**的。跨午夜不是邊角案例，是主要用途，
所以判斷式分成兩支（`start < end` 照常、否則 `hour >= start or hour < end`），
並且讓「起訖同一小時」= 全天候（使用者想關掉時段限制時最直覺的表達方式）。

### 三個「不要太聰明」的決定

- **展開播放清單在 API 層做，不在排程器裡做。** 排程器只認「已經展開好的歌曲清單」，
  所以它完全不碰網路，測試可以用純資料把整個生命週期跑完。
- **`watch?v=xxx&list=yyy` 不算播放清單。** 使用者從清單裡複製某首歌的網址時，
  想點的是那一首。只有 `playlist?list=` 才展開整張 —— 那是 YouTube「分享整個播放清單」給的網址。
- **取消不中斷正在處理的那一首。** 中途砍掉留下的是半成品資料夾，
  下次還要靠「快取管理」去清。讓它跑完幾分鐘，比留一個坑給未來的自己好。

### 只看 metadata 會漏掉要補跑的歌

「已經在曲庫裡就略過」原本用 `get_song_metadata()` 判斷，這是錯的：
metadata 是流水線**早期**就寫下的，處理到一半中斷的資料夾照樣有 metadata。
那種歌會被永遠標成「略過」，也就永遠不會被補跑 —— 而它正是最需要被補跑的那種。
改用新增的 `is_song_complete()`（四個必要檔案都在），跟「快取管理」分頁的完整性徽章同一套標準。

### 重開機要記得的不只是清單

任務清單持久化是理所當然的，比較容易漏的是 **`force_run`（使用者按過的「立即開始」）**：
半夜按下去然後機器重開，如果只還原清單不還原這個旗標，它就會安靜地退回等時段，
使用者隔天早上發現一首都沒跑。意圖也是狀態。
反過來，處理到一半的 `RUNNING` 項目要退回 `PENDING` 重跑 —— 那首歌八成只完成了一半。

### 前端：即時重畫不能吃掉正在輸入的字

分頁會收 `BATCH_UPDATE` 廣播即時重畫（每處理完一首歌一次）。
第一版直接重寫 `innerHTML`，結果是使用者貼了 30 行清單、還沒按送出，
背景跑完一首歌就把整框字清空了。現在重畫前先接住 textarea 的內容、選取範圍與焦點，
畫完再放回去 —— 用 Playwright 實測過「打字 → 收到廣播 → 字還在」。

顯示邏輯（上百首時挑哪 8 首上畫面、時段字串、狀態燈優先度）抽到
`frontend/js/batch-view.js` 用 `node --test` 守著。這類錯誤不會拋例外，
只會讓畫面看起來正常但其實在騙人 —— 比方說挑錯項目，正在跑的那首沒被顯示出來，
使用者就會以為機器沒在動。

### 驗證

- 後端 264 條（新增 27 條排程 + 6 條端點）、前端 75 條（新增 8 條）全綠，ruff 乾淨。
- 起了一台真的伺服器：塞入示範任務 → 按「立即開始」→ 觀察迴圈確實每 20 秒醒來、
  一次處理一首、失敗的標記錯誤後繼續下一首、待處理數確實下降。
  （這個環境連不到 YouTube，所以每首都失敗 —— 剛好把失敗路徑走了一遍。）

**下一步**：ROADMAP 剩下的選配項目（和聲效果、對唱模式、情境背景、多包廂）。

## 2026-09-07（第三輪）— 麥克風自動增益（v1.1.0）

**目標**：ROADMAP 的對照清單在 v1.0.0 已經全數打勾，這一輪開始做「後續想做的」
第一項 —— 麥克風自動增益。挑它先做的理由很實際：包廂裡最常聽到的抱怨不是音準
也不是效果，而是「換人唱又要重調麥克風音量」。上一位貼著麥克風吼、下一位離 20 公分
小聲哼，輸入電平差 20 dB 以上，這件事每首歌都會發生一次。

### 為什麼用前饋，不用回授

analyser 本來就接在 `micSource` 上（音高評分要的是原始訊號），
所以量到的電平天生就在增益節點之前 —— 直接拿來當前饋量測，一行都不用改。

反過來（量已經放大過的訊號）會變成「放大 → 量到更大 → 少放大 → 量到更小」的
呼吸迴路。更麻煩的是那個迴路的時間常數會跟房間殘響耦合在一起：
同一組參數在小包廂與大廳的行為完全不同，現場根本調不出來。前饋沒有這個問題，
代價是它不知道最終輸出多大聲 —— 所以削峰保護要自己用「輸入 + 目前增益」推估。

### 三條安全規則（順序就是優先度）

1. **沒人唱的時候絕不加增益**（噪音閘門 -45 dBFS）。這條最重要：安靜的房間也有底噪，
   照著「拉到目標音量」算下去會一路加到上限，然後第一個字進來直接爆掉，
   多人模式還會當場嘯叫。所以閘門以下只累計靜音時間，什麼都不動。
2. **要降立刻降（0.25s）、要升慢慢升（3s）**。降是保護、升是舒適；
   升太快會讓句與句之間的空隙把底噪一起抬起來，那個聲音很像機器在呼吸。
3. **範圍夾住**（+9 / -12 dB），而且**多人模式的加成上限收到 +6 dB**。
   人聲外放時每多加 1 dB 就離回授近 1 dB，這是物理，軟體只能選擇不要去踩。
   `configure()` 收到更小的上限時會**立刻**把現有增益夾回去（不等下一幀趨近）——
   收緊範圍是安全動作。

### 兩個寫錯了才發現的地方

- **容忍區不能寫成死區**。第一版是「差不到 1 dB 就不動」，結果增益永遠停在
  離目標 1 dB 的地方：趨近是指數的，一路靠近到剩 1 dB 就被死區凍住，
  等於系統性地永遠差一格（測試直接抓到 6 dB 只補到 5.0）。
  改成**遲滯**：差 1 dB 以上才「開始」調，一開始調就一路調到位（剩 0.15 dB 收手）。
- **削峰保護線是速度地板，不是「不准再降」的地板**。第一版把保護判斷寫在
  電平判斷的 `else` 前面，於是貼著麥克風吼的時候，增益被鎖在「剛好不削峰」的 -5 dB，
  而目標電平其實要求 -12 dB —— AGC 等於整首歌都沒作用。
  現在兩個目標都算出來取較小（降得多的）那個，只是用保護的時間常數去追。

### 換裝置歸零、換歌不歸零

- 換麥克風要 `reset()`：動圈換成電容，靈敏度差很遠，學到的增益是上一支的。
- 換歌只 `resetStats()`：一個人常唱兩三首，把增益丟回 0 dB 只會讓他每首歌的
  第一句都先小聲三秒。副作用是 `voicedSeconds`（同時是暖機計時器）歸零，
  所以換歌後會重新暖機 1.2 秒 —— 這剛好是想要的：換歌很可能換人，
  前奏那一兩句先維持現有增益、聽清楚新的人有多大聲再動。

### 電平表（意外地是最有用的部分）

舞台按 `S` 的音訊面板多一條收音電平表。原本只是 AGC 的除錯工具，
做完發現它解決的是另一個問題：**麥克風到底有沒有在收音**。
沒插好、選錯裝置、筆電實體靜音鍵沒開 —— 以前要開唱才發現，現在三秒就看出來。
三段顏色（灰／青／粉）對應的是「軟體幫不了、只有人能動」的兩種狀況：
太遠（加到上限也只是放大底噪）與太近（削峰救不回來）。

渲染迴圈在暫停時就 `return` 了，所以表會凍住 —— 面板開著且沒在唱的時候
另外跑一個 66ms 的試音迴圈，用新開的 `measureRms()`（只算 RMS，
不跑自相關音高偵測 —— 那是整條迴圈裡最貴的一步）。

### 刻意沒做的事

**沒有讓自動增益影響評分**。音高偵測的噪音門檻（RMS 0.015）還是照原始訊號判，
所以自動增益加得再多，分數還是照實際唱的算 —— 分數會因為音量被機器調過而改變，
是最難解釋的一種 bug。實務上這個門檻也很少擋到真的在唱歌的人：
它相當於 -36 dBFS，而 AGC 要出手的「小聲」通常在 -30 dBFS 上下，本來就過得了門檻。

### 測試

`frontend/tests/mic-agc.test.js` 24 條，全部是純資料邏輯（不碰 DOM、不碰 Web Audio）：
靜音餵一分鐘不加增益、暖機、遲滯收斂到位、不對稱曲線（0.4 秒內降得比升得多兩倍以上）、
削峰保護、長時間安靜放回中性、30fps 與 120fps 一致、分頁切回來的超大 dt、
壞資料（NaN / 負 RMS / 沒有 frame）不會讓增益變 NaN。
後端加一條設定範圍測試。合計後端 232 條、前端 67 條。

## 2026-09-07（第二輪）— Docker 一鍵部署 + 正式發布（v1.0.0）

**目標**：ROADMAP 只剩「系統」那兩項，做完就是可以發布的系統。
這一輪不新增演唱功能，全部在處理「別人怎麼把這台機器架起來、
以及三個月後怎麼知道他跑的是哪一版」。

### 版本號：唯一真相來源
- 新增 `backend/version.py`（`__version__` + codename + `KARATUBE_BUILD`）。
  FastAPI 的 `version=`、`/api/version`、設定頁頁尾、release 打包全讀這一個常數。
- 新增 `GET /api/version` 與 `GET /api/health`。
  健康檢查刻意不碰模型也不碰磁碟 —— 拿它當容器 HEALTHCHECK 才不會在
  處理歌曲吃滿 CPU 時被誤判成掛掉。
- 新增 `CHANGELOG.md`。`tests/test_version.py` 守住
  「CHANGELOG 最上面那一筆 == version.py」與版本順序遞減；
  release workflow 再比對 git 標籤。發出去的東西版本號對不上是最難追的問題，
  三道檢查都很便宜。

### 部署設定環境變數化
- `config.py`：`KARATUBE_HOST` / `KARATUBE_PORT` / `KARATUBE_PUBLIC_HOST` /
  `KARATUBE_PUBLIC_PORT` / `KARATUBE_CACHE_DIR`，值壞掉一律退回預設 ——
  機器可以印錯網址，但不能因為一個環境變數打錯就開不起來。
- **`public_base_url()`**：QR code 與「手機點歌」網址原本是
  「自動偵測本機 IP + 監聽 port」。容器裡偵測到的是 bridge 網段（172.17.x.x），
  手機掃了根本連不進去；反向代理後面對外的 port 也不是容器監聽的那個。
  現在設了 `PUBLIC_HOST/PORT` 就以它們為準，80/443 不寫進網址。
- `run.py`：容器裡不開瀏覽器（偵測 `/.dockerenv` 或 `KARATUBE_IN_CONTAINER`），
  否則開機日誌會被 xdg-open 的錯誤洗版、看起來像壞了。banner 印出版本號。

### Docker
- `Dockerfile`：依賴分兩層（改程式碼不用重裝 PyTorch，那層要幾分鐘）、
  內建 ffmpeg、非 root（uid 10001）、`/data` 為 volume、`/api/health` HEALTHCHECK。
  GPU 版只要換 `BASE_IMAGE` build arg 成 CUDA 映像。
- **踩到的坑**：`~/.cache` 必須先在映像裡建好並 chown。
  Docker 掛 named volume 時會沿用映像裡那個目錄的擁有者，
  沒先建的話 volume 是 root 的，非 root 行程下載不了 Whisper / Demucs 權重，
  而且錯誤訊息完全看不出是權限問題。
- `docker-compose.yml`：曲庫與模型權重分開兩個 volume（前者是使用者資料要備份，
  後者只是下載快取）、GPU 區塊註解好放著、`.env` 帶 `KARATUBE_PUBLIC_HOST`。
- `.dockerignore`：`cache/` 是最重要的一條 —— 用過的機器那裡有好幾 GB，
  沒排除的話光是送 build context 就要等很久。

## 2026-09-07 — 導唱音量自動 ducking（唱穩了導唱自己退場）

**目標**：ROADMAP「音訊」剩下的最後一項。商用機（DAM 的 *ガイドボーカル自動フェード*、
金嗓的「導唱漸弱」）早就不把導唱人聲當成開／關兩檔的開關 ——
它跟著唱的人走：唱穩了退到背景，走音或忘詞時回來扶一把。
KaraTube 原本只有一支「導唱人聲 0~100%」的滑桿，等於要使用者自己在
「怕忘詞」與「怕唱不出自己的味道」之間二選一。

### 新模組：`frontend/js/guide-ducker.js`

不做任何新的音訊分析：**逐幀判定沿用評分心跳已經算好的結果**
（這一幀有沒有導唱音符、有沒有唱出聲、準不準），
`PitchEngine.tick()` 從「不回傳」改成回傳這份判定，段落評分與 ducking 共用同一份 ——
音高偵測是整條 60fps 迴圈裡最貴的一步，而且兩邊各自偵測一次的話，
算出不同結果時會非常難查。

這個功能錯了會非常明顯地毀掉體驗，所以三個參數都是照失敗模式訂的：

- **不對稱曲線**：淡出時間常數 1.6 秒、淡回 0.22 秒。
  退得太快 → 副歌唱準兩個字導唱就消失，第三個字忘詞當場裸奔；
  回得太慢 → 已經走音兩秒才聽到導唱，那時人早就放棄這一句。
- **Schmitt 遲滯門檻 0.55 / 0.35**：命中率在門檻附近抖動時維持現狀。
  沒有遲滯的話導唱會一直忽大忽小，那比全開還吵。
  門檻是照逐幀判定的實際手感抓的（逐幀命中比直覺嚴格，唱得不錯的人落在 0.5~0.7，
  照直覺設 0.8 會永遠不退）。
- **暖機 3 秒**：沒有這道門檻，前奏後第一個音唱準就會觸發 —— 那是運氣不是穩定。
- **間奏不改變狀態**：`hasNote=false` 的幀不更新信心度也不重新判定。
  那段本來就沒有導唱人聲可退，硬要衰減只會讓副歌一進來導唱先大聲一下再退，變成幫倒忙。
- **深度上限 0.95**：永遠留一點導唱在背景當安全網，不給「完全消音」這個選項。
- 命中率用時間常數而不是幀數的 EMA，所以 30fps 的機器不會變成兩倍慢
  （測試直接比對 30fps 與 120fps 的收斂位置）。

### 音訊圖：導唱倍率與導唱音量分成兩個節點
`sourceVoc → guideDuckGain → gainVoc → normGain → masterGain`。
刻意不把倍率乘進 `gainVoc`：使用者拉的導唱音量與機器的自動退場是兩件事，
混在同一個 gain 上，自動退場後再去動滑桿，滑桿刻度就會跟實際音量對不起來。

### 舞台與結算
- 舞台右下角新增 🎚️ **導唱自動淡出 XX%** 徽章（練唱徽章正上方，同一欄不會疊）。
  沒有這個提示的話，導唱變小聲只會被當成「機器把導唱吃掉了」。
  文字每 250ms 才更新一次 —— 60fps 直接寫 `textContent` 會每幀重排版面。
- 結算畫面新增 **🎚️ 導唱獨立度 XX%**（導唱自動淡出的時間比例）。
  這個數字比總分更能看出進步：分數會被歌難不難影響，
  「上週副歌整段靠導唱，這週導唱退場了七成」才是直接的回饋。
  導唱沒開、或有效演唱不到 20 秒就整行不顯示 —— 兩句歌的比例只是雜訊。

### 設定
- `settings.py` 新增 `guide_duck_enabled`（預設開）與 `guide_duck_depth`（預設 0.6，上限 0.95）。
- 點歌台系統設定頁多一組「🎚️ 導唱自動淡出」（表單照後端欄位規格自動長出來）。
- 改設定不重置狀態：唱到一半調深度不該讓導唱跳回全開；
  但開關切換兩個方向都重來（關掉要立刻放掉導唱，打開要重新暖機）。
- 導唱音量本來就是 0（純伴奏）時整段邏輯不跑，徽章也不亮。

### 測試（後端 219 條 + 前端 43 條，全綠）
- 新增 `frontend/tests/guide-ducker.test.js`（17 條）：暖機門檻、退場深度與漸進、
  救援速度（走音六秒內回到接近全開）、遲滯區間不翻轉、間奏不改變狀態與不計入統計、
  關閉時完全不作用、深度夾限、唱到一半改設定、`reset()`、獨立度統計的守門、
  更新頻率無關性（30fps vs 120fps）、分頁切回來的巨大 dt、非法輸入不產生 NaN。
- `tests/test_settings.py` +1：導唱淡出預設值與深度夾限（上限刻意不到 1.0）。

### 文件
- README（核心特色 19、目錄結構、測試條數）、USER_GUIDE（系統設定新章節、
  導唱獨立度、常見問題「導唱自己變小聲是壞了嗎」）、ROADMAP 打勾、STATUS.yaml。

### 下一步（建議下輪迭代）
1. Docker 一鍵部署（ROADMAP 系統類只剩這項與 release 打包）。
2. 正式發布：版本號、release 打包、安裝說明。

## 2026-09-06 — 段落評分（哪一段唱得最好／最差）＋ 前端單元測試基礎建設

**目標**：ROADMAP「演唱體驗」剩下的最後一項。總分是娛樂，段落評分才是能拿來練歌的資訊 ——
「62 分」只讓人沮喪，「副歌 2 只有 31%、主歌都在 70% 以上」直接指出下一輪要練哪裡。
順手把「前端單元測試」那一格也補掉：這次新增的邏輯剛好是可以脫離瀏覽器測的純資料邏輯。

### 新模組：`frontend/js/section-scorer.js`

沒有新增任何分析：**分段沿用練唱模式已經在算的曲式**
（`chorus_detector` 由歌詞重複結構切出的前奏/主歌/副歌/間奏/尾奏），
**判定沿用評分心跳每幀已經算好的結果**（有沒有導唱音符、有沒有唱出聲、準不準）。
段落評分做的事只有一件：把同一幀的結果依時間歸到所屬段落再累計一份。

- `normalizeSections()`：濾掉前奏／間奏／尾奏（沒有導唱音符，列出來只會是一排 0%）、
  丟掉時間軸壞掉的資料、依起點排序，並丟掉與前一段**重疊**的段落 ——
  重疊會讓「一個時間點只對到一段」的前提失效，寧可少評一段也不要對錯段。
  用「排除清單」而不是「白名單」，後端日後多切出 bridge 之類的段落會自動納入。
- `sectionIndexAt()` 用**二分搜尋**，不用「記住上一段往前掃」的游標：
  A-B 循環與進度條跳轉會讓時間任意前後跳，線性游標在那些情境下會退化成每幀重掃整首。
- `summary()`：每段命中率 = 該段命中幀 ÷ 該段有導唱音符的幀。
  這個定義讓 A-B 循環唱三輪也算得對（整段累計的比例，不是最後一輪覆蓋前面）。
- `gradeForAccuracy()`：等級門檻從 `pitch-engine.js` 抽出來共用，
  單段評語與整首總評的手感才一致（原本門檻寫死在 `getFinalResult()` 裡）。

### 兩道「不亂下結論」的守門（這個功能真正的難點）

功能本身只是加總，難的是**什麼時候該閉嘴**：

1. **太短的段落不參加評分**：導唱音符不足 30 幀（60fps 下約 0.5 秒）的段落標成未評分。
   一兩幀的運氣不該決定誰是「最差的段落」。
2. **表現太平均就不點名**：最佳與最差差距 < 5 個百分點時 `best` / `worst` 都回 `null`，
   前端只畫長條圖不下結論。整首均勻地唱到 55% 時說「副歌 2 是你最差的段落（54%）」
   是在製造焦慮，不是回饋。
   —— 這條的邊界踩到浮點雷：`0.6 - 0.55` 在 IEEE 754 裡是 `0.049999…`，
   直接比門檻會讓「剛好差 5 個百分點」隨機失效（測試先抓到，才改成先四捨五入再比）。

同分時最佳取先唱到的那一段，讓結果不隨排序演算法的實作而變。

### 舞台結算畫面

- 成績單中間新增 **📊 段落表現**：每段一條命中率長條（最佳標黃、待加強標粉），
  上方點名 💯 最佳段落 / 📈 待加強；點不出來時寫「整首表現平均，沒有明顯拖分的段落」。
- 可評分段落不到兩段（沒歌詞、只唱一段就切歌）整塊收起來 ——
  段落評分是加分項，總分與等級不受影響。
- 長條從 0 長出來的動畫和分數滾動一起跑，維持商用機結算畫面的儀式感；
  段落多的歌超過高度就在卡片內捲，不會把卡片撐出畫面。
- 段落預覽（首句歌詞）進 `title` 提示，且所有插進 `innerHTML` 的文字都跑過 `escapeHtml()`。

### 貫穿的接線

- `player.js` 載歌時多抓一次 `/api/songs/{id}/sections`，
  用 `.catch()` 兜住 —— 段落是附加資訊，抓不到不能擋播放（歌詞還沒好的歌就是沒有曲式）。
  順序上 `setPitchData()`（會歸零評分）必須在 `setSections()` 之前。
- `pitch-engine.js` 的 `evaluateSingingScore()` 改成回傳 `{hit, perfect}`，
  段落評分沿用同一個判定，不重算也不會兩邊算出不同答案。
- 結論（「副歌 1」/「主歌 2」兩個標籤）跟著成績寫進 `cache/score_history.json`：
  長條圖是現場資訊，但「這首歌我老是哪一段唱壞」是回頭看歷史才有用的東西。
  空值一律存成空字串而不是 `None`，前端才能一律用 `if (r.best_section)` 判斷。
- 點歌台／手機的結算通知加上「💯 副歌 1 / 📈 主歌 2」。

### 工程品質：前端單元測試上線

- 新增 `frontend/tests/section-scorer.test.js`（26 條，`node:test` + `node:assert`）：
  等級門檻的每個邊界、段落清單正規化（壞資料、重疊、排序、未知種類）、
  時間→段落（邊界、空隙、負時間、NaN）、逐幀累計、reset/換歌歸零、
  最佳/待加強的挑選與兩道守門、A-B 循環累計、浮點邊界。
- `section-scorer.js` 同時支援 `<script>` 與 `require()`（尾端雙出口），

## 2026-09-06 — 曲庫分類瀏覽（語言 / 歌手）＋ 新歌榜 ＋ 推薦歌單

**目標**：補上 ROADMAP「點歌體驗」剩下的兩項。搜尋很好用，但商用點歌機的主畫面
從來不是只有搜尋框 —— 使用者常常是「想唱台語歌，但一時想不起歌名」，
這時要能用**語言別**和**歌手**把曲庫縮小到看得完的範圍。

### 新服務：`backend/services/library.py`

曲庫是使用者點過的歌自然長出來的，而 YouTube 只給我們標題與頻道名，
沒有語言標籤、也沒有真正的歌手欄位。所以分類得自己判：

**語言判定**（`detect_language`，純函數）依序：

1. **明示標記**最準 —— 歌名／頻道名出現「台語」「粵語」「日文歌」直接採用。
2. **諺文**：≥ 3 字，或諺文 × 2 ≥ 漢字 → 韓語。
3. **假名**：≥ 3 字，或假名 × 2 ≥ 漢字 → 日語。
   用比例而不是「有假名就算」，是因為華語歌名很愛夾一個「の」
   （「我の愛」不該被丟進日語分頁）。
4. **方言用字**：漢字 ≥ 2 時數粵語／台語專用字**出現了幾種**，
   要 ≥ 2 種才定案 —— 單一個「厝」或「係」在國語歌詞裡也會出現，
   一個字就判定的話誤判率高到分類沒有意義。用字表只收辨識度高的
   （所以不收「係」「仲」這種國語文本也常見的）。
5. 其餘漢字 → 國語；拉丁字母 ≥ 3 → 英語；都不符合 → 其他。

判語言只讀歌詞前 600 字：整首讀進來對結果沒有幫助，只是白花 I/O。

**歌手正規化**（`normalize_artist`）：先去掉 YouTube 的機器後綴
（`- Topic`、`VEVO`、`官方頻道` / `Official`）；剩下的名字若含唱片公司／
音樂頻道字樣（Records、娛樂、音樂、頻道…），改從「歌手 - 歌名」「歌手｜歌名」
的標題前半段取；都失敗歸「未知歌手」——
讓判不出來的歌聚成一堆，比每首各自成為一位「歌手」好用得多。

**快取策略**：判定結果寫回該首歌的 `metadata.json`（`language` / `artist_name`），
每首只算一次，之後瀏覽都是純讀檔。不另外存索引檔 ——
刪快取時分類跟著消失，不會留下對不上的孤兒資料。

### 新 API

- `GET /api/library` — 分類軸：每個語言別幾首、每位歌手幾首（歌多的排前面）。
- `GET /api/library/songs?language=&artist=&sort=` — 篩選 + 排序
  （最新加入 / 最常點唱 / 歌名 / 歌手）。
- `GET /api/library/new` — 新歌榜，14 天內加入的標 `is_new`。
- `GET /api/library/recommend` — 推薦歌單，每首附推薦理由。

## 2026-09-05 — 練唱模式：A-B 段落循環 + 自動副歌偵測 + 段落跳轉

**目標**：補上商用 KTV 點歌機的「副歌重播」。這是 ROADMAP「演唱體驗」剩下的最後一項，
也是一般人真正拿伴唱機來練歌時最常用的功能 —— 沒有它，練副歌只能整首重唱。

### 新功能：🔁 練唱模式（A-B 區段循環）

- **共享狀態**：`QueueManager` 新增 `loop_enabled` / `loop_start` / `loop_end` 三個欄位，
  跟其他調音參數走同一條 `/api/control`，所以點歌台、手機、舞台看到的圈選範圍永遠一致。
- **收斂規則**（`_normalize_loop`）：
  - A、B 按反了自動對調 —— 聽到一半才想圈這段，先按 B 再按 A 是很自然的操作，不該報錯。
  - 區間缺一角、或短於 1 秒時一律關掉循環：零長度的區間會讓舞台在同一秒鐘上瘋狂 seek。
  - 換歌時清空（`clear_loop()` 掛在 `play_next`）：A-B 點屬於某一首歌，
    留著會讓下一首在莫名其妙的地方跳回去。
- **跳轉指令**：新增 `POST /api/seek` → `CONTROL_COMMAND: SEEK`。
  伺服器不持有播放位置（媒體在舞台端），所以只送指令、不改自己的狀態。

### 新功能：🎯 自動副歌偵測（`backend/pipeline/chorus_detector.py`）

**問題**：「副歌在哪裡」沒有人會替每首歌手動標記，但沒有這個資訊，
「一鍵副歌重唱」就只能退化成使用者自己聽著抓時間。

**作法**：純文字重複結構分析，不碰音訊。歌詞時間軸在流水線裡已經對齊好了，
而副歌的定義本來就是「整段歌詞重複出現的區塊」，所以拿逐行文字找
「最長、重複最多次的連續區塊」就夠了 —— 比做音訊自相似矩陣便宜好幾個數量級，
而且找到的行可以直接對回它自己的時間。

1. 每行正規化（去標點、空白、轉小寫）：不同來源的 LRC 標點寫法不一，
   不正規化會把同一句判成兩句。
2. 對每組起頭相同的行往下延伸取最長共同區塊，並把它的每個前綴也收進候選 ——
   四行副歌可能只有後兩行在尾聲又多唱一次，那個兩行版本的重複次數比較高，值得參加評分。
3. 評分：先看涵蓋的總行數（重複次數 × 每次行數），同分時偏好「一次比較長」的區塊。
4. 時間守門：低於 5 秒（跳針）或超過 100 秒（抓到整段主歌+副歌）的候選淘汰，換下一名。
5. 全部落空時退一步找「重複三次以上的單行鉤子」（口水歌），
   單行本來就只有兩三秒，時間門檻要跟著放寬到 2.5 秒，否則這條退路等於沒有。
6. 再找不到就回 `None`，前端退回手動 A-B，不會壞。

段落切分（`detect_sections`）則靠唱句之間的靜默：空超過 6 秒算換段，
切出 前奏 / 主歌 N / 副歌 N / 間奏 N / 尾奏，副歌段用偵測結果標記。
新端點 `GET /api/songs/{song_id}/sections` 即算即回，不寫檔、不需要快取。

### 前端

**點歌台（`controller.js` / `index.html`）**
- 調音台新增「🔁 練唱模式」區塊：`A` / `B` 設點鍵（顯示目前時間）、開始/停止循環、清除、
  **副歌重唱** 一鍵鍵，以及自動切好的段落膠囊列（點標籤跳轉、點 🔁 循環該段）。
- 兩點都設好就自動開始循環 —— 商用點歌機按完 B 就跳回 A，不會要你再按第三顆鍵。
- 進度條改成可點擊跳轉，並在上面用黃色區塊畫出目前的 A-B 區間。
- 曲式分析結果依 `song_id` 快取，同一首只跟伺服器要一次。

**舞台（`player.js` / `player.html`）**
- `renderLoop` 每幀檢查是否唱過 B 點，過了就 `seekMedia(A)`。
  200ms 冷卻是必要的：mp3 的 seek 只能落在解碼區塊邊界，跳回去之後補間時鐘
  要一兩幀才重新錨定，沒有冷卻會在 B 點瘋狂連續跳。
- `seekMedia()` 三條軌（伴奏、人聲、MV）一起搬並重新錨定時鐘；
  卡在最後 0.15 秒之外，避免使用者想跳到尾奏卻直接被 `ended` 結算掉。
- 右下角常駐 🔁 練唱徽章並標出區間 —— 沒有這個標示，台上的人只會覺得機器在跳針。
- `PitchEngine.clearTrail()`：跳轉後清掉使用者音高軌跡（舊點的時間都在新位置的未來，
  留著會在導唱線上畫出鬼影），但**分數與統計保留** —— 那些幀是真的唱過的。

## 2026-09-04 — 自動音量平衡（EBU R128）+ 系統設定頁 + pipeline 純函數測試

**目標**：把「發布給別人用的機台」還缺的兩件事補上 ——
使用者不改程式碼就能調整機台行為（設定頁），
以及不用每首歌手動轉音量（自動音量平衡）。順帶補齊 pipeline 的單元測試防線。

### 新功能：🔊 自動音量平衡（EBU R128 / ITU-R BS.1770-4）

**問題**：YouTube 來源的響度差距極大 —— 官方 MV 母帶常壓到 -8 LUFS，
個人上傳的現場版可能只有 -22 LUFS。中間差 14 dB，主觀上大約是「三倍大聲」，
所以每換一首歌就要重新轉音量，這是包廂裡最煩人的體驗之一。

- 新增 `backend/pipeline/loudness.py`：自己實作 BS.1770-4 的
  **K 加權（高頻棚 + RLB 高通）→ 400ms/75% 重疊區塊 → 絕對閘 -70 LUFS
  → 相對閘 -10 LU → 整合響度**。
  - 濾波器係數依類比原型在任意取樣率重新推導，在 48kHz 會退化成規格書列出的參考係數
    （測試直接比對到小數第 9 位）。
  - 不直接抓 pyloudnorm：只需要一個數字卻要多帶一層相依，而且純函數
    （吃 numpy 陣列、吐一個數字）才好用合成訊號在 CI 上測。
  - 濾波優先用 scipy，沒有 scipy 時走純 numpy 備援 —— CI 只裝 numpy 也跑得動。
- 流水線最後（分離、對字幕、抽音高之後）量一次 **伴奏軌** 的響度，
  把 `lufs` / `peak_dbfs` / `gain_db` 存進 metadata。量測失敗只是沒有這筆資料，
  不會讓整首歌處理失敗。
- 新 API `GET /api/songs/{id}/loudness`：回傳**依當下設定重算**的增益 ——
  目標響度改了不用重跑流水線。metadata 沒有響度資料的舊歌會現場量一次並補寫回去，
  所以既有曲庫不必整批重處理。
- 播放端 `audio-effects.js` 新增正規化增益節點 `normGain`：
  `gainInst / gainVoc → normGain → masterGain`。
  **麥克風與氣氛音效直接接 masterGain，不經過這個節點** ——
  換歌調整音量平衡時，唱歌的人不會覺得自己的聲音忽大忽小。
- 三重保險，寧可少調也不要調壞：量不到 → 0 dB；增益夾在 ±12 dB；
  峰值保護（拉完不超過 -1 dBFS）。

### 新功能：⚙️ 系統設定頁

- 新增 `backend/services/settings.py`：以 `SETTINGS_SPEC`（型別／範圍／選項）為單一事實來源，
  存成 `cache/settings.json`。
  - **越界夾回合法值、未知欄位忽略**，不丟例外 —— 設定頁是給人用的，
    手機上滑錯一格不該讓伺服器回 500，舊版前端送新欄位也不該壞。
  - 設定檔壞掉退回預設值，不阻擋開機（機台不能因為一個 JSON 壞掉就唱不了歌）。
- 新 API：`GET/POST/DELETE /api/settings`、`POST /api/settings/apply-defaults`。
  改動透過 WebSocket 廣播 `SETTINGS_UPDATE`，所有裝置即時同步；
  舞台端一連上就會收到（片頭卡秒數、結算開關都在裡面）。
- 可設定的五類：
  1. **開機預設調音** —— 開機時自動套進共享狀態；也可一鍵「套用到現在」不必重開。
  2. **自動音量平衡** —— 開關與目標響度。
  3. **快取上限與自動清理** —— 每處理完一首檢查一次，超過就從最舊的刪，
     `storage.enforce_cache_limit()` 會跳過演唱中與佇列裡的歌。
  4. **AI 模型** —— Whisper / Demucs 模型改成可選；模型在啟動時載入，
     UI 明示「要重開伺服器才生效」並顯示目前實際運行中的模型。
  5. **舞台演出** —— 片頭卡與結算畫面的開關與秒數（原本是寫死的常數）。
- 前端表單是照後端回傳的 `spec` 長出來的：後端加一個欄位，
  controller 只要補一行標題文字就會自動多一列，不用同時改三個地方。
  滑桿 350ms 防抖才送 API；自己剛動過的 2 秒內不吃廣播重畫（否則手上拖的滑桿會被換掉）。
