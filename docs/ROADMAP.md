## 💡 後續想做的（非必要，想到就補）

### 系統
- [ ] 多包廂（一台伺服器帶多組舞台與佇列）
- [x] 升降 Key 的移調 DSP *(2026-09-24)* —— 這一項不是新功能，是**補上一個一直
      沒接上的功能**。UI、共享狀態、跨裝置同步、README 都齊全，只有舞台端
      沒有人讀 `state.pitch_shift` —— 所以按下去每一個看得到的環節都正常，
      就是聲音沒動，而客人的結論是「這台機器的升降 Key 壞了」。
      做出來的難處全部在「移調不能動到時間軸」：`playbackRate` 兩行就移調了，
      但它同時把速度乘上同一個比例（+6 = 快 41%），而歌詞、導唱音符、
      段落評分、A-B 循環、錄音、兩點校正全部活在 `audio.currentTime` 上。
      所以播放速度一律 1.0，移調在 AudioWorklet 裡自己算。其餘三個決定：
      **原調要旁路**（九成以上的時候都在原調，不該為了沒人用的功能一直背著
      45ms 延遲，而且旁路那條是逐樣本相等、有測試釘住）、**兩個聲道共用同一條
      讀取頭軌跡**（各跑一份會慢慢分家，舞台會聽起來在左右飄）、
      **一顆鍵要牽動四個地方**（伴奏、導唱音符、和聲調性、字幕補償 ——
      後三個沒接上比第一個更難查）。詳見 CHANGELOG 1.24.0。
- [x] 櫃檯管理鎖 *(2026-09-22)* —— 「可以放到店裡」與「只能放在家裡」之間
      那條線。功能本身很小（一組 PIN、一個 token），難的全部在**鎖什麼、
      不鎖什麼**：鎖錯一條的代價不是多按一次密碼，是整個晚上沒有人能唱歌，
      而櫃檯不一定在。所以唱歌的事一律不鎖（點歌、切歌、調音、評分、查歌、
      自己那一次錄音），鎖的判準是「會不會影響到下一組客人，或做完就回不去」。
      清單做成白名單兩張表 + 一條把 app 路由抓出來比對的測試 —— 那條測試才是
      主體，因為三個月後加路由的人不會記得有那個檔案。上鎖不需要密碼
      （關門不需要鑰匙）、閒置自動上鎖（櫃檯忘記鎖是常態）、解鎖綁裝置
      （櫃檯的平板解開不等於包廂每支手機都解開）、壞檔 fail-closed，
      而且忘記密碼一定有解（環境變數／刪檔案，兩條都要碰得到伺服器 ——
      那正是安全邊界）。詳見 CHANGELOG 1.20.0。
- [x] 自動接歌（待機時自己接一首）*(2026-09-20)* —— 商用點歌機的「沒有安靜這個
      狀態」。功能本身三行就寫得完（隨機挑一首播），難的全部在**機器什麼時候
      該閉嘴**：只挑已經備好的歌（不趁大家在聊天時去下載新歌把 CPU 吃光）、
      空了要先等二十秒（別跟正在找歌的人搶）、有人點歌時看「有沒有人已經唱
      進去了」再決定當場讓位還是唱完（45 秒為界）、連著接三首沒人接手就安靜
      （沒有人點歌通常代表沒有人在了）。而且機器接的歌不算任何人的一首 ——
      尤其不進點唱排行，否則照排行挑歌、播出來又計進排行，那條排行三個晚上
      之後就只剩機器自己的回音。詳見 CHANGELOG 1.18.0。

### 字幕對齊
- [x] 每首歌自己的字幕偏移 *(2026-09-22)* —— 「字幕對不上」有兩種原因
      （這台裝置的喇叭延遲、這首歌的 LRC 偏差），以前塞在同一個數字裡，
      所以為某一首爛 LRC 調的 +300ms 會跟著機器走，下一首反而多錯 300ms，
      而且那個錯誤**無聲、無界、會自我增強**。拆開之後最重要的決定是
      「方向鍵動哪一個」：預設動這首歌，因為它的失敗模式**大聲、有界、
      會自己報到**（同方向、差不多的量、每一首都這樣）—— 機器因此看得見它，
      可以主動說「這比較像喇叭的延遲」，但只提示不自動套用。
      另外一個不能錯的地方：偏移只移動字幕，**絕不移動評分**（導唱音符活在
      音訊時間軸上）。詳見 CHANGELOG 1.22.0。
- [x] 對齊品質徽章與「只重算歌詞」*(2026-09-22)* —— 診斷檔一直都在寫，
      只是從來沒出現在畫面上；而「字幕整首歪掉」唯一的修法是那顆貴的
      「重新處理」。難的是**判讀**：沒有診斷檔是「未知」不是 0 分、
      whisper 的 score 恆為 0 是「沒有 LRC 可對」不是「對得爛」、
      placeholder 才是真的該紅；而且分數沒有對人校準過，所以文字是主體、
      數字退到 tooltip。詳見 CHANGELOG 1.22.0。
- [x] 「兩點校正」*(2026-09-23)* —— 解的是第三種症狀「越唱越歪」（抓到的歌詞
      來自變速過的上傳版本）。數學是兩點一線，十行就寫得完；難的全部在
      **那條線值不值得相信**。
      最重要的一個數字是「兩點至少隔 60 秒」：按鍵的反應時間雜訊會被跨距
      **放大**成速度誤差（誤差 ≈ 雜訊 ÷ 跨距），跨距 20 秒時 0.15 秒的手誤
      在四分鐘的歌片尾是 1.8 秒 —— **比不校正更糟**，而且歪在片尾（沒有人
      在那裡盯著字幕）。所以太近的第 2 點當成「重新標記第 1 點」而不是錯誤
      （按錯的人本來就會立刻再按一次，當成錯誤的話那個錯的點就拔不掉了）。
      第二件事是**機器猜得到、猜不準的那一步交給人看**：按下去時只能用時間
      配對「他指的是哪一句」，而字幕正歪著（那就是他按鍵的原因）—— 所以把
      配對到的那一句原文印出來，對錯了再按一次就重標。
      其餘都是「寧可拒絕也不要算出一條錯的直線」：速度不在 0.85×~1.15×、
      先後對不起來、偏移超過 ±2 秒、按鍵離所有句首超過 8 秒，一律拒絕並說出
      下一步。而人的反應時間**刻意不補** —— 那是對兩點都一樣的常數，相減時
      整個消掉，只落在偏移上，而偏移本來就是按一下方向鍵就修得掉的東西。
      詳見 CHANGELOG 1.23.0。

### 查歌
- [x] 歌號點歌（六位數）*(2026-09-21)* —— 商用點歌機上最快的一條點歌路，
      也是包廂裡唯一可以用喊的那一條。功能本身三行就寫得完（給每首歌一個
      流水號），全部的內容是一個**承諾**：這組號碼永遠不會變成別首歌。
      所以刪快取不回收號碼（留墓碑，打進去說「這首已經不在曲庫了」而不是
      給出別人的歌）、同一首回來拿回原號（綁 song_id）、只發給已經備好的歌、
      發號順序照入庫時間所以可重建、號碼簿壞掉寧可整個功能停掉也不重發一套。
      數字鍵刻意**不**照注音鍵盤那樣變灰 —— 變灰的話已下架的號碼打不完，
      而使用者正是為了那句「它去哪了」才來打的。詳見 CHANGELOG 1.19.0。
- [x] 歌星注音索引（歌星查歌）*(2026-09-19)* —— 商用點歌機的「歌星點歌」。
      難的不是鍵盤（跟歌名查歌共用同一副），是**誰跟誰是同一個人**：同一位歌星
      在曲庫裡會長出「周杰倫」「Jay Chou」「周杰倫 Jay Chou」三種寫法，不併的話
      清單上會出現三個周杰倫，每一個手上只有他一部分的歌。併的規則刻意保守
      （整段比、漢字不同就不准併、沒有證據就不猜）：錯併的代價是歌單裡混進別人
      的歌，比漏併嚴重得多。詳見 CHANGELOG 1.17.0。

### 包廂與櫃檯之間
- [x] 服務鈴（包廂呼叫櫃檯）*(2026-09-22)* —— 舞台訊息的反方向，補完包廂與櫃檯
      之間的另一條路。功能本身三行就寫得完（存一筆需求、亮給櫃檯看），難的全部在
      **按下去之後**：一顆沒有回音的鈴會被按第五次，因為按的人分不出「櫃檯看到了、
      正在弄」跟「這顆鍵根本沒作用」。所以同時只有一張未結案的單（再按是併進去，
      櫃檯看到的是一列與「按了 3 次」，不是五列一樣的東西）、併單**不重設等待
      時間**（等最久的那一桌不該因為按最多次而排到最後面）、狀態分四種而且
      一直留在畫面上（跳一下就消失的「已送出」等於沒有回應）、客人可以自己取消
      而且取消與完成在紀錄上分得開。服務鈴的字**一個都不上舞台** —— 台上那個人
      沒有點那份冰塊。詳見 CHANGELOG 1.20.0。

### 商用點歌機還有、這裡還沒有的（下輪可挑）
- [x] 包廂計時與「剩下多久」提醒 *(2026-09-16)* —— 「時間到之後怎麼辦」的答案是
      **不要停正在唱的那一首**：時間到讓它唱完，唱完之後不再播下一首，佇列
      一首都不刪。超時的上限因此是一首歌的長度（可預期），而不是停在副歌那一句
      （不可預期的難堪）。設定頁刻意沒有「立刻停掉」這個選項。詳見 CHANGELOG 1.14.0。
- [x] 舞台跑馬燈訊息 *(2026-09-17)* —— 「它會蓋住歌詞的哪一區」的答案是
      **一區都不蓋**：訊息帶做成版面裡的 flex 元素，出現時把整排 HUD 往下推，
      而不是絕對定位疊上去；歌詞與音準線那半邊完全不動。大字卡只在沒有人
      唱歌的時候出現，播歌中（連緊急訊息也）一律降級成上緣那一條。
      而且它**不捲動** —— 會動的字會一直把餘光拉過去，而唱歌的人正需要那個
      餘光看歌詞。詳見 CHANGELOG 1.15.0。
- [x] 歌名字數／注音首字查歌 *(2026-09-18)* —— 商用點歌機的實體鍵盤查法。
      「查什麼」的答案是**只查已經備好的曲庫**（列出來的每一首都是快取秒播），
      而難的不是鍵盤，是**索引要建在哪一串字上**：YouTube 標題不是歌名
      （「周杰倫 Jay Chou - 稻香 Rice Fields【Official MV】4K」照整串字算，
      字數是二十幾個、注音從「ㄓ」開始），所以先萃歌名本體再建索引；
      多音字則每個讀音都存 —— 只留一個的話，另一半使用者永遠查不到那首歌，
      而且他會以為曲庫裡沒有。詳見 CHANGELOG 1.16.0。
