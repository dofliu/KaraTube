**KaraTube** 是一個隨時指定任何 YouTube 或 YouTube Music 歌曲，即可全自動轉換為專業 KTV 伴唱畫面的現代化卡拉OK系統。

📖 文件：[使用說明書](docs/USER_GUIDE.md)｜[安裝與部署](docs/DEPLOYMENT.md)｜[更新日誌](CHANGELOG.md)｜[功能路線圖](docs/ROADMAP.md)｜[開發進度日誌](docs/PROGRESS_LOG.md)

## 🌟 核心特色

1. **⚡ YouTube 隨選隨唱 (On-Demand Processing)**
   - 支援輸入歌曲關鍵字或直接貼上 YouTube / YouTube Music 網址。
   - 後端全自動流水線：下載 1080p 背景 MV $\rightarrow$ AI 分離伴奏與人聲 $\rightarrow$ 逐字時間軸歌詞對齊 $\rightarrow$ 抽取音高導唱線。
   - 智慧快取機制：點過的歌曲第二次秒播，免重複等待。

2. **🎵 AI 高品質人聲伴奏分離 (Demucs v4 / BS-RoFormer)**
   - 使用深度學習模型分離出純伴奏（Instrumental）與人聲（Vocals）。
   - 前端支援「**原唱/伴奏無段切換**」，隨時可在 0% 純伴奏到 100% 導唱原聲之間自由拉桿調節。

3. **✨ 經典雙行 KTV 逐字平滑變色字幕 (Dual-Line Sweeping Karaoke)**
   - 經典 KTV 雙行交替排版（一行正在唱，一行預備）。
   - 3、2、1 倒數預備光點提示。
   - 毫秒級字元漸變變色動畫（支援中文、英文、日文、韓文）。
   - **歌詞對齊採 LRC 主導、聲學校正**：抓多個 LRC 候選各自對齊，
     以 (scale, offset) 仿射變換修正片頭裁切與變速上傳，再把每行行首吸附到
     人聲軌真實的起唱點，行內逐字依累積人聲能量分配（不是均分）。
   - **播放端補償音訊輸出延遲**（`AudioContext.outputLatency`），
     並提供 ±1 秒即時微調：舞台端按 `←` `→`（Shift 微調 10ms、`0` 歸零），
     或從點歌台／手機的「🎬 字幕同步」滑桿調整，兩端即時同步。

4. **🎯 即時音準導唱線與評分系統 (JOYSOUND / DAM Style Scoring)**
   - 頂部音準線即時顯示旋律音符。
   - 麥克風音高實時捕捉（Autocorrelation / YIN 演算法），繪製玩家音高游標軌跡。
   - 即時 Combo 累積、音準判定（PERFECT / GREAT / GOOD）與歡呼慶祝特效。

5. **🎛️ 專業 KTV 調音與氣氛音效 (Web Audio DSP)**
   - 升降 Key 調節（-6 ~ +6 Semitones），**男調/女調一鍵切換**（♂ 降 4 Key / ♀ 升 4 Key），
     所有裝置 Key 值即時同步。
   - 音樂（伴奏）音量與麥克風音量獨立調節，互不影響。
   - 麥克風效果四個獨立參數：**殘響**（空間感）、**回音音量**、
     **回音重複次數**、**回音間隔**（80~600ms）。回授量與輸出音量走不同的
     增益節點，所以「小聲但多次」跟「大聲但一次」都調得出來，回音也可以真正歸零。
   - **效果風格一鍵套用**：🚪 包廂 / 🎭 劇場 / 🏟️ 演唱會 三種現場感，
     一顆按鈕同時設定殘響與回音四個參數，之後仍可用滑桿微調。
   - 一鍵「乾聲」：現場破音或嘯叫時立刻關掉所有效果。
   - 罐頭氣氛音效：👏 熱烈掌聲、🎉 歡呼口哨、👎 倒喝采。

6. **🏆 熱門點唱排行 (Play Rankings)**
   - 每首歌實際上台演唱時才計數（排進佇列又被移除的不算）。
   - 點歌台「🏆 點唱排行」分頁顯示名次、累計次數與最近演唱日期，一鍵再點一次。
   - 統計存在 `cache/play_stats.json`，重開機不會歸零。

7. **⭐ 我的最愛 (Favorites)**
   - 每張歌卡右上角的星星一鍵收藏／取消收藏常唱歌曲。
   - 點歌台「⭐ 我的最愛」分頁集中管理，最新收藏排最前面，一鍵再點歌。
   - 收藏存在 `cache/favorites.json`，重開機不會消失。

8. **🕘 已唱歷史 (Sung History)**
   - 一次一筆的演唱時間序列：同一首唱三次就有三筆，顯示「唱於 今天 21:34」。
   - 點歌台「🕘 已唱歷史」分頁一鍵再點今天唱過的歌，並統計今天唱了幾首。
   - 歷史存在 `cache/song_history.json`（保留最近 500 筆），重開機不會消失。

9. **🏁 唱畢總評分結算畫面 (Score Settlement)**
   - 整首唱完舞台自動亮出成績單：總分滾動動畫、SSS~C 等級、音準率、最大 COMBO。
   - 顯示「本曲個人最佳」與「擊敗全場 XX% 的演唱」，破紀錄會標示 🎉 刷新個人最佳。
   - 結算顯示 9 秒（秒數可在系統設定調整、點擊畫面可跳過）後自動進下一首；沒人開口唱的純播放不會出結算。
   - 評分歷史與各曲個人最佳存在 `cache/score_history.json`；點歌台與手機端同步收到結算通知。
   - 音準評分與畫面渲染分離：隱藏音準線時照樣計分，結算才公平。
   - **段落評分**：成績單附一張「哪一段唱得最好、哪一段要練」的長條圖（見特色 18）。

10. **🗂️ 快取管理與錯誤重試 (Cache Management)**
   - 點歌台「🗂️ 快取管理」分頁：每首快取歌曲的磁碟用量、完整性徽章、總用量與磁碟剩餘空間。
   - 一鍵 **刪除**（釋放空間）或 **重新處理**（字幕全歪、檔案缺漏時砍掉重跑整條流水線）。
   - 處理中斷的壞資料夾（缺 metadata）也列得出來、刪得掉；演唱中或佇列裡的歌擋住不給刪。
   - 佇列裡處理失敗的歌直接按 🔁 重試，不用重新搜尋點歌。

11. **📱 雙螢幕輸出與手機掃碼點歌**
   - **螢幕 1（點歌台 / 手機控制端）**：搜尋歌曲、管理排隊清單、調音、音效、
     音樂音量、字幕同步、音準線顯示切換、點唱排行。
   - **螢幕 2（舞台大螢幕）**：全螢幕高畫質 MV、雙行卡拉OK字幕、音準導唱線、即時評分。
   - 手機掃描 QR Code 即可連入局域網無線點歌。

12. **🎫 導唱片頭卡與多人包廂暱稱 (Intro Card & Room Nicknames)**
   - 每首歌前奏亮出商用機風格的開場卡：歌名、「演唱者：XXX」、點歌人。
   - 每台裝置（點歌台與每支手機）可設定自己的暱稱，佇列顯示「👤 誰點的」，
     舞台片頭卡同步顯示「點歌:XXX」。不設定也能照常點歌。

13. **↕️ 點歌佇列拖曳排序 (Drag-to-Reorder Queue)**
   - 按住佇列每首歌左側的 ⠿ 把手上下拖曳即可調整演唱順序。
   - 桌機滑鼠與手機觸控都支援（Pointer Events），放手後所有裝置即時同步。

14. **🔊 自動音量平衡 (EBU R128 Loudness Normalization)**
   - 每首歌在處理流水線最後量一次 **整合響度**（ITU-R BS.1770-4 的 K 加權 + 雙重閘門），
     播放時自動補到同一個目標（預設 -14 LUFS），不再「上一首震耳欲聾、下一首聽不到」。
   - 增益夾在 ±12 dB 並做峰值保護（拉完不超過 -1 dBFS），不會把歌拉到破音；
     量不到響度就一律 0 dB —— 寧可不動，也不要亂調。
   - 只作用在伴奏與導唱人聲那條路徑，麥克風與氣氛音效不受影響，
     所以換歌時唱歌的人不會覺得自己的聲音忽大忽小。
   - 啟用前就快取好的舊歌不必重跑流水線：第一次播放時現場量一次並補寫回 metadata。

15. **⚙️ 系統設定頁 (Machine Settings)**
   - **開機預設調音**：音量、Key、殘響／回音四參數、柔化、演唱模式、音準線 ——
     包廂調到滿意的手感存成預設，下次開機直接就位；也可一鍵「套用到現在」。
   - **快取上限與自動清理**：超過上限自動從最舊的歌開始刪，演唱中與佇列裡的絕不刪。
   - **AI 模型選擇**：Whisper（tiny ~ large-v3）與 Demucs 模型，不改程式碼就能換。
   - **舞台演出**：片頭卡與結算畫面的開關與停留秒數，改完舞台端立刻套用。
   - 設定存在 `cache/settings.json`，任一台裝置改動即時同步到所有裝置。

16. **🔁 練唱模式：A-B 段落循環與一鍵副歌重唱 (Practice Loop)**
   - 播到定點按 **A** 標起點、按 **B** 標終點，唱到終點自動跳回起點反覆練唱，
     兩點都設好就直接開始循環（跟商用點歌機一樣，不用再按第三顆鍵）。
   - **副歌重唱**：伺服器分析歌詞的重複結構自動找出副歌，一顆按鈕圈起來循環，
     不必自己聽著抓時間。
   - **段落跳轉**：前奏 / 主歌 / 副歌 / 間奏 / 尾奏 自動切好一排膠囊，
     點標籤跳到該段、點 🔁 直接循環該段；進度條也可以點一下跳過去。
   - A-B 區間是共享狀態：包廂裡每台裝置看到的圈選範圍一樣，舞台右下角常駐
     🔁 徽章標出循環區間（不然台上的人只會覺得機器在跳針）。
   - 換歌自動清掉區間；跳轉不會沒收已經唱到的分數，只清掉音準線上的舊軌跡。

17. **🎼 曲庫分類瀏覽、新歌榜與推薦歌單 (Library Browsing & Recommendations)**
   - 商用點歌機式的「分類點歌」：依 **語言別**（國語／台語／粵語／日語／韓語／英語／其他）
     與 **歌手** 篩選曲庫，再依最新加入／最常點唱／歌名／歌手排序。
   - 語言別由伺服器自動判定：歌名與頻道名的明示標記優先，其次看歌詞的
     諺文／假名／漢字比例，粵語與台語再靠方言專用字（要出現兩種以上才定案，
     避免一個字就誤判）。判定結果寫回 `metadata.json`，每首歌只算一次。
   - 歌手名自動從 YouTube 頻道名還原（`周杰倫 - Topic` → `周杰倫`、`AdeleVEVO` → `Adele`）；
     頻道看起來是唱片公司時，改從「歌手 - 歌名」的標題前半段取。
   - **🆕 新歌榜**：最近 14 天加入曲庫的歌標上 NEW 徽章。
   - **💡 為你推薦**：從點唱紀錄推回下一首，每首都附推薦理由 ——
     「好久沒唱了」「你唱過 XXX，這首還沒唱過」「剛加入曲庫，還沒開嗓過」。

18. **📊 段落評分 (Per-Section Scoring)**
   - 唱畢結算多一張段落表現長條圖：**主歌 1 / 副歌 1 / 主歌 2 …** 各自的命中率與等級，
     並點名 💯 **最佳段落** 與 📈 **待加強段落**。總分 62 分只讓人沮喪，
     「副歌 2 只有 31%、主歌都在 70% 以上」才知道下一輪要練哪裡。
   - 分段沿用練唱模式的曲式分析（`chorus_detector` 由歌詞重複結構算出），
     不必額外標記；前奏／間奏／尾奏沒有導唱音符，自動不列入。
   - 兩道「不亂下結論」的守門：導唱音符不足約 0.5 秒的段落不參加評分
     （一兩幀的運氣不該決定誰最差）；最佳與最差差距不到 5 個百分點就不點名任何段落，
     只顯示長條圖 —— 整首均勻地唱到 55% 時嫌棄某一段是製造焦慮，不是回饋。
   - 練唱模式的 A-B 循環把同一段唱了三輪也算得對：命中率是整段累計的比例。
   - 結論（「最佳：副歌 1 / 待加強：主歌 2」）跟著成績寫進 `cache/score_history.json`，
     點歌台與手機的結算通知也看得到。
   - 逐幀判定與段落累計在 `frontend/js/section-scorer.js`，寫成純資料邏輯，
     由 `node --test` 覆蓋（26 條）。

19. **🎚️ 導唱音量自動 ducking (Guide Vocal Auto-Ducking)**
   - 商用機的「導唱漸弱」（DAM 的 *ガイドボーカル自動フェード*）：導唱人聲不再是開／關兩檔，
     而是跟著唱的人走 —— **唱穩了它自己退到背景，走音或忘詞時立刻回來扶一把**。
   - 曲線刻意做成不對稱：**慢慢退**（時間常數 1.6 秒，退場是背景動作）、
     **立刻回**（0.22 秒，救援不能遲到）。命中率用 2.5 秒（約一句歌詞）的觀察窗，
     短於一句的失誤不會把導唱整個叫回來。
   - **遲滯（Schmitt）門檻** 0.55 / 0.35：命中率在門檻附近抖動時維持現狀，
     不會忽大忽小 —— 那比導唱全開還吵。
   - 前奏／間奏（沒有導唱音符）不改變狀態：那段本來就沒有人聲可退，
     硬要衰減只會讓副歌一進來導唱先大聲一下再退。
   - 開始退場前要先累積 3 秒有效演唱（暖機），第一個音唱準不算穩定；
     深度上限 0.95，**永遠留一點導唱在背景當安全網**，不會整個消音。
   - 導唱音量本來就轉到 0（純伴奏）時完全不作用；舞台右下角以 🎚️ 徽章
     標出「導唱自動淡出 XX%」，免得被當成機器把導唱吃掉了。
   - 唱畢結算多一行 **導唱獨立度**：這首歌有多少比例的時間你不需要導唱帶
     （導唱沒開、或唱不到 20 秒不足以判斷時就不顯示，不硬給數字）。
   - 純資料邏輯在 `frontend/js/guide-ducker.js`，由 `node --test` 覆蓋（17 條）；
     深度與開關在點歌台的系統設定頁，改完舞台端立刻生效。

20. **🎤 麥克風自動增益 (Mic Auto Gain Control)**
   - 包廂裡最常見的抱怨不是音準也不是效果，而是「**換人唱就要重調麥克風音量**」：
     上一位貼著麥克風吼、下一位離 20 公分小聲哼，輸入電平可以差 20 dB 以上。
     機器自己把每個人拉到同一個目標電平（預設 **-18 dBFS**，設定頁可調）。
   - **前饋（feed-forward）而不是回授**：量的是麥克風原始訊號（analyser 接在增益節點**之前**），
     算出來的倍率套在後面。反過來量已放大的訊號會變成「放大 → 量到更大 → 少放大」的
     呼吸迴路，而且它的時間常數跟房間殘響耦合在一起，現場幾乎調不出來。
   - 三條安全規則（順序就是優先度）：
     1. **沒人唱時絕不加增益**（噪音閘門 -45 dBFS）。安靜房間也有底噪，
        照著「拉到目標」算下去會加到上限，第一個字直接爆掉，多人模式當場嘯叫。
     2. **要降立刻降（0.25 秒）、要升慢慢升（3 秒）**。降是保護、升是舒適；
        升太快會把句與句之間的底噪一起抬起來，聽起來像機器在呼吸。
     3. **範圍夾住**：最多 +9 / -12 dB，且**多人模式的加成上限收到 +6 dB** ——
        人聲外放時每多加 1 dB 就離回授近 1 dB。
   - **削峰保護**：預估輸出（原始電平 + 目前增益）超過 -6 dBFS 就用 0.06 秒的
     時間常數立刻降，無視暖機與遲滯。保護線是「速度地板」不是「不准再降的地板」——
     目標電平要求降得更多時聽目標的，否則音量會被鎖在剛好不削峰的最大聲。
   - **遲滯而不是死區**：差不到 1 dB 不「開始」調整，但一開始調就一路調到位。
     寫成死區的話每次都會停在離目標 1 dB 的地方，系統性地永遠差一格。
   - 增益走**獨立的 gain 節點**（`micAgcGain`），跟使用者的麥克風音量滑桿分開，
     自動調整動過之後滑桿刻度仍然對得上；節點位置在 limiter **之前**，
     所以判斷失誤（咳嗽、拍打麥克風）還有 limiter 擋著。
   - 換麥克風時歸零重學（動圈換電容靈敏度差很遠）；**換歌只清統計、保留學到的增益**
     （同一個人常唱好幾首，歸零只會讓每首第一句都先小聲三秒），並重新暖機 1.2 秒。
   - 舞台端按 `S` 的面板有**即時收音電平表**（太小聲偏左灰、正常青色、快削峰轉粉紅）
     與自動增益讀數 —— 麥克風沒插好、選錯裝置、靜音鍵沒開，在這裡三秒就看出來。
     機器補償超過 ±1 dB 時舞台右下角亮 🎤 徽章。
   - 唱畢結算會給**能動手的建議**：平均一直 +3 dB 以上＝麥克風可以拿近一點；
     一直 -3 dB 以下或曾啟動削峰保護＝拿遠一點。差不到 3 dB 就不出現。
   - 純資料邏輯在 `frontend/js/mic-agc.js`，由 `node --test` 覆蓋（24 條）；
     開關與目標電平在點歌台的系統設定頁，改完舞台端立刻生效。

21. **🌙 排程預處理 (Scheduled Batch Pre-processing)**
   - 隨選處理的代價是「第一次點一首新歌要等好幾分鐘」。這一頁把等待挪到沒人唱歌的時候：
     晚上把整張 **YouTube 播放清單**（或一堆網址、關鍵字混著貼，一行一個）丟進
     點歌台的「🌙 排程預處理」分頁，機器在設定的時段裡自己跑完整條流水線，
     隔天所有歌都是「⚡ 快取秒播」。
   - **有人在唱歌就讓開**：流水線吃滿 GPU 與 CPU，跟現場演唱搶資源會讓舞台掉幀。
     所以每處理完「**一首**」就重新確認一次現場狀況 —— 不是每批確認一次，
     客人推門進包廂點第一首歌時，機器最多再忙一首歌的時間就會把資源讓出來。
   - **時段是預設，不是牢籠**：預設 02:00–06:00，**跨午夜**（23 → 6）照樣成立，
     起訖設成同一小時 = 全天候。臨時要跑就按「⚡ 立即開始」跳過時段限制
     （但「有人唱歌就讓開」仍然有效），跑完自動收回，下一批照樣照表操課。
   - **一首失敗不拖垮整批**：影片被下架、網路斷線只標記那一首並繼續下一首，
     事後按「🔁 重試失敗」只重跑壞掉的那幾首，不用整批重來。
   - **已在曲庫的自動略過**（看四個必要檔案是否齊全，而不是只看 metadata ——
     只看 metadata 會把處理到一半的殘留資料夾誤判成完成，那首歌就永遠不會被補跑）。
     貼一張 30 首的清單通常會直接顯示「其實只有 3 首要跑」。
   - **重開機續跑**：任務存在 `cache/batch_jobs.json`，上次中斷在半路的那首退回等待重跑，
     使用者按過的「立即開始」也會被記住 —— 半夜按下去然後機器重開，意圖不該被吃掉。
   - 進度以 WebSocket `BATCH_UPDATE` 廣播，所有裝置即時看到「現在跑到哪一首、
     為什麼還沒開始」；狀態列永遠寫著原因（等時段／有人在唱／功能被關掉）。
   - 顯示邏輯（上百首時畫面挑哪幾首、時段字串、狀態燈）在
     `frontend/js/batch-view.js`，由 `node --test` 覆蓋；
     排程判斷與任務生命週期在 `backend/services/batch_scheduler.py`，pytest 27 條。

22. **🎶 和聲 / 雙聲部 (Auto Harmony)**
   - 商用點歌機的 **HARMONY** 鍵：一個人唱，喇叭出來像兩個人 ——
     系統把麥克風訊號即時移調，疊在旋律的**三度／五度／低八度**上。
   - 移調量**依這首歌的調性照音階算**，不是固定升幾個半音。以 C 大調為例：
     Do 的上三度是 Mi（+4），但 Re 的上三度是 Fa（**+3**）。
     固定 +4 會唱出 Fa♯ —— 那是 G 大調的音，在包廂裡就是當著客人的面走音。
   - 五個聲部：**三度**（最標準）、**下三**（主唱在高音區時往下疊比較穩）、
     **五度**（空心開闊，適合搖滾與台語歌長音）、**八度**（男聲厚度）、
     **雙聲**（上三度＋低八度，最接近對唱的聽感）。
   - **判不出調性就退成低八度疊唱**（音符太少、念白／饒舌、歌詞還沒處理好）。
     八度在任何調、任何音都不會錯 —— 寧可少一點花樣，也不要有一半機率唱出調外音。
   - **沒人唱就不出聲**：和聲是把麥克風訊號移調再疊回去，
     沒人開口時疊出來的是升高八度的呼吸聲、椅子聲與空調聲，非常明顯而且很吵。
     需要音階資訊的聲部在前奏／間奏（沒有導唱音符）也安靜。
   - 音量上限夾在 **0.85**，**永遠不會蓋過主唱**；低八度再自動收一點
     （低頻能量集中，同樣的增益聽起來重得多，會吃掉主唱的清晰度）。
   - 和聲屬於人聲，跟主唱吃同一個「人聲外放」總開關與同一組殘響／回音 ——
     **單人模式（人聲不進喇叭）聽不到和聲**，這是刻意的：和聲從喇叭出去會被
     麥克風收回來再移調一次，那條路徑會一路往上疊，比單純的回授更難止。
   - 舞台右下角 🎶 徽章常駐顯示聲部與**判到的調性**（「和聲 上三度（C 大調）」）——
     和聲聽起來不對時，「機器把這首歌判成什麼調」是唯一有用的線索。
   - 移調 DSP 在 `frontend/js/harmony-worklet.js`（AudioWorklet，音訊執行緒），
     和聲規劃（調性判定與音階度數）在 `frontend/js/harmony-planner.js`，
     兩者都由 `node --test` 覆蓋（39 條，含「220Hz 要求升八度，量出來是不是 440Hz」
     的數值驗證）。細節見下方〈🎶 和聲是怎麼算出來的〉。

23. **🎤🎤 對唱模式 (Duet Mode)**
   - 商用點歌機的**男女對唱評分**：兩支麥克風各自計分，
     舞台上一塊 **DUET SCORE** 計分板兩條分數即時跳，領先的那一位亮起來。
   - 唱完的結算畫面把兩個人的成績**並排比出勝負**（分數、等級、音準率、COMBO），
     每一位的「本曲個人最佳」也各自記 —— 有名字的人「刷新紀錄」指的是刷新**自己**的紀錄。
     再往下是**段落對決**：哪一段是誰的主場（見特色 24）。
   - **串音判定是這個功能的全部難處**：兩支麥克風在同一個房間，
     A 唱歌時 B 的麥克風也收得到。不處理的話 B 只要舉著麥克風站著就會有
     跟 A 差不多的分數 —— 而且**畫面上完全看不出異狀**（分數在跳、Combo 也在累計），
     現場沒有人有辦法發現分數是假的。判定規則見下方〈🎤🎤 對唱的串音是怎麼判的〉。
   - **兩種接法**：兩支 USB 麥克風（各自一個輸入裝置），或兩支麥克風接同一台
     立體聲音效介面／混音器（**左聲道 = A、右聲道 = B**，這是包廂真正的接法）。
     介面只給單聲道時會明確拒絕 —— 悄悄退回單聲道的話 B 麥拿到的是 A 的複製品。
   - **只有一個人唱就不比勝負**：對唱開著但另一支麥克風放在桌上很常見，
     那時候亮出「A 勝 B」不是比賽而是誤會，直接顯示那一位的單人成績單。
   - 音準畫布同時畫兩條軌跡（**A 桃紅、B 青綠**），第二支麥克風有自己的
     收音電平表與自動增益（兩個人的距離不可能一樣）。
   - 對唱模式下和聲只疊在 A 麥上 —— 第二支麥克風本身就是第二個聲部。

24. **🎼 段落對決 (Duet Section Duel)**
   - 「誰贏」只是一個數字，**「哪一段是誰的主場」**才是包廂裡真正會吵起來的東西。
     對唱結算畫面把同一段落兩位的命中率**往中間對拉**成一排長條圖
     （左邊 A、右邊 B、段落標籤釘在正中間），掃一眼就知道副歌是誰撐起來的。
   - 上方一行比數（「小明 2 段・小美 1 段・平手 3 段」），
     再加上各自的**主場段落**（領先最多的那一段），也一併記進評分歷史。
   - **分段接唱不算勝負**：對唱歌曲本來就是主歌 1 你唱、主歌 2 我唱、副歌一起唱。
     只有一個人唱的段落標成「由 X 主唱」並淡化，沒唱的那一邊顯示「—」而不是 0%——
     畫成 0% 看起來像「唱了但完全沒中」，那是兩件完全不同的事。
   - **參與量差太多也不比**：跟一句（40 幀）與唱滿整段（400 幀）的命中率不是
     同一件事，參與量比例低於一半就退成「這一段主要是他唱的」。
     差距不到 5 個百分點算平手（門檻與段落評分共用一組，兩張成績單不會互相打嘴）。

25. **🌌 情境背景 (Ambient Stage Background)**
   - 沒抓到 MV 的歌不再是一片黑（那看起來像「這首歌壞掉了」），
     改放會跟著音樂動的情境視覺，底圖是這首歌的封面放大模糊。
     待機（沒有歌）時同樣有畫面 —— 商用點歌機的待機情境畫面。
   - **抓到的 MV 其實是一張圖也算數**：YouTube 上大量「音樂版／歌詞版」上傳
     其實是一張靜態圖配四分鐘音訊，檔案是有的，所以「有沒有 MV」會回答「有」。
     舞台每 1.2 秒把畫面縮成 32×18 取一次樣，連續幾筆都幾乎沒有差異就判定
     「這是一張圖」，換成情境背景（判定約 5 秒完成，通常還藏在片頭卡後面）。
   - **五種主題**：極光、星空、霓虹、海洋、燭火。「自動」會依歌曲**固定**挑一個 ——
     同一首歌昨天是星空今天是霓虹，第一個反應會是「機器怎麼怪怪的」。
   - **背景不准閃**：舞台螢幕在暗房間裡佔滿整面牆，所以亮度走限速器
     （每秒最多變 0.45，等效閃爍遠低於光敏性癲癇的 3 Hz 安全線）。
     鼓點只推「動態」（粒子、波形），永遠不碰亮度。
   - **背景不准跟歌詞搶**：亮度被主題錨點、設定頁的亮度上限、字幕區的 vignette
     壓三道；設定頁可一路調到只剩 30%，也可以整個關掉（回到黑畫面）。
   - **成本是最低優先**：30fps 上限、半解析度畫布（柔邊交給 GPU 的 CSS blur）、
     分頁看不見就完全不畫，並量測每幀成本自動降級 ——
     背景掉幀沒人會發現，字幕與評分掉幀所有人都會。

26. **📈 跨場次段落趨勢 (Cross-session Section Trends)**
   - 段落評分（特色 18）說的是「**這一次**哪一段唱壞了」，而那句話每次都不一樣。
     這一項說的是「**每一次**」：同一首歌唱滿三次之後，結算畫面與點歌台的
     「📊 我的成績」分頁會告訴你「這首歌的副歌 2 你一向掉 13 個百分點」。
   - **比的是形狀，不是高度**：每一場先減去**那一場自己的平均**再累積。
     直接平均的話算出來的是「這個人的嗓子好不好」—— 感冒那天每一段都掉
     15 個百分點，平均下來每一段看起來都是弱點。
   - **三道門才開口**：至少三場、幅度至少 5 個百分點（與段落評分共用門檻）、
     方向一致（至少三分之二的場次同方向）。第三道是關鍵：平均值分不出
     「三次都掉一點」與「兩次正常、一次崩掉」，但這兩件事該講的話完全不同。
   - **曲式變了就重新累積**：歌曲重新處理後切出來的段落可能不一樣，
     「副歌 2」在新舊兩版不是同一段。只比對段落組成相同的場次，以最新一場為準。
   - **每個人分開算**：段落弱點是這個人的弱點；三個人的副歌混成一筆平均，
     算出來的是這首歌的副歌難不難唱。對唱模式兩位各自累積各自的趨勢。
   - 場次不夠時明講「再唱 N 次就能看出來」而不是留白，
     並在累積到四場後告訴你這段期間是在進步還是在退步。

27. **🎙️ 錄唱回放 (Performance Recordings)**
   - 分數說的是「唱得好不好」，錄音說的是「唱起來是什麼樣子」。
     每一次演唱（伴奏＋麥克風的混音）都錄下來，點歌台的
     「🎙️ 錄唱回放」分頁就地播放、下載、標記保留（📌）。
   - **預設關閉**，而且是唯一「不開就完全不動作」的功能：錄音錄到的是包廂裡
     所有人的聲音。錄著的時候舞台左上角常駐紅點「錄音中」，
     設定頁關掉的當下就停手並丟掉手上那一段，歌暫停時錄音也跟著暫停。
   - **錄的是喇叭音量之前的混音**（音訊圖上的 `mixBus`）：有人把喇叭轉小
     甚至靜音，錄下來的不該跟著變小 —— 錄音要的是這首歌唱成什麼樣子，
     跟包廂當下開多大聲是兩件事。
   - **唱太短的不留**（預設 10 秒）：判斷用的是「唱了多久」而不是「錄了多久」，
     而且累計的是時間不是幀數（30fps 與 120fps 的機器否則會差到四倍）。
   - **配額是磁碟保險絲**（預設 50 首 / 512 MB，可調）：錄音與歌曲快取共用
     同一顆磁碟，超過時從最舊、沒有標記保留的那一筆開始刪，九成就先提醒。
   - 切歌照樣留（唱了兩分鐘才被切掉，那兩分鐘一樣是一次演唱）、
     重唱直接丟（評分已歸零，留著會配上一份對不起來的成績）。

28. **🔗 錄音分享 (Share Links)**
   - 唱完那一句「傳給我」在這裡結案：在錄音那一列按 **🔗 分享**，
     產生**有時效**的連結與 QR，當事人用自己的手機掃走，
     在獨立的分享頁（`/share/<token>`）播放或下載。
   - **不是「開啟一次就作廢」的一次性連結**：播一個音檔不是一次請求
     （拖進度條的 Range、Safari 的第二次請求），第一個請求就燒掉連結的話，
     壞掉的是當事人自己的播放。所以「一次性」在這裡是**時效性**：
     預設 24 小時自動失效、隨時可撤銷，另可設「下載幾次就失效」
     （**只算明確的下載**，播放不算）。
   - **沒有「永不過期」**（上限 30 天）：錄到的是包廂裡所有人的聲音，
     一個永遠有效又不需要登入的公開連結，事後想收也收不回來。
   - **連結跟著錄音一起死**：錄音被刪除或被配額無聲擠掉時，
     舊連結立刻打不開，而且講的是「這一次的錄音已經不在了」而不是
     「連結不存在」—— 後者會被理解成網址打錯，於是他會一直重掃。
     失效的四種原因（過期／撤銷／次數用完／錄音不在了）分開講。
   - 分享頁是獨立的一頁，只載入自己那一份樣式（手機上的行動網路），
     歌名與演唱者一律 `textContent` 塞入（那是 YouTube 抓回來的字串）。
   - 連結指向這台機器的網址，**預設只在同一個網路裡打得開**；
     要讓人帶回家聽，設 `KARATUBE_PUBLIC_HOST` 指到對外位址。

29. **🎧 錄音轉 MP3 (MP3 Transcoding)**
   - 帶走那一次還不夠，要**在帶去的地方打得開**：錄音是瀏覽器錄的
     webm/Opus（Safari 是 mp4/AAC），而車上的 USB、長輩的舊手機、
     傳進群組裡直接點開的那些地方，多半只認 MP3。
     錄音那一列多一顆 **🎧 MP3**，分享頁上也有一顆。
   - **按下去才轉**：一個晚上錄三十首、會被帶走的大概三首，錄完就轉等於
     拿正在放歌的 CPU 去換沒人要的檔案。轉好的留著當快取，第二次是秒回。
   - **MP3 快取永遠不會擠掉任何一次演唱**：它有自己的上限（錄音配額的 1/4，
     額外佔用，畫面上寫出來），滿了從**最久沒用到**的那一份開始刪 ——
     演唱刪掉就沒有，MP3 再轉一次就有，兩邊不該用同一個配額。
   - **同一筆同時只轉一次、整台機器同時只轉一個**：前者擋「按了沒反應
     所以再按一次」，後者擋一桌人同時下載把 CPU 從舞台那邊搶走。
   - **ffmpeg 不在就把按鈕收起來**，並且分得出「設定頁關掉了」與
     「機器上沒有 ffmpeg（或那個 ffmpeg 沒有 libmp3lame）」—— 兩者要做的事
     完全不同。裝好之後在設定頁按重新偵測即可，不必重開伺服器。
   - ID3 標籤帶歌名與演唱者（車機螢幕顯示的就是這個），44.1kHz／預設 192 kbps。

30. **📦 整晚打包下載 (Night Export)**
   - 分享連結是「一個人帶走自己那一首」，這一條是**收場時的那句話** ——
     「今天晚上的通通給我一份」。錄唱回放最上面多一條打包列，
     按 **⬇️ 打包下載** 把一整場包成一個 zip，旁邊的選單可以只要某一位唱的。
   - **一場不是照日曆日期切的**：包廂的一場是「九點唱到凌晨兩點半」，
     照日期切會把它剖成兩半，唱到最嗨的後半還會被標成「隔天」。
     改成照**空檔**切（預設相隔 6 小時算換一場，設定頁可調）；
     畫面上跨午夜的場次寫成 `今晚 21:05 – 隔天 02:30`。
   - **邊打包邊送**：不先在磁碟上生一份 zip —— 一場 200 MB 就要另外佔
     200 MB，而錄音配額存在的理由正是「這顆磁碟會被塞爆」。
   - **zip 裡的檔名帶序號與時間**（`01 21-05 月亮代表我的心 - 阿明.webm`），
     車機與檔案總管照檔名排序，解開之後今晚的順序還在。
   - **附一份 `曲目.txt`，而且是最後一個項目**：它是打包完才生出來的，
     所以連「哪幾首沒包進來」（當下剛好被刪或被配額擠掉的）都講得出來。
   - **同時只打一包**（一包幾百 MB，而那條網路正是舞台在用的）；
     打包這條路**只在點歌台出得來**，不掛在分享 token 底下 ——
     一個 zip 是整場所有人的聲音，那不是掃 QR 的人該拿得到的東西。

## 🧪 測試與 CI

```bash
# 後端（471 條）
pip install -r requirements-dev.txt
python -m pytest tests/ -v
ruff check .

# 前端純邏輯（249 條，用 Node 內建測試執行器，不需要 npm install）
node --test "frontend/tests/*.test.js"
```

重的 AI 模型（Demucs / Whisper / librosa）都是延遲載入，
所以整個 FastAPI app 可以在不裝 torch 的環境直接 import 起來測。
GitHub Actions 會在每個 PR 自動跑：後端 `compileall` + `ruff` lint + `pytest`、
前端 `node --check` 全 JS 語法檢查 + `node --test` 單元測試、
以及部署檔驗證（`docker compose config` + `docker build --check`）。
不在 CI 裡真的建映像 —— PyTorch 那層要幾 GB，但「一鍵部署壞在一個 YAML 縮排上」
是最不該發生的事，所以語法一定檢查。lint 規則見 `ruff.toml`。

前端測試只涵蓋能脫離瀏覽器執行的純資料邏輯
（目前是段落評分、導唱自動 ducking、麥克風自動增益、排程分頁與跨場次趨勢的
顯示邏輯、錄唱回放的「要不要留」規則，以及和聲的調性判定與移調 DSP）。
這類判斷在真實包廂裡看不出對錯 —— 沒人知道機器說「副歌唱得最差」是不是算對的 ——
所以寫成不碰 DOM、不碰 Web Audio 的模組，用測試守住。
`node --test` 的路徑要傳 glob（`"frontend/tests/*.test.js"`），傳目錄會被當成模組 require。

另外有一支不測邏輯、只測**載入**的 `frontend/tests/script-scope.test.js`。
舞台與點歌台的 JS 是用 `<script src>` 載進同一個全域作用域的，兩支檔案在最外層
宣告同名的 `const` 會讓後載入的那一支在解析階段丟 SyntaxError 而**整支不執行**
（真的發生過：`mic-agc.js` 與 `duet-scorer.js` 都有 `SILENCE_DB`，
舞台的 `player.js` 因此整支停在 `new DuetScorer()` 那一行）。
這種錯 `node --check`（一次一支）與 `node --test`（各自獨立作用域）都測不到，
所以照 HTML 實際載入的清單另外檢查一次。

執行中的版本可以直接問系統，不用猜（回報問題時請附上）：

```bash
curl -s http://localhost:8080/api/version
# {"name":"KaraTube","version":"1.6.0","codename":"Never Black"}
```

點歌台的 **⚙️ 系統設定** 頁尾也會顯示版本。

版本號的**唯一真相來源**是 `backend/version.py` —— FastAPI 的 `version=`、
`/api/version`、發布打包全都讀那一個常數。發布時三個地方必須一致：
git 標籤、`backend/version.py`、`CHANGELOG.md` 最上面那一筆。
`tests/test_version.py` 守住後兩者，`release.yml` 進一步比對標籤 ——
發出去的東西版本號對不上，是最難追的一種問題。

```bash
# 維護者發布流程
# 1. 改 backend/version.py 的 __version__
# 2. CHANGELOG.md 最上面加一筆 ## [x.y.z] - YYYY-MM-DD
```

標籤推上去後 `release.yml` 會先跑完整 CI 與版本一致性檢查，

## 🎬 字幕同步

歌詞對得準不準由兩層決定，兩層都可以單獨檢查：

**後端對齊**（`backend/pipeline/lyrics_aligner.py`）
每首歌處理完會在 `cache/songs/<id>/alignment.json` 留下對齊診斷：

```json
{ "source": "lrc", "scale": 0.996, "offset": 0.4, "score": 0.577, "recall": 0.967, "lines": 47 }
```

- `source` — `lrc`（採用線上歌詞時間軸）或 `whisper`（找不到可信歌詞，改聽人聲轉錄）
- `scale` / `offset` — 相對原始錄音估出來的變速與偏移
- `score` — 行首落在真實起唱點的程度，**低於 0.28 會自動改走 Whisper 路徑**
- `recall` — 有多少比例的人聲被歌詞行覆蓋到，可用來抓「LRC 少了一段副歌」

改過對齊邏輯後，用下面的指令重算已快取的歌：

```bash
python rebuild_lyrics.py
```

只重算單一首、或只檢查現況不動檔案：

```bash
python rebuild_lyrics.py bu7nU9Mhpyo
```

```bash
python rebuild_lyrics.py --check
```

**播放端延遲**
`AudioContext.outputLatency` 會自動補償（Windows WASAPI 常見 40~200ms），
但藍牙喇叭、外接混音器、HDMI 電視的延遲量測不到，需要手動補：

- 舞台螢幕：`←` `→` 每次 50ms，`Shift + ← →` 每次 10ms，`0` 歸零
- 點歌台 / 手機：底部「🎬 字幕同步」滑桿

調整值會存在舞台端瀏覽器的 localStorage，下次開機自動沿用。

## 🔁 練唱模式與副歌偵測

副歌在哪裡沒有人會手動標，所以 KaraTube 自己找（`backend/pipeline/chorus_detector.py`）。

作法是**純文字重複結構分析**，不碰音訊：歌詞時間軸在流水線裡已經對齊好了，
而副歌的定義本來就是「整段歌詞重複出現的區塊」，所以拿逐行文字找
「最長、重複最多次的連續區塊」就夠了 —— 比做音訊自相似矩陣便宜好幾個數量級，
而且找到的行可以直接對回它自己的時間。

1. 每行歌詞先正規化（去標點、去空白、轉小寫），不同來源的 LRC 標點寫法才不會被判成兩句。
2. 對每組起頭相同的行往下延伸，取出所有「出現過至少兩次」的連續區塊（含其前綴）。
3. 評分挑冠軍：先看涵蓋的總行數（重複次數 × 每次行數），同分時偏好「一次比較長」的區塊 ——
   完整四行的副歌比兩行的鉤子更像使用者想練的那一段。
4. 時間長度守門：低於 5 秒（跳針）或超過 100 秒（抓到整段主歌+副歌）的候選一律淘汰，換下一名。
5. 全部落空時退一步找「重複三次以上的單行鉤子」（口水歌），再找不到就回 `null`，
   前端退回手動設 A-B 點，不會壞。

段落切分則靠唱句之間的靜默：空超過 6 秒就算換段，切出前奏 / 主歌 / 副歌 / 間奏 / 尾奏。

```bash
curl http://localhost:8000/api/songs/<song_id>/sections
```

```json
{
  "chorus": { "start": 61.5, "end": 92.2, "lines": 4, "repeats": 3, "confidence": 0.8 },
  "sections": [ { "index": 0, "kind": "intro", "label": "前奏", "start": 0, "end": 12.4 } ]
}
```

分析是即算即回的純函數，不寫檔也不需要快取；A-B 區間本身放在共享狀態裡，
所以點歌台、手機、舞台看到的圈選範圍永遠一致。

## 📊 段落評分是怎麼算的

同一份曲式分析除了拿來練唱，也拿來回答「這一輪我哪一段唱壞了」
（`frontend/js/section-scorer.js`）。

評分心跳每一幀本來就會判定三件事：此刻有沒有導唱音符（這一幀算不算分母）、
有沒有唱出聲音、唱得準不準。段落評分不重算任何判定，只是把同一幀的結果
**依時間歸到所屬段落**再累計一份：

1. 段落清單先正規化 —— 濾掉前奏／間奏／尾奏（沒有導唱音符，列出來只會是一排 0%）、
   丟掉時間軸壞掉的資料、依起點排序，並丟掉與前一段重疊的段落
   （重疊會讓「一個時間點只對到一段」的前提失效，寧可少評一段也不要對錯段）。
2. 時間 → 段落用**二分搜尋**，不用「記住上一段往前掃」：A-B 循環與進度條跳轉
   會讓時間任意前後跳，線性游標在那些情境下會退化成每幀重掃整首。
3. 每段的命中率 = 該段命中幀 ÷ 該段有導唱音符的幀，所以 A-B 循環把副歌唱三輪
   也算得對 —— 那是整段累計的比例，不是最後一輪覆蓋前面。
4. 等級門檻與整首總評共用同一份表（SSS ≥ 75% … C），單段評語與總評的手感才一致。

兩道「不亂下結論」的守門，是這個功能真正的難點：

- **太短的段落不參加評分**：導唱音符不足約 0.5 秒（60fps 下 30 幀）的段落只標成
  「未評分」。一兩幀的運氣不該決定誰是最差的段落。
- **表現太平均就不點名**：最佳與最差差距不到 5 個百分點時，`best` / `worst` 都回 `null`，
  前端只畫長條圖不下結論。整首均勻地唱到 55% 時說「副歌 2 是你最差的段落（54%）」
  是在製造焦慮，不是回饋。
  （差距要先四捨五入再比門檻：`0.6 - 0.55` 在浮點裡是 `0.049999…`，
  直接比會讓「剛好差 5 個百分點」這個邊界隨機失效。）

可評分段落不到兩段（沒歌詞、只唱了一段就切歌）時整塊收起來，
總分、等級、音準率照常顯示 —— 段落評分是加分項，不是必要條件。

## 📈 「你一向強在哪一段」是怎麼算的

段落評分回答的是**這一次**，而那句話每次都不一樣。跨場次趨勢
（`backend/services/section_trends.py`，純函式）回答的是**每一次**：
資料來源就是 `cache/score_history.json` 裡每一場存下來的段落命中率。

### 為什麼不能直接把每次的命中率平均起來

那樣算出來的是「這個人的嗓子好不好」，不是「哪一段是弱點」：

```
        主歌 1   副歌 1        ← 同一個人、同一首歌
第 1 場   80%     50%
第 2 場   78%     48%
第 3 場   50%     20%          ← 感冒了，整體掉 30 個百分點
```

直接平均的話第三場會把兩段一起往下拉，**每一段看起來都變弱了**。
但這個人的形狀從頭到尾沒變：副歌一向比主歌低 15 個百分點。

所以每一場**先減去那一場自己的平均**，累積的是偏差而不是絕對值。
減平均時刻意不照音符數加權 —— 加權的話最長的那一段（通常就是副歌）
會主導基準線，等於拿副歌跟副歌自己比，永遠顯示不出副歌是弱點。

### 三道門才開口說「一向」

| 門檻 | 值 | 沒有它會怎樣 |
|------|-----|-------------|
| 場次數 | 同一曲式至少 3 場 | 唱一次就說「你一向如何」是在唬人 |
| 幅度 | 平均偏差 ≥ 5 個百分點 | 與段落評分共用門檻，兩張成績單不會互相打嘴 |
| 方向一致性 | ≥ 2/3 的場次同方向 | 平均值分不出「三次都掉一點」與「一次崩掉」 |

第三道最容易被忽略也最重要：兩次正常、一次副歌崩掉，平均偏差可以跟
「三次都掉 9 個百分點」一模一樣，但前者該說的是「那天狀況不好」，
後者才是「這一段要練」。把前者講成「你一向掉副歌」是在誣賴人，
而使用者知道那不是真的 —— 然後整塊功能就不可信了。

### 曲式變了就從那一場重新累積

歌曲重新處理（換模型、歌詞來源變了）之後 `chorus_detector` 切出來的段落
可能多一段主歌，後面所有編號往後挪一位 —— 這時候「副歌 2」在新舊兩版
指的不是同一段。所以每一場存一份**曲式指紋**（可評分段落的標籤依序排成一列），
只比對指紋相同的場次，並以**最新一場**的曲式為準
（用舊曲式的多數決的話，重新處理之後新資料永遠進不來）。

其他幾個刻意的決定：

- **每個人分開算**（`song_id` + 演唱者）。段落弱點是**這個人**的弱點；
  三個人的副歌混成一筆平均，算出來的是這首歌的副歌難不難唱。
- **只看最近 20 場**。唱了五十次的歌，半年前的唱法不能拿來說「一向」，
  而且人真的會進步，舊資料會把進步稀釋掉。
- **累積到 4 場才談進步／退步**（每場平均命中率的迴歸斜率 × 跨越場次，
  總變化超過 5 個百分點才下判斷）。3 場的斜率太容易被單一場次帶著走。
- **場次不夠時明講「再唱 N 次」**，不是留白 —— 使用者才知道這塊不是壞了。

畫法是往中間對拉的長條圖，但**中線的意義與段落對決不同**：
對決的中線是「兩個人之間」，趨勢的中線是「**這個人自己的平均**」，
往右是主場、往左是弱點。畫絕對命中率的話看到的是這首歌哪一段難唱，
不是這個人哪一段弱，而後者才是要練的東西。
沒被點名的段落畫淡色而不是藏起來：那是「還沒有結論」，不是「剛好等於平均」。

相關 API：`GET /api/scores/{song_id}/trend?singer=`（單曲）、
`GET /api/scores/trends`（總表，點歌台的「📊 我的成績」分頁用）。
`POST /api/scores` 的回應也直接帶趨勢，舞台端唱完不必再打一次 ——
而且那份趨勢**含剛唱完的這一次**：今天明明唱好了副歌，畫面還說副歌是你的弱點，
是最傷人的那種不一致。

## 🎙️ 錄唱回放是怎麼錄的

開關在 ⚙️ 系統設定 → 🎙️ 錄唱回放，**預設關閉**；錄好的在點歌台的
「🎙️ 錄唱回放」分頁。錄音在**瀏覽器端**做（`MediaRecorder`），
伺服器只負責存檔與生命週期。

### 接在音訊圖的哪一點

```
伴奏 ┐
導唱 ┤
麥克風＋效果 ├─→ mixBus ─→ masterGain ─→ 喇叭
罐頭音效 ┘        │
                   └─→ MediaStreamDestination ─→ MediaRecorder ─→ 上傳
```

錄音接的是 `mixBus`，也就是**喇叭音量之前**。接在 `masterGain` 之後比較省事，
但那是喇叭音量：有人接電話把喇叭轉小，錄下來的就跟著變小，轉到靜音那一首就沒了。
錄音要的是「這首歌唱成什麼樣子」，跟包廂當下開多大聲是兩件事。

`MediaStreamDestination` 只建一次並重複使用 —— 每首歌建一個新的會在
AudioContext 裡累積節點（只要還連著就不會被回收），唱一整晚之後
`mixBus` 上會掛著幾十個沒人讀的目的節點。

### 什麼時候錄、什麼時候留

| 情況 | 行為 | 為什麼 |
|------|------|--------|
| 開始播放 | 開始錄 | 一次演唱＝一個檔案 |
| 暫停 | 錄音跟著暫停（長度也不算） | 那時候包廂在講話，不是這次演唱的一部分 |
| 切歌 | 照樣結算上傳 | 唱了兩分鐘才被切掉，那兩分鐘一樣是一次演唱 |
| 重唱 | 丟掉重來 | 評分已歸零，留著會配上一份對不起來的成績 |
| 設定頁關掉錄音 | 當場停手並丟掉 | 按下「不要錄」之後還錄著是不能接受的 |
| 唱不到 10 秒（可調） | 不留 | 前奏被切歌／沒人開口的錄音會把想留的擠掉 |

「唱了多久」用的是評分心跳每一幀的發聲判定累計出來的**時間**（對唱時兩支
有一支在唱就算），而不是幀數 —— 幀數在 30fps 的機器與 120fps 的螢幕上
同一首歌會差到四倍。單幀差距夾在 100ms，免得分頁切到背景時那段空白被算成在唱。

### 配額（磁碟保險絲）

錄音與歌曲快取共用同一顆磁碟。沒有上限的話，最後失敗的會是「歌曲下載不下來」，
而沒有人會聯想到是錄音吃光的。預設 50 首 / 512 MB，超過就從最舊、
**沒有標記保留（📌）**的那一筆開始刪；到九成先提醒（滿了才講已經來不及）。
舊的全被標記保留而配額又滿了時，**當場拒絕並說明**，不是存進去再默默刪掉它。

### 兩個容器層面的坑

* **webm 沒有 Duration**：`MediaRecorder` 是串流容器，開始錄時還不知道會錄多久，
  所以 `audio.duration` 讀出來是 `Infinity`，進度條拖不動。
  清單上的長度因此是**錄的時候量好跟著上傳**的；播放時則先 seek 到一個不可能的
  時間點逼瀏覽器算出真正長度再跳回 0（只做一次，而且只在真的要播的時候）。
* **容器因瀏覽器而異**：Chrome / Firefox 給 webm(Opus)，Safari 只給 mp4(AAC)。
  副檔名照實際 mime 決定，不然下載回去作業系統的播放器打不開。

相關 API：`GET /api/recordings`、`POST /api/recordings`（音檔走 raw body、
metadata 走 query string）、`GET /api/recordings/{id}/audio`（支援 Range）、
`POST /api/recordings/{id}/pin`、`DELETE /api/recordings/{id}`、`DELETE /api/recordings`。

## 🔗 錄音分享連結是怎麼運作的

`backend/services/share_links.py` 管的是「誰能拿到哪一筆、拿到什麼時候為止」，
錄音檔本身仍由 `recordings.py` 管。三個關鍵決定：

**「一次性」是時效性，不是「開啟一次就作廢」。**
照字面實作（第一個請求就把 token 燒掉）壞掉的是當事人自己的播放：
`<audio>` 拖進度條會發 Range 請求、Safari 會對同一個檔案再發一次、
手機切回前景也可能重連 —— 使用者看到的是歌播到一半死掉，重整還救不回來。
所以連結是**有時效**的（預設 24 小時、上限 30 天、隨時可撤銷），
「下載幾次就失效」則只算明確的下載（`download=1`），播放一律不算。

**沒有「永不過期」。** 錄到的是包廂裡所有人的聲音，一個永遠有效、
不需要登入的公開連結是事後想收也收不回來的東西。少一個選項換這個上限。

**失效分四種原因講，而且「錄音不在了」不是「連結不存在」。**
錄音被配額擠掉時沒有人按過任何按鈕，所以 `prune()` 對帳時不把那些連結整筆刪掉
（會變成「連結不存在」＝ 被理解成網址打錯，於是他一直重掃），
而是標成 `gone` 留七天（`TOMBSTONE_DAYS`），讓他看得到那句話。

| 端點 | 用途 |
|------|------|
| `POST /api/recordings/{id}/share` | 產生或**沿用**連結（`{"new": true}` 才換新的） |
| `GET /api/recordings/{id}/shares` | 這筆錄音發出去過的連結（含已失效與原因） |
| `DELETE /api/share/{token}` | 撤銷 |
| `GET /api/share/{token}` | 分享頁要的資料（只有這一筆看得到的欄位） |
| `GET /api/share/{token}/audio` | 音檔（`?download=1` 才算次數） |
| `GET /api/share/{token}/qr.png` | 這個連結的 QR |
| `GET /share/{token}` | 分享頁本身（靜態檔，資料由頁面自己去拿） |

分享索引放 `cache/recording_shares.json` 而**不是**錄音資料夾裡：
`RecordingLibrary._reconcile()` 會把錄音資料夾裡不在索引上的檔案當成孤兒檔刪掉，
放進去會在下次開機時無聲消失（所有已發出去的連結一起死）。

## 🎧 錄音轉 MP3 是怎麼做的

`backend/services/transcoder.py`。開關與位元率在 ⚙️ 系統設定 → 🎧 錄音轉 MP3。

**用到才轉，而且轉出來的是可以丟的東西。**
一個晚上錄三十首、會被帶走的大概三首，錄完就全部轉等於拿正在放歌、算音準、
跑人聲分離的那顆 CPU 去換沒人要的檔案。所以按下去才轉，轉好的留著當快取。

**MP3 快取不吃錄音配額。**

| | 錄音 | MP3 快取 |
|---|---|---|
| 位置 | `cache/recordings/` | `cache/recordings/mp3/` |
| 上限 | 設定頁（預設 50 首 / 512 MB） | 錄音配額的 1/4，**額外**佔用 |
| 滿了刪誰 | 最舊、沒有標記保留（📌）的 | **最久沒用到**的那一份 |
| 刪掉的後果 | 那一次沒了 | 下次按 🎧 MP3 重轉一份 |

讓 MP3 算進錄音配額的話會發生這件事：有人按了一下下載，包廂裡最舊的那一次
演唱被擠掉了 —— 而演唱刪掉就沒有，MP3 再轉一次就有。兩邊的可挽回性不對等，
所以它們不共用同一個配額。「額外佔用」等於磁碟總量最多是錄音配額的 1.25 倍，
這件事在設定頁與清單上都寫出來。

**LRU 用遞增序號（`mp3_seq`）而不是時間戳**：同一秒內連按兩次（一桌人同時
掃 QR）時間戳分不出先後，而且時間會倒退（NTP 校時）——
剛用過的那一份會突然變成「最久沒碰的」。序號跟著索引存，重開機接著跑。

**兩道關卡**（`TranscodeGate`）：同一筆同時只轉一次（擋「按了沒反應所以再按
一次」），整台機器同時只轉一個（唱歌永遠比轉檔重要）。排不進去時回一句
「現在忙」而不是無限等待。轉檔跑在 `asyncio.to_thread` 裡 ——
直接在 async 端點裡跑 `subprocess`，那十幾秒整台伺服器的 WebSocket 都會停住。

**先寫 `.part` 再原子換檔**：逾時或失敗留下的半個檔案若被當成 MP3 送出去，
使用者聽到的是「播到一半斷掉」，他的結論會是那一次錄音壞了。
順帶一提，`ffmpeg` 是**看副檔名決定輸出格式**的，所以指令裡要明講 `-f mp3`，
否則寫到 `xxx.mp3.part` 會直接 `Error initializing the muxer`。

**ffmpeg 不在就把功能收起來**，而且分得出三種狀況：`disabled`（設定頁關掉了）、
`not_installed`（叫不動）、`no_lame`（有 ffmpeg 但沒有 libmp3lame ——
為了授權把 lame 拆出去的精簡版是真的存在的）。裝好之後
`POST /api/recordings/mp3/recheck` 重新偵測，不必重開伺服器。

| 端點 | 用途 |
|------|------|
| `GET /api/recordings/{id}/audio?format=mp3` | 轉好的 MP3（`&download=1` 給檔名） |
| `GET /api/share/{token}/audio?format=mp3` | 分享頁的 MP3（失敗不扣下載次數） |
| `DELETE /api/recordings/mp3` | 清掉所有轉好的 MP3（錄音一個都不動） |
| `POST /api/recordings/mp3/recheck` | 重新偵測 ffmpeg |

## 📦 整晚打包是怎麼包的

`backend/services/night_export.py`（場次切割、檔名清洗、串流打包、打包名額），
畫面上那一行字在 `frontend/js/night-export.js`。
「相隔幾小時算換一場」在 ⚙️ 系統設定 → 📦 整晚打包。

### 一場是怎麼算出來的

**不是照日曆日期。** 包廂的一場是「晚上九點唱到凌晨兩點半」——
照日期切的話這一場會被切成兩半，而且後半（真正唱到嗨的那一段）會被標成
「隔天」。所以照**空檔**切：相鄰兩次演唱相隔超過 `recording_session_gap_hours`
（預設 6 小時）就算換了一場。

空檔法在另一個方向也對：同一天下午兩點與晚上九點各唱一輪，日期法會把它們
算成同一場（實際上是兩桌不同的客人），空檔法分得開。

時間戳壞掉的那一筆**不製造斷點** —— 切下去只會多出一場只有一首的鬼場次。
場次的 key 是**開始時間**（`20260913-2105`）而不是流水號：流水號會因為前面的
場次被配額清掉而整批位移，使用者剛複製的那個網址隔天就指到別場去了。

### 為什麼是串流，而且沒有 Content-Length

先在磁碟上生一份 zip 的話，一場 200 MB 就要**另外**佔 200 MB ——
而錄音配額存在的理由正是「這顆磁碟會被塞爆」，打包下載不該是那個把磁碟
塞爆的人。所以 zip 是一邊讀一邊往連線寫的，伺服器端永遠只有幾百 KB 在記憶體裡。

代價是沒有 `Content-Length`（瀏覽器不顯示百分比，畫面上有先說）。這是刻意的：
先算一次總長度再串流，中間只要有一筆被配額擠掉，實際送出的位元組就對不上
宣告的長度，瀏覽器會把整包當成**下載失敗** —— 那比沒有進度條糟得多。

`_StreamSink` 刻意只有 `write()` 與 `tell()` 而**沒有** `seek()`：
Python 的 `zipfile` 發現回頭寫不了就會改用 data descriptor（把 CRC 與大小寫在
檔案資料後面），而不是先留白、事後回頭補 —— 已經送出去的位元組是改不了的。

### 壓縮、檔名與曲目清單

| 項目 | 做法 | 為什麼 |
|------|------|--------|
| 音檔 | `ZIP_STORED`（不壓縮） | 已經是 Opus/AAC，再壓省不到 1%，CPU 要留給舞台 |
| 曲目清單 | `ZIP_DEFLATED` | 純文字，壓下去省七成，而它只有幾 KB |
| 檔名 | `01 21-05 歌名 - 演唱者.webm` | 車機與檔案總管照檔名排序，序號在前才留得住順序 |
| 非法字元 | `\ / : * ? " < > \|` 與控制字元換 `_` | 歌名裡的斜線與冒號在 Windows 存不下去 |
| 長度 | 照 **UTF-8 位元組**裁 | 中文一個字 3 bytes，照字數裁會裁出存不進去的名字 |
| 同名 | 自動讓開成 `(2)` | 同一首唱兩次不能互相覆蓋（那是一次真的演唱） |

`曲目.txt` 是**最後一個項目**，而且是打包完才生出來的 ——
所以它講得出「哪幾首沒包進來」（打包當下剛好被刪或被配額擠掉的那幾首）。
先寫的話它會說謊：清單上有一首資料夾裡沒有的歌，使用者會以為解壓縮壞掉。
同理，打包途中某一首開不起來就**跳過並記一筆**，不是整包放棄 ——
少一首加一行說明，比一個下載到 80% 斷掉的檔案有用得多。

### 同時只打一包，而且租約有期限

一包是幾百 MB，而那條網路正是舞台端串影片與 WebSocket 在走的。
第二個人按下去得到的是 429 與一句「正在打包另一份」，等一下再按同一個網址
就會成功。位子用**有期限的租約**放著：使用者按了下載又立刻關掉分頁時，
串流的 generator 有可能從來沒被跑過（沒有任何程式碼會執行到 `finally`），
沒有期限的話那個位子就永遠空不出來。

**整晚打包不跟著分享 token 走。** 一個 zip 是整場所有人的聲音，
那不是掃 QR 的人該拿得到的東西 —— 這條路只在點歌台（包廂內網）出得來。
整包也刻意**不轉 MP3**：一整晚三十首要轉三十次，等於拿正在放歌的 CPU 去換
檔案；要 MP3 的話按那一首自己的 🎧 MP3（曲目清單裡也寫了這句話）。

| 端點 | 用途 |
|------|------|
| `GET /api/recordings/sessions` | 有哪幾場、各幾首多大、是不是正在打包 |
| `GET /api/recordings/sessions/{key}/zip` | 串流下載一整場（`?singer=` 只要某一位） |

## 🎼 曲庫分類是怎麼判出來的

YouTube 不會告訴我們一首歌是國語還是台語，歌手欄位也只是上傳頻道名，
所以 `backend/services/library.py` 自己判（純函數，可單獨測）：

**語言別**（`detect_language(title, artist, lyrics_text)`）依序判斷：

| 順序 | 判準 | 說明 |
|:---|:---|:---|
| 1 | 明示標記 | 歌名／頻道名出現「台語」「粵語」「日文歌」等字樣，直接採用 |
| 2 | 諺文比例 | 諺文 ≥ 3 字，或諺文數 × 2 ≥ 漢字數 → 韓語 |
| 3 | 假名比例 | 假名 ≥ 3 字，或假名數 × 2 ≥ 漢字數 → 日語（所以歌名裡一個「の」不會誤判） |
| 4 | 方言用字 | 漢字 ≥ 2 時，粵語／台語專用字各數「出現幾種」，**≥ 2 種**才定案 |
| 5 | 其餘漢字 | → 國語 |
| 6 | 拉丁字母 | ≥ 3 個 → 英語，都不符合 → 其他 |

**歌手**（`normalize_artist(title, uploader)`）：先把頻道名的 `- Topic`、`VEVO`、
`官方頻道` / `Official` 後綴去掉；如果剩下的名字含唱片公司／音樂頻道字樣
（Records、娛樂、音樂、頻道…），改從「歌手 - 歌名」「歌手｜歌名」的標題前半段取；
兩邊都不行就歸到「未知歌手」，讓這些歌至少聚在一起。

判定結果寫回該首歌的 `metadata.json`（`language` / `artist_name`），
所以只算一次，之後瀏覽曲庫都是純讀檔；刪快取索引就跟著消失，不會留下孤兒資料。
分類判錯只影響歌落在哪個分頁 —— 判不出來一律歸「其他」，不會讓曲庫頁掛掉。

相關 API：`GET /api/library`（分類軸）、`GET /api/library/songs`（篩選 + 排序）、
`GET /api/library/new`（新歌榜）、`GET /api/library/recommend`（推薦歌單）。

## 🎶 和聲是怎麼算出來的

和聲是整個系統裡「錯了最刺耳、但最難用耳朵定位」的功能：唱出調外音的時候，
使用者只會覺得「這台機器的和聲很難聽」，不會知道是因為 Re 的上三度被算成 +4。
所以這件事分成兩層，各自都能單獨驗證。

### 第一層：要疊在哪個音上（`frontend/js/harmony-planner.js`）

1. **估調性**：拿這首歌的導唱音符（`pitch.notes`）做音級加權直方圖，
   跟 Krumhansl-Kessler 的大調／小調感知輪廓做 12 個旋轉 × 2 種調式的相關分析，
   取最高的那一個。
   - 權重用**時間長度**而不是出現次數：主音與屬音通常是長音，經過音又快又多，
     照次數算會把裝飾音當成調性骨幹。
   - 單一長音上限 **2 秒**：尾奏那個拖了 12 秒的長音不該一個人決定整首的調。
   - 兩道門檻：有效音符不足 **8 秒**（樣本不夠，相關係數只是雜訊）或
     相關係數低於 **0.45**（音級分布不像任何大小調）就**不給調性**。
2. **算音階度數**：把導唱音符換算成音階上的第幾度，往上／往下走兩度（三度和聲）
   或四度（五度和聲），再回推要移幾個半音。所以同一首歌裡每個音的移調量是
   +3 或 +4 交替出現的 —— 那才是和聲，固定值只是移調。
   - 非音階音（半音經過音、藍調音）吸附到最近的音階音再算度數：
     寧可平行三度，也不要跑出調外。
3. **沒有調性就退成低八度**：八度在任何調、任何音都不會錯。
4. **出聲時機**：沒人唱不出聲；需要音階資訊的聲部沒有導唱音符時也不出聲；
   同一個音符不重算移調量，換音符也要隔 80ms 才准再換一次
   （否則音符邊界上兩個音交替被判為 active 時，移調量會每幀跳一次，聽起來像和聲在抖）。

### 第二層：怎麼把聲音移過去（`frontend/js/harmony-worklet.js`）

Web Audio 沒有內建的移調節點（`playbackRate` 只能對 buffer 用、`detune` 只有
oscillator 有），所以移調要自己算。用的是可變延遲移調：

```
output(t) = input(t - d(t))      瞬時頻率比 = 1 - d'(t)
```

延遲量以固定斜率變化，出來的音高就被固定比例移動 —— 升八度就讓延遲以每秒 1 秒的
速度縮短。但延遲不能無限縮短，走到底就得跳回去，而那是波形的斷點。
所以用**兩條讀取頭**（延遲相差半個視窗）：快跳到底的那條先淡出，另一條淡入接手，
兩條增益永遠加起來等於 1。

- 視窗深度 **45ms**（平均延遲 22ms）：太短會讓跳回去太頻繁而變成明顯的震音，
  太長則和聲比主唱慢半拍，聽起來像回音而不是和聲。
- 交叉淡接刻意只佔一輪的 **30%**：兩條同時出聲時，同一個聲音以相差 depth/2 的
  兩個延遲相加 = 梳型濾波器，某些頻率會互相抵消（實測 330Hz 掉 27%）。
  縮短交叉區間把它壓到 **8% 以內**，主觀上從「聲音悶掉」變成聽不出來。
  拿掉交叉淡接不是選項 —— 那個跳點會變成每秒好幾次的爆音。
- 代價是移調越多、跳回去越頻繁，會有輕微的顆粒感。這對和聲完全可以接受：
  它本來就是效果音，真人和聲也不會跟主唱一模一樣。

DSP 核心寫成不依賴 Web Audio 的純陣列運算，所以 CI 每次都真的量一次
「輸入 220Hz、要求升八度，出來是不是 440Hz」（`frontend/tests/harmony-shifter.test.js`）。

### 音訊圖上的接點

```
micSource → highpass → deEss → agcGain → limiter → micGain ─┬→ monitorGain →┬→ masterGain
                                                            │               ├→ reverb
                                                            │               └→ echo
                                                            └→ 和聲移調 ×2 → 和聲音量 ─┘
```

接在 `micGain` **之後**（麥克風音量滑桿會一起帶動和聲，音量比例才不會跑掉）、
`monitorGain` **之前**（和聲跟主唱吃同一個外放總開關與同一組殘響回音）。
單人模式時 `monitorGain` 是 0，和聲自然也不出現。

## 🎤🎤 對唱的串音是怎麼判的

對唱模式（`frontend/js/duet-scorer.js`）的難處不是加第二個計分器，
而是**兩支麥克風在同一個房間**：A 唱歌的時候 B 的麥克風也收得到 A 的聲音。

不處理的話，B 只要把麥克風舉著站在旁邊，分數就會跟 A 差不多。
而這件事最惡劣的地方是 **它看起來完全正常** —— 兩邊的分數都在跳、
Combo 也在累計、音準線也在動。現場沒有任何人有辦法發現分數是假的。

所以整個模組的唯一工作是回答每一幀的那個問題：**這一幀該算誰的？**

| 規則 | 依據 | 為什麼需要 |
|------|------|-----------|
| 電平主導 | 兩支麥克風的**原始電平**差 ≥ 9 dB（設定頁 3~24 dB）就只算大聲的那一位 | 近距離收音的串音通常比本人小 12~20 dB |
| Schmitt 遲滯 | 進入獨佔差 9 dB、回到「兩邊都算」差 4.5 dB，中間維持現狀 | 沒有遲滯的話門檻附近每幀都在換人，兩邊的分數會亂跳 |
| 音高分歧例外 | 兩邊偵測到的音高差 ≥ 1.5 個半音 → 兩邊都給分 | 串音是同一個聲音的複製品，音高必然一樣；音高不同就是真的有兩個人 |
| 訊號門檻 | 音高分歧只在被壓的那一邊高於底噪 12 dB 時生效 | 底噪的自相關結果基本上是隨機數，拿它比「音高不一樣」等於放串音進來 |
| 噪音閘門 | 低於 -45 dBFS 當成這支麥克風沒人唱 | 與麥克風自動增益同一個值，「有沒有人」在兩處是同一件事 |

音訊圖上第二支麥克風走一條**與 A 完全相同**的前級鏈（同一個工廠函式產生，
兩邊各寫一次的話哪天調了 A 的 de-esser 忘了 B，在包廂裡只會被講成「B 麥比較差」）：

```
                                   ┌ analyserB（量原始電平，判串音用）
第二支麥克風 / 右聲道 → splitter ──┤
                                   └ highpass → deEss → agcGainB → limiter → micGainB → monitorGain
```

兩支麥克風共用 `monitorGain`（外放總開關）與同一組殘響／回音送出 ——
兩支的效果不一樣，聽起來會像兩個不同的房間在對唱。
但 analyser 與自動增益各自獨立：換人唱不用重調音量這件事，
對唱模式下反而更重要（兩個人的音量與距離幾乎不可能一樣）。

### 段落對決：哪些段落可以拿來比

兩位的段落成績本來就各自算好了（`section-scorer.js`），所以段落對決
（`compareSections()`）唯一的工作是「並排」這一步。而這一步最容易做錯的地方
不是算術，是**把分段接唱當成勝負** —— 對唱歌曲本來就是主歌 1 你唱、
主歌 2 我唱、副歌一起唱。所以每一段先過三道守門，才決定要不要給名次：

| 守門 | 門檻 | 不設會怎樣 |
|------|------|-----------|
| 兩邊都唱夠 | 各自被算到的導唱音符 ≥ 30 幀（約 0.5 秒，與段落評分同一個值） | 沒唱那一段的人被畫成 0%，畫面宣布「A 68% 完勝 B 0%」，而他沒辦法反駁 |
| 參與量相當 | 少的那一邊 ≥ 多的那一邊的一半 | 跟一句（40 幀）只要那一句準就有 100%，唱滿整段（400 幀）的人被自己的難處拉低 |
| 差距夠大 | 命中率差 ≥ 5 個百分點才點主場，否則平手 | 61% 對 59% 宣布主場，是在幫他們製造爭吵而不是回饋 |

過不了前兩道的段落照樣列出來，但標成「由 X 主唱」並淡化、另一邊顯示「—」
（不是 0%），也不計進比數。三道守門的每一條都有測試釘住
（`frontend/tests/duet-scorer.test.js`），包括「門檻必須與段落評分一致」這一條 ——
兩邊用不同的門檻會出現「單人成績單說這段有評分、段落對決說沒有」的畫面。

三件實作上的細節：

1. **判定用的是「增益之前」的原始電平**。兩支麥克風各有自己的自動增益，
   量放大後的訊號會把音量差抹平 —— 那就永遠判不出誰在唱。
2. **判定必須在計分之前**。照原本的流程（`tick()` 自己量、自己計分）
   會變成「先計分、再判定這一幀該不該計分」，已加的分數要減回去、
   Combo 與段落統計要回捲，那是找不完的 bug。所以改成兩階段：
   兩支各 `measureRms()` → `duet.decide()` → 各自
   `tick(t, { credit, reuseRms: true })`（沿用剛量好的波形，
   不重跑一次自相關 —— 那是整條 60fps 迴圈裡最貴的一步）。
3. **音高分歧修掉的是一種系統性不公平**。只有電平主導時，
   「唱得比較收的那一位」小 10 dB 就整首都沒分數。
   加上音高判斷之後，「小聲但唱的是另一個音」被正確認成第二個人，
   「小聲且音高一樣」仍然被判成串音 —— 這兩件事才第一次真的被分開。

### 判定調不好的時候（現場排查）

症狀是「我明明在唱，分數卻不動」。三個線索：

- 舞台計分板上被判成串音的那一列會**變淡並寫「串音靜音中」**。
- 結算畫面標出「有 XX% 的時間被判為串音」（超過 30% 才顯示）——
  那不是唱不好，是兩支麥克風靠太近或門檻設太高，分數本身已經不公平。
- 照那個比例調系統設定頁的**串音判定門檻**：
  房間小、喇叭大聲就調高；調太高會讓唱得比較收的那一位一直沒分數。

物理上最有效的一招仍然是**把兩支麥克風拉開、各自靠近嘴巴** ——
軟體只能在電平差存在的時候分辨，差不出來的時候誰也救不了。

### 麥克風有回音／嘯叫時

1. **先把 🎙️ 麥克風音量拉到 0** —— 立刻切斷監聽。音準評分不受影響，
   因為 `micAnalyser` 是直接從 `micSource` 接出去的，不經過 `micGain`。
2. 打開調音台按「乾聲」，把殘響與回音歸零，再慢慢往上加。
3. 若是筆電內建麥克風配內建喇叭，`echoCancellation` 是關閉的
   （開啟會破壞歌聲與音準偵測），聲學回授無法靠軟體解決 ——
   請改用耳機監聽或外接混音器。

## 🎧 演唱模式與回授（嘯叫）

筆電是回授最糟的幾何：麥克風與喇叭裝在同一個機殼裡，除了空氣傳導還有
**機殼結構傳導**，這條路徑靠拉開距離解決不了。自激通常落在 2~5kHz，
所以聽起來是「尖銳」而不是低頻嗡嗡。

### 單人模式（預設）

人聲**完全不進喇叭**——`monitorGain` 設為 0，位置在殘響與回音送出之前，
所以連效果也一起靜音。回授迴路被物理性切斷，不可能嘯叫。

音準評分照常運作：`micAnalyser` 是直接接在 `micSource` 上，不經過監聽路徑。

### 多人模式

人聲外放，**必須搭配外接喇叭**。外接喇叭直接消掉機殼傳導那條路徑，
距離每加倍再少 6dB。但真正決定成敗的是**近距離收音**——
嘴巴離麥克風 3cm vs 50cm，訊噪比差 24dB，這是最大的一筆。
理想配置是外接喇叭 + 指向性手持麥克風，喇叭擺在麥克風前方朝外。

### 軟體能做的（`_buildMicChain`）

軟體只能把回授門檻往上推幾個 dB，幾何才是主因。這條鏈處理四種實際問題：

| 節點 | 作用 |
|------|------|
| `micHighpass` 110Hz | 砍掉近接效應與桌面震動傳來的低頻 |
| `micDeEss` 高棚 5.5kHz | 回授自激與齒音都集中在這帶，可調 0 ~ -12dB |
| `micAgcGain` +9 / -12dB | 自動增益：把不同人、不同距離的音量拉到同一個目標（多人模式加成上限收到 +6dB） |
| `micLimiter` -14dB / 12:1 | 迴路增益短暫超過 1 時壓住，不讓它長大成嘯叫 |

順序不能換：自動增益一定在 limiter **之前**，否則它加上去的增益沒有任何東西擋著。

殘響的脈衝響應也改成高頻先衰減（模擬空氣吸收）。原本是純白噪，
尾巴的高頻跟起始一樣多，人聲卷積上去會有沙沙的金屬感。

### 音訊裝置選擇

舞台螢幕按 `S`（或右上角 ⚙️）開啟。裝置 ID 綁定該台機器，
所以只能在舞台端選，不能從手機遙控。輸出裝置切換需要 Chrome 110+
（`AudioContext.setSinkId`），其他瀏覽器請從作業系統的音效設定切換。

### 現場嘯叫的處理順序

1. 舞台按 `M` 切回單人模式，人聲立刻離開喇叭。
2. 或把點歌台的 🎙️ 麥克風音量拉到 0。
3. 調音台按「乾聲」關掉殘響與回音，再慢慢往上加。
4. 「🔆 柔化」往右拉，壓掉尖銳的那一帶。
5. 若在多人模式，可到系統設定頁把「麥克風自動增益」關掉 ——
   自動增益最多只會加 +6dB，但回授邊緣上那 6dB 就是差別。
