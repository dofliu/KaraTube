## 2026-09-07（第三輪）— 麥克風自動增益（v1.1.0）

**目標**：ROADMAP 的對照清單在 v1.0.0 已經全數打勾，這一輪開始做「後續想做的」
第一項 —— 麥克風自動增益。挑它先做的理由很實際：包廂裡最常聽到的抱怨不是音準
也不是效果，而是「換人唱又要重調麥克風音量」。上一位貼著麥克風吼、下一位離 20 公分
小聲哼，輸入電平差 20 dB 以上，這件事每首歌都會發生一次。

### 為什麼用前饋，不用回授

analyser 本來就接在 `micSource` 上（音高評分要的是原始訊號），
所以量到的電平天生就在增益節點之前 —— 直接拿來當前饋量測，一行都不用改。

反過來（量已經放大過的訊號）會變成「放大 → 量到更大 → 少放大 → 量到更小」的
呼吸迴路。更麻煩的是那個迴路的時間常數會跟房間殘響耦合在一起：
同一組參數在小包廂與大廳的行為完全不同，現場根本調不出來。前饋沒有這個問題，
代價是它不知道最終輸出多大聲 —— 所以削峰保護要自己用「輸入 + 目前增益」推估。

### 三條安全規則（順序就是優先度）

1. **沒人唱的時候絕不加增益**（噪音閘門 -45 dBFS）。這條最重要：安靜的房間也有底噪，
   照著「拉到目標音量」算下去會一路加到上限，然後第一個字進來直接爆掉，
   多人模式還會當場嘯叫。所以閘門以下只累計靜音時間，什麼都不動。
2. **要降立刻降（0.25s）、要升慢慢升（3s）**。降是保護、升是舒適；
   升太快會讓句與句之間的空隙把底噪一起抬起來，那個聲音很像機器在呼吸。
3. **範圍夾住**（+9 / -12 dB），而且**多人模式的加成上限收到 +6 dB**。
   人聲外放時每多加 1 dB 就離回授近 1 dB，這是物理，軟體只能選擇不要去踩。
   `configure()` 收到更小的上限時會**立刻**把現有增益夾回去（不等下一幀趨近）——
   收緊範圍是安全動作。

### 兩個寫錯了才發現的地方

- **容忍區不能寫成死區**。第一版是「差不到 1 dB 就不動」，結果增益永遠停在
  離目標 1 dB 的地方：趨近是指數的，一路靠近到剩 1 dB 就被死區凍住，
  等於系統性地永遠差一格（測試直接抓到 6 dB 只補到 5.0）。
  改成**遲滯**：差 1 dB 以上才「開始」調，一開始調就一路調到位（剩 0.15 dB 收手）。
- **削峰保護線是速度地板，不是「不准再降」的地板**。第一版把保護判斷寫在
  電平判斷的 `else` 前面，於是貼著麥克風吼的時候，增益被鎖在「剛好不削峰」的 -5 dB，
  而目標電平其實要求 -12 dB —— AGC 等於整首歌都沒作用。
  現在兩個目標都算出來取較小（降得多的）那個，只是用保護的時間常數去追。

### 換裝置歸零、換歌不歸零

- 換麥克風要 `reset()`：動圈換成電容，靈敏度差很遠，學到的增益是上一支的。
- 換歌只 `resetStats()`：一個人常唱兩三首，把增益丟回 0 dB 只會讓他每首歌的
  第一句都先小聲三秒。副作用是 `voicedSeconds`（同時是暖機計時器）歸零，
  所以換歌後會重新暖機 1.2 秒 —— 這剛好是想要的：換歌很可能換人，
  前奏那一兩句先維持現有增益、聽清楚新的人有多大聲再動。

### 電平表（意外地是最有用的部分）

舞台按 `S` 的音訊面板多一條收音電平表。原本只是 AGC 的除錯工具，
做完發現它解決的是另一個問題：**麥克風到底有沒有在收音**。
沒插好、選錯裝置、筆電實體靜音鍵沒開 —— 以前要開唱才發現，現在三秒就看出來。
三段顏色（灰／青／粉）對應的是「軟體幫不了、只有人能動」的兩種狀況：
太遠（加到上限也只是放大底噪）與太近（削峰救不回來）。

渲染迴圈在暫停時就 `return` 了，所以表會凍住 —— 面板開著且沒在唱的時候
另外跑一個 66ms 的試音迴圈，用新開的 `measureRms()`（只算 RMS，
不跑自相關音高偵測 —— 那是整條迴圈裡最貴的一步）。

### 刻意沒做的事

**沒有讓自動增益影響評分**。音高偵測的噪音門檻（RMS 0.015）還是照原始訊號判，
所以自動增益加得再多，分數還是照實際唱的算 —— 分數會因為音量被機器調過而改變，
是最難解釋的一種 bug。實務上這個門檻也很少擋到真的在唱歌的人：
它相當於 -36 dBFS，而 AGC 要出手的「小聲」通常在 -30 dBFS 上下，本來就過得了門檻。

### 測試

`frontend/tests/mic-agc.test.js` 24 條，全部是純資料邏輯（不碰 DOM、不碰 Web Audio）：
靜音餵一分鐘不加增益、暖機、遲滯收斂到位、不對稱曲線（0.4 秒內降得比升得多兩倍以上）、
削峰保護、長時間安靜放回中性、30fps 與 120fps 一致、分頁切回來的超大 dt、
壞資料（NaN / 負 RMS / 沒有 frame）不會讓增益變 NaN。
後端加一條設定範圍測試。合計後端 232 條、前端 67 條。

**下一步**：ROADMAP「後續想做的」剩下和聲效果、對唱模式（兩支麥克風分別評分）、
情境背景、預先排程處理、多包廂。對唱模式看起來最有價值，但它要動到
`getUserMedia` 的多裝置與評分的分軌，是比這一輪大的改動。

## 2026-09-07（第二輪）— Docker 一鍵部署 + 正式發布（v1.0.0）

**目標**：ROADMAP 只剩「系統」那兩項，做完就是可以發布的系統。
這一輪不新增演唱功能，全部在處理「別人怎麼把這台機器架起來、
以及三個月後怎麼知道他跑的是哪一版」。

### 版本號：唯一真相來源
- 新增 `backend/version.py`（`__version__` + codename + `KARATUBE_BUILD`）。
  FastAPI 的 `version=`、`/api/version`、設定頁頁尾、release 打包全讀這一個常數。
- 新增 `GET /api/version` 與 `GET /api/health`。
  健康檢查刻意不碰模型也不碰磁碟 —— 拿它當容器 HEALTHCHECK 才不會在
  處理歌曲吃滿 CPU 時被誤判成掛掉。
- 新增 `CHANGELOG.md`。`tests/test_version.py` 守住
  「CHANGELOG 最上面那一筆 == version.py」與版本順序遞減；
  release workflow 再比對 git 標籤。發出去的東西版本號對不上是最難追的問題，
  三道檢查都很便宜。

### 部署設定環境變數化
- `config.py`：`KARATUBE_HOST` / `KARATUBE_PORT` / `KARATUBE_PUBLIC_HOST` /
  `KARATUBE_PUBLIC_PORT` / `KARATUBE_CACHE_DIR`，值壞掉一律退回預設 ——
  機器可以印錯網址，但不能因為一個環境變數打錯就開不起來。
- **`public_base_url()`**：QR code 與「手機點歌」網址原本是
  「自動偵測本機 IP + 監聽 port」。容器裡偵測到的是 bridge 網段（172.17.x.x），
  手機掃了根本連不進去；反向代理後面對外的 port 也不是容器監聽的那個。
  現在設了 `PUBLIC_HOST/PORT` 就以它們為準，80/443 不寫進網址。
- `run.py`：容器裡不開瀏覽器（偵測 `/.dockerenv` 或 `KARATUBE_IN_CONTAINER`），
  否則開機日誌會被 xdg-open 的錯誤洗版、看起來像壞了。banner 印出版本號。

### Docker
- `Dockerfile`：依賴分兩層（改程式碼不用重裝 PyTorch，那層要幾分鐘）、
  內建 ffmpeg、非 root（uid 10001）、`/data` 為 volume、`/api/health` HEALTHCHECK。
  GPU 版只要換 `BASE_IMAGE` build arg 成 CUDA 映像。
- **踩到的坑**：`~/.cache` 必須先在映像裡建好並 chown。
  Docker 掛 named volume 時會沿用映像裡那個目錄的擁有者，
  沒先建的話 volume 是 root 的，非 root 行程下載不了 Whisper / Demucs 權重，
  而且錯誤訊息完全看不出是權限問題。
- `docker-compose.yml`：曲庫與模型權重分開兩個 volume（前者是使用者資料要備份，
  後者只是下載快取）、GPU 區塊註解好放著、`.env` 帶 `KARATUBE_PUBLIC_HOST`。
- `.dockerignore`：`cache/` 是最重要的一條 —— 用過的機器那裡有好幾 GB，
  沒排除的話光是送 build context 就要等很久。

### 發布流程
- `.github/workflows/release.yml`：推 `v*` 標籤 → 跑完整 CI ＋ 比對
  「標籤 == version.py」→ 打包 `.tar.gz` / `.zip` ＋ SHA256 校驗檔 →
  從 CHANGELOG 抽出該版段落當 release notes → 建 GitHub Release。
  發布前重跑一次 CI 是刻意的：PR 過了不代表當下的 main 是好的。

### CI
- 新增 `deploy-files` job：`docker compose config -q` ＋ `docker build --check`。
  不在 CI 裡真的建映像（PyTorch 那層要幾 GB），但「一鍵部署壞在一個 YAML 縮排上」
  是最不該發生的事。`--check` 對風格建議也會回非零，所以只有真正的錯誤才擋 PR。

### 文件
- 新增 `docs/DEPLOYMENT.md`：硬體需求、Docker / 直接安裝 / GPU、環境變數表、
  Nginx 反向代理（WebSocket upgrade 標頭是必要的）、
  麥克風需要安全來源（`getUserMedia` 只在 https 或 localhost 給）、
  systemd 開機自啟、備份哪幾個檔、升級與發布、部署常見問題。
- README（徽章、Docker 快速啟動、版本與發布章節、目錄結構）、
  USER_GUIDE（安裝改為兩種方式 + 「我在跑哪一版」）、
  ROADMAP（對照清單全數打勾，改列後續想做的）、CHANGELOG（1.0.0）、STATUS.yaml。

### 測試（後端 231 條 + 前端 43 條，全綠）
- 新增 `tests/test_version.py`（5 條）：語意化版本格式、`version_info()` 形狀、
  `KARATUBE_BUILD`、CHANGELOG 一致性與順序。
- 新增 `tests/test_config.py`（4 條）：環境變數轉整數（含空白、空字串、`auto`、
  `80.5`、中文數字都要退回預設）、`PUBLIC_PORT` 預設等於監聽 port。
- `tests/test_api.py` +3：`/api/version`、`/api/health`、
  `public_base_url()` 的三種情境（80 / 443 / 自訂 port）。

### 下一步
ROADMAP 的商用對照清單已全數完成，v1.0.0 可以打標籤發布。
之後想到再補的項目（麥克風自動增益、對唱模式、多包廂等）已列在 ROADMAP 下半。

## 2026-09-07 — 導唱音量自動 ducking（唱穩了導唱自己退場）

**目標**：ROADMAP「音訊」剩下的最後一項。商用機（DAM 的 *ガイドボーカル自動フェード*、
金嗓的「導唱漸弱」）早就不把導唱人聲當成開／關兩檔的開關 ——
它跟著唱的人走：唱穩了退到背景，走音或忘詞時回來扶一把。
KaraTube 原本只有一支「導唱人聲 0~100%」的滑桿，等於要使用者自己在
「怕忘詞」與「怕唱不出自己的味道」之間二選一。

### 新模組：`frontend/js/guide-ducker.js`

不做任何新的音訊分析：**逐幀判定沿用評分心跳已經算好的結果**
（這一幀有沒有導唱音符、有沒有唱出聲、準不準），
`PitchEngine.tick()` 從「不回傳」改成回傳這份判定，段落評分與 ducking 共用同一份 ——
音高偵測是整條 60fps 迴圈裡最貴的一步，而且兩邊各自偵測一次的話，
算出不同結果時會非常難查。

這個功能錯了會非常明顯地毀掉體驗，所以三個參數都是照失敗模式訂的：

- **不對稱曲線**：淡出時間常數 1.6 秒、淡回 0.22 秒。
  退得太快 → 副歌唱準兩個字導唱就消失，第三個字忘詞當場裸奔；
  回得太慢 → 已經走音兩秒才聽到導唱，那時人早就放棄這一句。
- **Schmitt 遲滯門檻 0.55 / 0.35**：命中率在門檻附近抖動時維持現狀。
  沒有遲滯的話導唱會一直忽大忽小，那比全開還吵。
  門檻是照逐幀判定的實際手感抓的（逐幀命中比直覺嚴格，唱得不錯的人落在 0.5~0.7，
  照直覺設 0.8 會永遠不退）。
- **暖機 3 秒**：沒有這道門檻，前奏後第一個音唱準就會觸發 —— 那是運氣不是穩定。
- **間奏不改變狀態**：`hasNote=false` 的幀不更新信心度也不重新判定。
  那段本來就沒有導唱人聲可退，硬要衰減只會讓副歌一進來導唱先大聲一下再退，變成幫倒忙。
- **深度上限 0.95**：永遠留一點導唱在背景當安全網，不給「完全消音」這個選項。
- 命中率用時間常數而不是幀數的 EMA，所以 30fps 的機器不會變成兩倍慢
  （測試直接比對 30fps 與 120fps 的收斂位置）。

### 音訊圖：導唱倍率與導唱音量分成兩個節點
`sourceVoc → guideDuckGain → gainVoc → normGain → masterGain`。
刻意不把倍率乘進 `gainVoc`：使用者拉的導唱音量與機器的自動退場是兩件事，
混在同一個 gain 上，自動退場後再去動滑桿，滑桿刻度就會跟實際音量對不起來。

### 舞台與結算
- 舞台右下角新增 🎚️ **導唱自動淡出 XX%** 徽章（練唱徽章正上方，同一欄不會疊）。
  沒有這個提示的話，導唱變小聲只會被當成「機器把導唱吃掉了」。
  文字每 250ms 才更新一次 —— 60fps 直接寫 `textContent` 會每幀重排版面。
- 結算畫面新增 **🎚️ 導唱獨立度 XX%**（導唱自動淡出的時間比例）。
  這個數字比總分更能看出進步：分數會被歌難不難影響，
  「上週副歌整段靠導唱，這週導唱退場了七成」才是直接的回饋。
  導唱沒開、或有效演唱不到 20 秒就整行不顯示 —— 兩句歌的比例只是雜訊。

### 設定
- `settings.py` 新增 `guide_duck_enabled`（預設開）與 `guide_duck_depth`（預設 0.6，上限 0.95）。
- 點歌台系統設定頁多一組「🎚️ 導唱自動淡出」（表單照後端欄位規格自動長出來）。
- 改設定不重置狀態：唱到一半調深度不該讓導唱跳回全開；
  但開關切換兩個方向都重來（關掉要立刻放掉導唱，打開要重新暖機）。
- 導唱音量本來就是 0（純伴奏）時整段邏輯不跑，徽章也不亮。

### 測試（後端 219 條 + 前端 43 條，全綠）
- 新增 `frontend/tests/guide-ducker.test.js`（17 條）：暖機門檻、退場深度與漸進、
  救援速度（走音六秒內回到接近全開）、遲滯區間不翻轉、間奏不改變狀態與不計入統計、
  關閉時完全不作用、深度夾限、唱到一半改設定、`reset()`、獨立度統計的守門、
  更新頻率無關性（30fps vs 120fps）、分頁切回來的巨大 dt、非法輸入不產生 NaN。
- `tests/test_settings.py` +1：導唱淡出預設值與深度夾限（上限刻意不到 1.0）。

### 文件
- README（核心特色 19、目錄結構、測試條數）、USER_GUIDE（系統設定新章節、
  導唱獨立度、常見問題「導唱自己變小聲是壞了嗎」）、ROADMAP 打勾、STATUS.yaml。

### 下一步（建議下輪迭代）
1. Docker 一鍵部署（ROADMAP 系統類只剩這項與 release 打包）。
2. 正式發布：版本號、release 打包、安裝說明。

## 2026-09-06 — 段落評分（哪一段唱得最好／最差）＋ 前端單元測試基礎建設

**目標**：ROADMAP「演唱體驗」剩下的最後一項。總分是娛樂，段落評分才是能拿來練歌的資訊 ——
「62 分」只讓人沮喪，「副歌 2 只有 31%、主歌都在 70% 以上」直接指出下一輪要練哪裡。
順手把「前端單元測試」那一格也補掉：這次新增的邏輯剛好是可以脫離瀏覽器測的純資料邏輯。

### 新模組：`frontend/js/section-scorer.js`

沒有新增任何分析：**分段沿用練唱模式已經在算的曲式**
（`chorus_detector` 由歌詞重複結構切出的前奏/主歌/副歌/間奏/尾奏），
**判定沿用評分心跳每幀已經算好的結果**（有沒有導唱音符、有沒有唱出聲、準不準）。
段落評分做的事只有一件：把同一幀的結果依時間歸到所屬段落再累計一份。

- `normalizeSections()`：濾掉前奏／間奏／尾奏（沒有導唱音符，列出來只會是一排 0%）、
  丟掉時間軸壞掉的資料、依起點排序，並丟掉與前一段**重疊**的段落 ——
  重疊會讓「一個時間點只對到一段」的前提失效，寧可少評一段也不要對錯段。
  用「排除清單」而不是「白名單」，後端日後多切出 bridge 之類的段落會自動納入。
- `sectionIndexAt()` 用**二分搜尋**，不用「記住上一段往前掃」的游標：
  A-B 循環與進度條跳轉會讓時間任意前後跳，線性游標在那些情境下會退化成每幀重掃整首。
- `summary()`：每段命中率 = 該段命中幀 ÷ 該段有導唱音符的幀。
  這個定義讓 A-B 循環唱三輪也算得對（整段累計的比例，不是最後一輪覆蓋前面）。
- `gradeForAccuracy()`：等級門檻從 `pitch-engine.js` 抽出來共用，
  單段評語與整首總評的手感才一致（原本門檻寫死在 `getFinalResult()` 裡）。

### 兩道「不亂下結論」的守門（這個功能真正的難點）

功能本身只是加總，難的是**什麼時候該閉嘴**：

1. **太短的段落不參加評分**：導唱音符不足 30 幀（60fps 下約 0.5 秒）的段落標成未評分。
   一兩幀的運氣不該決定誰是「最差的段落」。
2. **表現太平均就不點名**：最佳與最差差距 < 5 個百分點時 `best` / `worst` 都回 `null`，
   前端只畫長條圖不下結論。整首均勻地唱到 55% 時說「副歌 2 是你最差的段落（54%）」
   是在製造焦慮，不是回饋。
   —— 這條的邊界踩到浮點雷：`0.6 - 0.55` 在 IEEE 754 裡是 `0.049999…`，
   直接比門檻會讓「剛好差 5 個百分點」隨機失效（測試先抓到，才改成先四捨五入再比）。

同分時最佳取先唱到的那一段，讓結果不隨排序演算法的實作而變。

### 舞台結算畫面

- 成績單中間新增 **📊 段落表現**：每段一條命中率長條（最佳標黃、待加強標粉），
  上方點名 💯 最佳段落 / 📈 待加強；點不出來時寫「整首表現平均，沒有明顯拖分的段落」。
- 可評分段落不到兩段（沒歌詞、只唱一段就切歌）整塊收起來 ——
  段落評分是加分項，總分與等級不受影響。
- 長條從 0 長出來的動畫和分數滾動一起跑，維持商用機結算畫面的儀式感；
  段落多的歌超過高度就在卡片內捲，不會把卡片撐出畫面。
- 段落預覽（首句歌詞）進 `title` 提示，且所有插進 `innerHTML` 的文字都跑過 `escapeHtml()`。

## 2026-09-06 — 曲庫分類瀏覽（語言 / 歌手）＋ 新歌榜 ＋ 推薦歌單

**目標**：補上 ROADMAP「點歌體驗」剩下的兩項。搜尋很好用，但商用點歌機的主畫面
從來不是只有搜尋框 —— 使用者常常是「想唱台語歌，但一時想不起歌名」，
這時要能用**語言別**和**歌手**把曲庫縮小到看得完的範圍。

### 新服務：`backend/services/library.py`

曲庫是使用者點過的歌自然長出來的，而 YouTube 只給我們標題與頻道名，
沒有語言標籤、也沒有真正的歌手欄位。所以分類得自己判：

**語言判定**（`detect_language`，純函數）依序：

1. **明示標記**最準 —— 歌名／頻道名出現「台語」「粵語」「日文歌」直接採用。
2. **諺文**：≥ 3 字，或諺文 × 2 ≥ 漢字 → 韓語。
3. **假名**：≥ 3 字，或假名 × 2 ≥ 漢字 → 日語。
   用比例而不是「有假名就算」，是因為華語歌名很愛夾一個「の」
   （「我の愛」不該被丟進日語分頁）。
4. **方言用字**：漢字 ≥ 2 時數粵語／台語專用字**出現了幾種**，
   要 ≥ 2 種才定案 —— 單一個「厝」或「係」在國語歌詞裡也會出現，
   一個字就判定的話誤判率高到分類沒有意義。用字表只收辨識度高的
   （所以不收「係」「仲」這種國語文本也常見的）。
5. 其餘漢字 → 國語；拉丁字母 ≥ 3 → 英語；都不符合 → 其他。

判語言只讀歌詞前 600 字：整首讀進來對結果沒有幫助，只是白花 I/O。

**歌手正規化**（`normalize_artist`）：先去掉 YouTube 的機器後綴
（`- Topic`、`VEVO`、`官方頻道` / `Official`）；剩下的名字若含唱片公司／
音樂頻道字樣（Records、娛樂、音樂、頻道…），改從「歌手 - 歌名」「歌手｜歌名」
的標題前半段取；都失敗歸「未知歌手」——
讓判不出來的歌聚成一堆，比每首各自成為一位「歌手」好用得多。

**快取策略**：判定結果寫回該首歌的 `metadata.json`（`language` / `artist_name`），
每首只算一次，之後瀏覽都是純讀檔。不另外存索引檔 ——
刪快取時分類跟著消失，不會留下對不上的孤兒資料。

### 新 API

- `GET /api/library` — 分類軸：每個語言別幾首、每位歌手幾首（歌多的排前面）。
- `GET /api/library/songs?language=&artist=&sort=` — 篩選 + 排序
  （最新加入 / 最常點唱 / 歌名 / 歌手）。
- `GET /api/library/new` — 新歌榜，14 天內加入的標 `is_new`。
- `GET /api/library/recommend` — 推薦歌單，每首附推薦理由。

只列檔案齊全的歌：不完整的快取唱不了，出現在點歌清單上只會讓人按下去撲空
（快取管理分頁另有一套，那裡本來就是要看得到壞資料夾才刪得掉）。

推薦歌單四種來源依序取、去重：好久沒唱的老朋友（唱過 ≥2 次但最近沒點）→
最近唱過的歌手的其他歌 → 從沒唱過的新歌 → 補位（最新加入）。
每首都帶 `reason`，因為推薦講不出道理就只是另一份亂排的清單。

### 點歌台 UI

- 新增兩個分頁：**🎼 分類瀏覽**（語言 / 歌手 / 排序三列膠囊篩選，可疊加）

  篩到沒有結果時篩選列**必須留著**，不然按了一個空分類就卡死、選不回來。
- 歌手可能有幾十位，那一列圈在固定高度內捲動，不讓篩選列把歌卡擠出畫面。

## 2026-09-05 — 練唱模式：A-B 段落循環 + 自動副歌偵測 + 段落跳轉

**目標**：補上商用 KTV 點歌機的「副歌重播」。這是 ROADMAP「演唱體驗」剩下的最後一項，
也是一般人真正拿伴唱機來練歌時最常用的功能 —— 沒有它，練副歌只能整首重唱。

### 新功能：🔁 練唱模式（A-B 區段循環）

- **共享狀態**：`QueueManager` 新增 `loop_enabled` / `loop_start` / `loop_end` 三個欄位，
  跟其他調音參數走同一條 `/api/control`，所以點歌台、手機、舞台看到的圈選範圍永遠一致。
- **收斂規則**（`_normalize_loop`）：
  - A、B 按反了自動對調 —— 聽到一半才想圈這段，先按 B 再按 A 是很自然的操作，不該報錯。
  - 區間缺一角、或短於 1 秒時一律關掉循環：零長度的區間會讓舞台在同一秒鐘上瘋狂 seek。
  - 換歌時清空（`clear_loop()` 掛在 `play_next`）：A-B 點屬於某一首歌，
    留著會讓下一首在莫名其妙的地方跳回去。
- **跳轉指令**：新增 `POST /api/seek` → `CONTROL_COMMAND: SEEK`。
  伺服器不持有播放位置（媒體在舞台端），所以只送指令、不改自己的狀態。

### 新功能：🎯 自動副歌偵測（`backend/pipeline/chorus_detector.py`）

**問題**：「副歌在哪裡」沒有人會替每首歌手動標記，但沒有這個資訊，
「一鍵副歌重唱」就只能退化成使用者自己聽著抓時間。

**作法**：純文字重複結構分析，不碰音訊。歌詞時間軸在流水線裡已經對齊好了，
而副歌的定義本來就是「整段歌詞重複出現的區塊」，所以拿逐行文字找
「最長、重複最多次的連續區塊」就夠了 —— 比做音訊自相似矩陣便宜好幾個數量級，
而且找到的行可以直接對回它自己的時間。

1. 每行正規化（去標點、空白、轉小寫）：不同來源的 LRC 標點寫法不一，
   不正規化會把同一句判成兩句。
2. 對每組起頭相同的行往下延伸取最長共同區塊，並把它的每個前綴也收進候選 ——
   四行副歌可能只有後兩行在尾聲又多唱一次，那個兩行版本的重複次數比較高，值得參加評分。
3. 評分：先看涵蓋的總行數（重複次數 × 每次行數），同分時偏好「一次比較長」的區塊。
4. 時間守門：低於 5 秒（跳針）或超過 100 秒（抓到整段主歌+副歌）的候選淘汰，換下一名。
5. 全部落空時退一步找「重複三次以上的單行鉤子」（口水歌），
   單行本來就只有兩三秒，時間門檻要跟著放寬到 2.5 秒，否則這條退路等於沒有。
6. 再找不到就回 `None`，前端退回手動 A-B，不會壞。

段落切分（`detect_sections`）則靠唱句之間的靜默：空超過 6 秒算換段，
切出 前奏 / 主歌 N / 副歌 N / 間奏 N / 尾奏，副歌段用偵測結果標記。
新端點 `GET /api/songs/{song_id}/sections` 即算即回，不寫檔、不需要快取。

### 前端

**點歌台（`controller.js` / `index.html`）**
- 調音台新增「🔁 練唱模式」區塊：`A` / `B` 設點鍵（顯示目前時間）、開始/停止循環、清除、
  **副歌重唱** 一鍵鍵，以及自動切好的段落膠囊列（點標籤跳轉、點 🔁 循環該段）。

## 2026-09-04 — 自動音量平衡（EBU R128）+ 系統設定頁 + pipeline 純函數測試

**目標**：把「發布給別人用的機台」還缺的兩件事補上 ——
使用者不改程式碼就能調整機台行為（設定頁），
以及不用每首歌手動轉音量（自動音量平衡）。順帶補齊 pipeline 的單元測試防線。

### 新功能：🔊 自動音量平衡（EBU R128 / ITU-R BS.1770-4）

**問題**：YouTube 來源的響度差距極大 —— 官方 MV 母帶常壓到 -8 LUFS，
個人上傳的現場版可能只有 -22 LUFS。中間差 14 dB，主觀上大約是「三倍大聲」，
所以每換一首歌就要重新轉音量，這是包廂裡最煩人的體驗之一。

- 新增 `backend/pipeline/loudness.py`：自己實作 BS.1770-4 的
  **K 加權（高頻棚 + RLB 高通）→ 400ms/75% 重疊區塊 → 絕對閘 -70 LUFS
  → 相對閘 -10 LU → 整合響度**。
  - 濾波器係數依類比原型在任意取樣率重新推導，在 48kHz 會退化成規格書列出的參考係數
    （測試直接比對到小數第 9 位）。
  - 不直接抓 pyloudnorm：只需要一個數字卻要多帶一層相依，而且純函數
    （吃 numpy 陣列、吐一個數字）才好用合成訊號在 CI 上測。
  - 濾波優先用 scipy，沒有 scipy 時走純 numpy 備援 —— CI 只裝 numpy 也跑得動。
- 流水線最後（分離、對字幕、抽音高之後）量一次 **伴奏軌** 的響度，
  把 `lufs` / `peak_dbfs` / `gain_db` 存進 metadata。量測失敗只是沒有這筆資料，
  不會讓整首歌處理失敗。
- 新 API `GET /api/songs/{id}/loudness`：回傳**依當下設定重算**的增益 ——
  目標響度改了不用重跑流水線。metadata 沒有響度資料的舊歌會現場量一次並補寫回去，
  所以既有曲庫不必整批重處理。
- 播放端 `audio-effects.js` 新增正規化增益節點 `normGain`：
  `gainInst / gainVoc → normGain → masterGain`。
  **麥克風與氣氛音效直接接 masterGain，不經過這個節點** ——
  換歌調整音量平衡時，唱歌的人不會覺得自己的聲音忽大忽小。
- 三重保險，寧可少調也不要調壞：量不到 → 0 dB；增益夾在 ±12 dB；
  峰值保護（拉完不超過 -1 dBFS）。

### 新功能：⚙️ 系統設定頁

- 新增 `backend/services/settings.py`：以 `SETTINGS_SPEC`（型別／範圍／選項）為單一事實來源，
  存成 `cache/settings.json`。
  - **越界夾回合法值、未知欄位忽略**，不丟例外 —— 設定頁是給人用的，
    手機上滑錯一格不該讓伺服器回 500，舊版前端送新欄位也不該壞。
  - 設定檔壞掉退回預設值，不阻擋開機（機台不能因為一個 JSON 壞掉就唱不了歌）。
- 新 API：`GET/POST/DELETE /api/settings`、`POST /api/settings/apply-defaults`。
  改動透過 WebSocket 廣播 `SETTINGS_UPDATE`，所有裝置即時同步；
  舞台端一連上就會收到（片頭卡秒數、結算開關都在裡面）。
- 可設定的五類：
  1. **開機預設調音** —— 開機時自動套進共享狀態；也可一鍵「套用到現在」不必重開。
  2. **自動音量平衡** —— 開關與目標響度。
  3. **快取上限與自動清理** —— 每處理完一首檢查一次，超過就從最舊的刪，

  4. **AI 模型** —— Whisper / Demucs 模型改成可選；模型在啟動時載入，
